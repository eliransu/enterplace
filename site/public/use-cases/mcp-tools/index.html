Use casesMCP tools

Know which agent may call which tool, and who approved the dangerous ones.

Agents reach GitHub, the data warehouse and the deploy system through MCP servers. Each server has its own token, and the list of who may call what lives in nobody's system. Gantry serves all of them at one endpoint and checks every call.

What goes wrong without control

A shared token per server
Every agent calls the GitHub server with the same credential. The server's log shows one caller, and it is not a person.
Every tool for everyone
An agent that needs to read issues can also delete a repository, because the server offers both and nothing sits in between.
Tools that change under you
A tool's description and schema are instructions to the model. A server that changes them can change what an agent does, and nobody is told.
No record of tool calls
When a deploy runs at night, you can see that it ran. You cannot see which agent asked, on whose behalf, with what arguments.

The steps

All of it is in the same policy file as your model rules. A tool is hidden unless a rule lists it.

  1. List your MCP servers

    Gantry serves their tools, prompts and resources at one endpoint, /mcp. Callers see each tool as server.tool. The server's own credential is read from an environment variable and never reaches a caller.

    MCP gateway in the docs

  2. Give each rule its tools

    A rule's tools list is what its people can see and call. A rule with no list gets no tools.

  3. Make dangerous tools wait for a person

    A call to a tool under approve_tools is held until an admin approves or denies it on the console's MCP approvals page, which shows who asked, the rule and the arguments. The decision record says who approved.

  4. Hold tools that changed

    Gantry pins each tool the first time it lists a server: a hash of its title, description, schemas and annotations. With tool_changes: block, a tool whose hash changed is left out and its calls are refused until an admin approves the new version.

  5. Connect the clients

    A client points at https://your-gantry/mcp and sends a Gantry key, or signs in with OAuth from the client. A server can also run each call with the caller's own credential, so the call happens as that person at the server too.

What you see afterwards

  • One list of every tool on every server, on the console's MCP tools page, with a stop and start button for each.
  • Every tools/call, prompts/get and resources/read in the audit log, under the person's name, before it reaches the server.
  • A mcp_tool_changed record, with the old and the new hash, whenever a tool changes.
  • Tool calls pass the rule's guardrails, so a secret in a tool argument is caught like a secret in a prompt.
approval_denied
An admin denied the call.
approval_timeout
Nobody answered within the time the rule sets.
tool_changed
The tool's description or schema changed and has not been approved.
credential_needed
The server runs calls as each person, and this person has not connected an account yet. The refusal carries the link.

Limits to know before you start

  • Gantry speaks Streamable HTTP to upstream servers. A server that only runs as a local process on a laptop is outside it.
  • An approval is a person looking at the arguments. It is as good as the attention the admin gives it. Keep the list of approved tools short.
  • A pin covers the tool's description and schema. It does not inspect what the server does when the tool runs.
