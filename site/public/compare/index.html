Enterplace next to LiteLLM and Bifrost.

Enterplace covers the gateway work you expect: one endpoint, several providers, routing, retries, caching, budgets. It is younger than both projects and each of them does some jobs better. The difference is what Enterplace does before a request leaves.

What Enterplace is built around

Five design decisions. Each can be checked in the docs or by running the binary.

The record comes first
Every request, allowed or refused, gets a hash-chained audit record before it is forwarded. If the record cannot be written, the request is refused. The chain is checked with one command, in the open source edition.
A wrong policy is an error
enterplace check names the file, the line and the nearest known word for every mistake. A misspelled field does not start quietly.
Nothing is dropped silently
The request body is forwarded byte for byte, except where your policy changes it. An unknown query parameter is refused by name.
Keys shown once, no prompts in the log
Enterplace keys are stored as a SHA-256 hash. The audit log holds no prompt text, answer text or keys.
One image, one database
A single static binary in an image built from scratch, running as a non-root user, with Postgres as the only other part. No Redis.

Where the others lead

If one of these is what you need most, the older project is the better choice today.

LiteLLM

  • Providers. It supports far more providers, with translation between their APIs.
  • A shared cache. Its cache is shared by every instance through Redis. Enterplace's answer cache is per replica.
  • Admin UI. A fuller admin interface. Enterplace's console is smaller.
  • History. More years in production at more companies.

Bifrost

  • Forwarding speed. It is built for low overhead with features on, and publishes benchmarks. Enterplace publishes no latency figures on this site.
  • Governance objects in open source. Customers, teams and virtual keys with budgets and rate limits.
  • Response headers that name the provider and the resolved model.
