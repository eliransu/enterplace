What Gantry protects, and where it stops.

Gantry exists so that no AI request leaves without a known caller, a policy decision and a record. This page says how it does that, what it does not cover, and where your data goes.

Status. Pre-1.0, version 0.1.0. Gantry has not yet had an independent security audit.

What Gantry protects

  • Gantry keys are stored hashed. Each key is 256 random bits from the operating system, shown once. Only its SHA-256 is kept, in a keys file created with mode 0600, and keys are looked up by hash.
  • Provider keys never reach callers. Gantry reads them from environment variables, holds them in memory marked as sensitive, never prints or records them, and sends each only to the provider that needs it.
  • Caller credentials are stripped. Before forwarding, Gantry removes any header whose name contains authorization, key, token, secret, organization or project (except idempotency-key), every x-amz header, proxy and CDN headers that carry the caller's address (x-forwarded-*, forwarded, via, cf-*, x-envoy-* and any name ending in -ip or containing client-ip or remote-addr), any header carrying the caller's Gantry key, Cookie, Host and the hop-by-hop headers.
  • Fail closed. The audit record is written before anything is forwarded. If the log cannot be written, every request is refused with audit_unavailable and /healthz answers 503 until an admin restarts Gantry. An unreadable kill switch file refuses every request with kills_unreadable.
  • A hash-chained audit log. Each record holds the hash of the one before it. gantry audit verify names the first changed, inserted, removed or reordered record, and Gantry refuses to start on a log whose chain does not hold. Records hold no prompt text, answer text or keys.
  • What was checked is what is sent. Two credentials on one request, a second spelling of the model key, a compressed body or an unknown query parameter is refused rather than guessed at.
  • TLS. --tls-cert and --tls-key serve HTTPS with TLS 1.2 and 1.3. Gantry binds 127.0.0.1 unless told otherwise and warns when it listens elsewhere without TLS.

What it does not protect

  • Whoever can write the policy or keys file decides who may do what. Whoever can write the audit log can rewrite the whole chain consistently. Protect these files like provider keys.
  • Records removed from the end leave an unbroken chain. Keep the last hash where the Gantry host cannot write, and check it with --expect-last.
  • Up to one second of records can be lost on a power failure. Records are synced to disk once a second.
  • Plain HTTP carries keys in the clear unless Gantry serves TLS itself or sits behind a TLS proxy.
  • Built-in guardrails match plain text. Anything encoded, split across messages or translated is not found, and they do not find passwords, names or addresses. A webhook guardrail set to fail_open forwards unchecked while it is down.
  • A public host name that resolves to a private address is not caught by the private-address check on provider URLs.
  • A key removed from the file by hand keeps working for up to 2 seconds, until the reload. Revoking through the console or admin API stops it at once.
  • One node, or a store. Without a Postgres store, budgets, rate limits, the cache and console sessions live in one process. With one, keys, kill switches, budgets and rate limits are shared by every replica. The answer cache stays per replica.

The full security model lists every limit.

Where your data goes

  • Gantry is self-hosted. It runs on your machines, in your network or cloud account. There is no hosted Gantry service in the path.
  • Prompts and answers go from your callers, through Gantry, to the providers your policy names, and back. Gantry does not store them.
  • The audit log, the policy and the keys file live on your disk. Keys, kill switches and spend live in your Postgres when you use a store.
  • Nothing is sent to the Gantry project. The Enterprise license is checked against a public key in the binary, with no network call.

Subprocessors

None. Self-hosted Gantry sends no data to anyone on Gantry's behalf.

The model providers your policy names (OpenAI, Anthropic and others) receive your requests under your own provider account. They are your providers, not Gantry's subprocessors.
