Put a name on every AI call.

Gantry is a self-hosted AI gateway: coding tools, apps and MCP clients call models through it, each request tied to a person and a budget.

The problem

Three questions most companies cannot answer today.

Who uses which AI tool?
Developers installed Claude Code, Cursor and Copilot on their own. A team wired an agent to an MCP server. The list lives in nobody's system.
What does it cost, and who spent it?
The provider sends one invoice for one shared key. It has a total and no names, so a runaway agent shows up at the end of the month.
What was sent out?
Source code, customer records and secrets go into prompts every day. When security or an auditor asks for the record, there is none to hand over.

This is where most companies are, and it is fixable without stopping anyone's work. Send every call through one place you run, watch first, and add one control at a time. The five steps below are that order.

Five steps

One change at a time, in this order.

Each step is a few lines in one policy file or one page in the console. You can stop after any of them and keep what you have.

  1. 1

    See

    Point your tools at Gantry with a rule that allows everything. Nothing is blocked. After a week you know which tools are in use, by which teams, and what each one costs.

    You get: a record of every request, spend per team and model, and gantry audit coverage, which lists who sent requests from which tool and which key holders sent nothing.

    Coverage in the docs 
    # gantry.policy.yaml
rules:
  - name: everyone
    principals: { any: true }
    models: ["*"]

# on each laptop, for Claude Code
export ANTHROPIC_BASE_URL=https://gantry.internal
export ANTHROPIC_API_KEY=gantry_...
  2. 2

    Know

    Give each person and each service its own key, or let developers sign in with your identity provider. The provider's key stays inside the gateway and never reaches a laptop.

    You get: a person and a team on every record. Keys are shown once and stored as a hash, and one person's key can be revoked without touching anyone else.

    Keys and identity in the docs 
    # a key per person
gantry key new maya.cohen --team payments

# or single sign-on from the terminal
gantry login https://gantry.example.com

# or JWTs from your identity provider
jwt:
  - issuer: https://login.example.com
    audience: gantry
    person_claim: email
    team_claim: team
  3. 3

    Limit

    Put a budget and a rate limit on a team, a person, a key or a model. Keep a kill switch for the day an agent loops or a key leaks.

    You get: spend that cannot pass the number you wrote, a refusal that tells the person why and when the budget starts again, and a switch that stops matching traffic within a second.

    Budgets and rate limits in the docs 
    rules:
  - name: payments-team
    principals: { team: payments }
    models: [claude-sonnet-5-5, claude-haiku-5-5]
    budget: { usd: 2000, per: month }
    rate: { rpm: 600 }
    parallel: 20

# when something goes wrong
gantry kill --team payments \
  --reason "runaway agent, investigating"
  4. 4

    Protect

    Turn on guardrails for prompts, answers and MCP tool calls. Run each one in shadow mode first: it records what it would have stopped and blocks nothing until the date you set.

    You get: secrets and personal data blocked or masked before they leave, your own patterns and keyword lists, vendor guardrails such as Lakera Guard, Presidio and Bedrock guardrails, and MCP tools that wait for an admin's approval.

    Guardrails in the docs 
    guardrails:
  - name: no-secrets
    type: secrets
    action: block
    shadow_until: 2027-01-15
  - name: mask-pii
    type: pii
    action: mask
rules:
  - name: payments-team
    # ...
    guardrails: [no-secrets, mask-pii]
    tools: [github.*]
    approve_tools: [github.merge_pull_request]
  5. 5

    Prove

    Every record carries the hash of the one before it. Change, insert or reorder a line and the chain breaks at that record. Anyone can check it with one command.

    You get: an audit log you can verify yourself. With Gantry Enterprise, export to Splunk, Datadog, Elastic, Sentinel or object storage, a retention period, and a legal hold. Each exported batch carries its hash range, so the SIEM can check its copy.

    Audit log in the docs 
    $ gantry audit verify gantry-audit.jsonl
gantry-audit.jsonl: 122 records in an
unbroken chain from record 1 to record 122.
Last hash: ef2d127d...

# one record, shortened
{"n":119,"person":"maya.cohen",
 "team":"payments","verdict":"allow",
 "rule":"payments-team",
 "prev":"6b86b273...","hash":"d4735e3a..."}

Use cases

Who asks for it, and what they get.

Security

"What left the company, and can I prove it?"

Guardrails on requests, answers and tool calls. A hash-chained record of every decision, with no prompt text, keys or matched secrets in it. Alerts on guardrail blocks and on a key used from a new address.

Platform

"How do I give 300 people model access without handing out provider keys?"

One endpoint for OpenAI, Anthropic, Azure OpenAI, Bedrock, Vertex AI and Gemini. Aliases, retries and fallbacks. A policy file that gantry check validates in CI, where a misspelled field is an error with its line number.

Finance

"Who spent this, and will the budget last the month?"

Spend per organization, team, person, key and model. Budgets in your time zone with periods from a minute to a year, and a forecast for each one: it lasts, or the day it runs out.

Engineering leaders

"Can we roll out coding agents without losing track of them?"

Two environment variables per developer. Each session runs under the developer's own name and inside the team's budget. A refusal shows up in the terminal they already use, with the reason and a decision ID.

Rolling out a coding agent

Claude Code, Codex, Copilot, Cursor and others, each developer signed in through your identity provider, each with a daily budget.

Coding tool guides

MCP tools

Your MCP servers behind one endpoint. Each person sees the tools their rule allows. A tool whose description changed can be held until an admin approves it.

MCP gateway

Internal apps and agents

A key per service, a budget per end customer or tag, and the same audit record as a person's request. The OpenAI and Anthropic SDKs need a base URL and a key.

Connect a project

Regulated data

Requests kept in the regions a rule allows, personal data masked before it leaves, and optional redacted bodies sealed apart from the log for the people you name.

Example rollouts

Three ways this goes, written out.

These are scenarios we wrote to show the steps, with real policy lines. They are not customers. Gantry is pre-1.0 and has no customer stories to publish yet.

Example rollout

A 200-person fintech rolling out Claude Code

Sixty engineers already use Claude Code with one shared Anthropic key. Finance sees a single invoice. Security has been asked whether card data has gone into a prompt.
  1. See. The shared key moves into Gantry and laptops point at the gateway. Nothing is blocked for two weeks.
  2. Know. Engineers run gantry login and get a personal key through the identity provider. The shared key is revoked.
  3. Limit. A daily budget per person and a monthly budget per team.
  4. Protect. The secrets guardrail runs in shadow, then blocks. Personal data is masked.

What they have: spend by engineer and team, a refusal message developers can act on, and a log that answers the card data question with records.

rules:
  - name: engineering
    principals: { team: engineering }
    models: [claude-sonnet-5-5, claude-haiku-5-5]
    budget: { usd: 6000, per: month }
    guardrails: [no-secrets, mask-pii]
limits:
  - { person: "*", budget: { usd: 30, per: day } }
guardrails:
  - { name: no-secrets, type: secrets, action: block }
  - { name: mask-pii, type: pii, action: mask }

Example rollout

A platform team with 40 MCP servers

Agents across the company call internal MCP servers for GitHub, the data warehouse and deploys. Each server has its own token, and nobody can list which agent may call which tool.
  1. See. The servers go behind Gantry's one MCP endpoint. Every tool call is recorded with the person who made it.
  2. Know. People sign in with their key or by OAuth from the client. Each rule lists the tools its team may see.
  3. Limit. Merges and deploys wait for an admin's approval. Any tool has a kill switch.
  4. Protect. Each tool is pinned by a hash of its description and schema. A changed tool is held until an admin approves it.

What they have: one list of every tool, who called it, and a way to stop one tool without taking a server down.

mcp:
  - name: github
    url: https://api.githubcopilot.com/mcp/
    tool_changes: block
  - name: warehouse
    url: https://warehouse-mcp.internal/mcp
    tool_changes: block
rules:
  - name: platform
    principals: { team: platform }
    models: [claude-sonnet-5-5]
    tools: [github.*, warehouse.query]
    approve_tools: [github.merge_pull_request]
    approval_timeout_seconds: 120

Example rollout

A healthcare company that must keep PHI in region

Clinical teams want model help with notes. Compliance requires that patient data stays with an EU endpoint under a signed agreement, and that six years of records can be produced on request.
  1. See. Gantry runs in the company's own EU cloud account, from the Terraform module.
  2. Limit. The clinical rule reaches only deployments labelled eu. A request with no EU deployment is refused before anything is sent.
  3. Protect. Personal data is masked, and a regex guardrail masks patient record numbers.
  4. Prove. With Gantry Enterprise: export to the SIEM, a retention period, and a legal hold when a case opens.

What they have: a record per request naming the region rule that decided it. Gantry enforces the label you set on each deployment. It does not check where a provider runs.

aliases:
  - name: clinical
    deployments:
      - { provider: azure-eu, model: gpt-4o, region: eu }
      - { provider: openai, model: gpt-4o, region: us }
guardrails:
  - { name: mask-pii, type: pii, action: mask }
  - name: patient-ids
    type: regex
    action: mask
    patterns: { mrn: 'MRN-[0-9]{8}' }
rules:
  - name: clinical
    principals: { team: clinical }
    models: [clinical]
    regions: [eu]
    guardrails: [mask-pii, patient-ids]

What is different

A gateway built around the record.

Gantry covers the gateway features you expect from LiteLLM or Bifrost: one endpoint, many providers, routing, retries, caching, budgets. The difference is what it does before a request leaves.

  1. Governance on every scope

    Budgets, rate limits and kill switches per organization, team, person, key, end customer, tag and model. gantry explain shows which rule decided and every limit that applied.

  2. An audit log you can verify

    The record is written before the request is forwarded. If it cannot be written, the request is refused. The chain is checked with one command, in the open source edition.

  3. One image, in your cloud

    A single static binary in an image built from scratch, running as a non-root user, with Postgres as the only other part. No Redis. Prompts and answers stay out of the log.

  4. One policy file

    Providers, rules, budgets and guardrails in one YAML file you keep in git. An unknown field is an error with its line and the nearest known word.

  5. Open source core

    Apache 2.0, for any number of people. Enterprise features are in the same image and turn on with a license key that is checked offline.

Security and deployment

It runs where your data already is.

  • The audit log holds no prompt text, no answer text and no keys. A rule can keep redacted bodies, sealed apart from the log, for the people it names.
  • Gantry keys are shown once and stored as a SHA-256 hash. Provider credentials kept in the store are sealed with AES-256-GCM under a master key you hold.
  • The image holds one static binary and runs as user 65532. The license is checked offline, and a lapsed license never stops model traffic.
  • Gantry is pre-1.0 and has not yet had an independent security audit. What it protects, and where it stops
