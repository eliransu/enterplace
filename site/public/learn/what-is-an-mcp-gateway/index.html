What is an MCP gateway?

An MCP gateway is one endpoint that sits between your agents and your MCP servers. Every tool call passes through it, so it is the one place where you can say who may call what, and keep a record.

The problem it solves

MCP, the Model Context Protocol, is how an agent reaches tools: create an issue on GitHub, query the data warehouse, run a deploy. Each MCP server offers a list of tools, and an agent connected to it can call all of them.

That is fine for one developer and one server. In a company it turns into four problems:

  • A shared token per server. Every agent calls the GitHub server with the same credential. The server's log shows one caller, and it is not a person.
  • Every tool for everyone. An agent that needs to read issues can also delete a repository, because the server offers both.
  • Tools that change under you. A tool's description and schema are instructions to the model. A server that changes them can change what an agent does, and nobody is told.
  • No record. You can see that a deploy ran at night. You cannot see which agent asked, for whom, with what arguments.

What an MCP gateway does

Agents connect to the gateway instead of to each server. The gateway connects to the servers. Five jobs follow from that position.

  • One endpoint. The tools of every server are served at one address. A client is configured once.
  • A name on every call. The caller signs in to the gateway as a person or a service. The servers' own credentials stay in the gateway and never reach a laptop.
  • A tool list per rule. Each person or agent sees only the tools their rule allows. A tool that is not listed is not shown at all.
  • Approval for the dangerous ones. A call to a named tool can wait until an admin approves it, with the caller and the arguments in front of them.
  • A record. Every tool call is written down before it reaches a server: who, which tool, allowed or refused, and why.

An example

The payments team's agents may create and list GitHub issues and search the docs. Josh on the platform team may merge pull requests, and each merge waits for an admin.

Emily, an intern with no tools in her rule, asks her agent to query the warehouse. The agent never sees a warehouse tool, so it cannot call one. Josh's agent calls github.merge_pull_request. The call is held, an admin sees who asked and with what arguments, approves it, and the record says who approved.

What an MCP gateway is not

  • It is not an MCP server. It has no tools of its own. It serves the tools of the servers you list.
  • It does not see everything. It sees the calls sent through it. An agent that still connects to a server directly is invisible to it.
  • It does not make a tool safe. It decides who may call a tool and records that they did. What the tool does with the arguments is still the server's business.
  • It is not the same as an AI gateway. An AI gateway sits in front of model providers and handles prompts, tokens and cost. An MCP gateway sits in front of tools. Some products do both, so one rule covers a person's models and tools.

Do you need one?

Probably not if a few developers each run local MCP servers for their own work. Probably yes if any of these is true:

  • Agents call tools that change systems: merge code, run a deploy, write to the warehouse.
  • An MCP server's token is shared by more people than you can name.
  • Security has asked which agents can reach which systems, and the answer is a guess.
  • You connect to MCP servers that someone else operates and can change.

How Enterplace does it

Enterplace is an AI gateway and an MCP gateway in one program, open source and self-hosted. The servers go under mcp: in the same policy file as the model rules, and their tools are served at /mcp as server.tool. It speaks Streamable HTTP, the older SSE transport and stdio to the servers.

It also pins each tool the first time it sees it, with a hash of the description and schema. When a server changes a tool, the change is recorded, or held until an admin approves it if you set tool_changes: block.

The steps, with the lines for each, are on the MCP tools page. The reference is MCP gateway in the docs.
