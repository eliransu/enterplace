Use casesLocal and self-hosted models

Your own models, behind the same names, rules and record.

You serve models with Ollama or vLLM, on your own hardware or in a network with no way out. The data stays in, and you still need to know who used which model, and to keep some teams on local models only.

What goes wrong without control

An open port on the network
Ollama ignores API keys. Anyone who can reach the server can use it, and its logs do not say who did.
Two worlds, two sets of rules
Hosted models go through one path and local ones through another. A team told to stay local can switch to a hosted model by changing a URL.
No usage numbers
You bought the GPUs. You cannot say which teams fill them, or whether the next purchase is needed.
Tools that phone home
In an air-gapped network, software that checks a license or sends telemetry over the internet stops working or gets blocked by review.

The steps

Local model servers speak OpenAI's API, so each one is a provider like any other, with one extra line.

  1. Add the local server as a provider

    A provider on a private address needs allow_private: true. Without it, gantry check refuses the file and says why. Ollama takes no key, so Gantry sends none, and never the caller's Gantry key.

    Local models in the docs {{> arrow}}

  2. Keep a team on local models

    A rule lists the models its people may use. Team legal gets the local model and nothing else. A request for a hosted model is refused with model_not_allowed before anything is sent.

  3. Give local models a price

    A budget needs a price to count. Set zero so a rule with a budget can still reach the local model, or set your own cost per token to charge teams for GPU time.

    Pricing in the docs {{> arrow}}

  4. Run coding agents on the local model

    Claude Code speaks Anthropic's messages API. With accept_messages: true on the provider, Gantry translates its requests to chat completions, so Claude Code can run on a model you serve.

    Translation in the docs {{> arrow}}

In an air-gapped network

Gantry was built to run with no connection out. These are the parts that matter there.

One image to bring in
A single static binary in an image built from scratch. The image also carries the Helm chart and the Terraform modules for its version, so you copy them out of the image you already approved.
The license is checked offline
The Enterprise license is verified against a public key built into the binary. The check never uses the network. A lapsed license turns Enterprise features off and never stops model traffic.
Nothing calls home
Self-hosted Gantry sends nothing to the Gantry project. Prometheus metrics are off by default, and traces and audit records go only to the systems you name.
Guardrails that run inside
The built-in secrets and personal data detectors run inside Gantry and send no text anywhere. Vendor guardrails call the vendor's API, so leave those out, or use the ones you host yourself.
A release you can verify
Images are signed and ship with an SBOM and provenance. Verify a release

Limits to know before you start

  • The local servers were configured from their docs and tested against local mocks. Each base URL was checked against the vendor's documentation, and the path Gantry calls was confirmed against a mock. Project status
  • Inside a container, 127.0.0.1 is the container. Use the host's address for a model server on the same machine.
  • Gantry does not serve models. It sits in front of the servers that do.
