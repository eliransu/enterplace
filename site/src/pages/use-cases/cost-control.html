What goes wrong without control

A total with no names
Finance asks which team the spend belongs to. Engineering answers with an estimate, because the shared key hides who sent what.
A surprise at the end of the month
An agent in a retry loop, or one person on the most expensive model for a week, is found on the invoice.
Caps that live in a spreadsheet
Each team has an agreed amount. Nothing refuses request number one over it.
No way to test a limit
Nobody knows what a 500 dollar cap would have blocked last month, so nobody dares to set one.

The steps

Look first. Every limit can run on trial, recording what it would refuse, before it refuses anything.

  1. See spend per person, team and model

    Once tools point at Gantry and each person has a key, the console's Analytics page ranks requests, tokens and cost by person, team, key, model or coding agent. Gantry prices each answer from a built-in table for most models, and gantry prices prints it.

    Steps 1 and 2: See and Know {{> arrow}}

  2. Add a monthly budget per team, on trial

    Pick the amount from what step one showed you. While the policy is in observe mode, a request over the budget is forwarded and recorded as would_refuse. Its cost still counts, so the numbers are real on the day you enforce.

    Step 3 in the docs {{> arrow}}

  3. Enforce it

    Delete the mode: observe line. From the next request, a team that reaches its budget is refused with budget_exceeded, and the message says when the budget starts again. Gantry reserves the most a request could cost before it is sent, so a budget cannot be overrun.

  4. Add the narrower limits

    A daily budget per person, a cap on one costly model, a rate limit, a budget on a single key. A new limit can run on trial by itself with shadow_until, while the rest of the policy is enforced.

    Budgets and rate limits {{> arrow}}

  5. Spend less on the same work

    A rule with cache answers a repeated request from a stored answer, for the same person or team. A hit costs nothing and is still recorded. prompt_cache: auto asks Anthropic to cache the stable start of a request, so the next call pays the cached input price. The console shows what caching saved per team.

    Caching in the docs {{> arrow}}

What you see afterwards

  • Spend this month against every budget in the policy.
  • A forecast per budget: it lasts the period at the current pace, or the date it runs out.
  • Who spent most, with a link to their requests.
  • Spend by model and provider, and the requests stopped before sending.

Alerts to Slack, Teams, PagerDuty or email before a budget runs out are part of Gantry Enterprise. Enterprise

Limits to know before you start

  • Cost is computed from token counts and a price table. It will be close to your invoice and not identical to it, for example where you have a negotiated rate. You can set your own prices in the policy.
  • A budget needs a price. A request for a model with no known price, under a rule with a budget, is refused with no_price until you add one.
  • Claude Team and Enterprise seats are not billed per dollar. In the watch setup, costs are Claude Code's own estimates at list price. Read them as relative usage.
  • Gantry counts what goes through it. A tool that still calls a provider directly spends outside every budget.
