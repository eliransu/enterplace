What goes wrong without control

One provider key per environment
Every service reads the same secret. The invoice has one line, and rotating the key means redeploying everything that uses it.
An agent that loops
An agent retries one task all night. The provider keeps answering, and the first signal is the bill.
No answer to "which service sent that?"
A customer asks whether their data went to a model. The provider's logs do not know your services, and yours do not record the call.
Credentials for three clouds in every repo
Azure, Google and AWS clients each need their own credentials, copied into each service that calls them.

The steps

The services keep their SDKs, prompts, retries and streaming. They change a base URL and a key.

  1. Issue a key per workload

    Give each service or job its own name, team and budget. The key is shown once and stored as a hash. Put it in the secret store the service already reads.

    Keys in the docs {{> arrow}}

  2. Point the SDKs at Enterplace

    The OpenAI and Anthropic SDKs read their base URL from the environment, so most services need no code change. The docs have a prompt you can give your coding agent to find and move every call site, then you read the diff.

    Connect a project {{> arrow}}

  3. Write the rule and the limits

    A rule names the team and the models it may use. Limits cap dollars, requests per minute and requests in flight. A product that serves your own customers can carry a budget per end customer.

    Budgets and rate limits {{> arrow}}

  4. Keep the stop button ready

    A kill switch needs no policy change. It stops a person, a team, a key or a model, and the callers it stops see the reason and who set it.

    Kill switches {{> arrow}}

What you see afterwards

  • Spend per service, team, end customer and model, with a forecast for each budget.
  • Every response carries X-Enterplace-Decision. Log it beside your own request ID and you can find the record for any call.
  • OpenTelemetry traces over OTLP, joined to the caller's trace, and Prometheus metrics on an address of their own.
  • On AWS and Google Cloud, Bedrock and Vertex AI need no provider key. The gateway signs in as its own role or service account.
Observability in the docs {{> arrow}}

Limits to know before you start

  • Enterplace is in the request path. Run more than one replica on a Postgres store, and put it where your services can reach it. The deploy guides cover sizing.
  • The decision record says what Enterplace decided. How the provider answered arrives in a second record, with status, tokens and cost, when the answer ends.
  • The answer cache is per replica. Budgets, rate limits and kill switches are shared through the store. Cached answers are not.
  • One caller's requests in flight may hold at most 64 MiB of request bodies.

Questions people ask

Our services already hold tokens from our identity provider. Do they need an Enterplace key too?

No. Enterplace accepts JWTs from issuers you trust in place of a key, and reads the person and team from claims you name. Access control

Does Enterplace change the request?

The body is forwarded byte for byte, except where your policy changes it: a guardrail that masks, or a translation you opted into. An unknown query parameter is refused by name, never dropped silently.

What if Enterplace cannot write its audit log?

Requests are refused with audit_unavailable until it can. That is the design: no request leaves without a record.

Do the agents' tool calls go through it too?

If the tools are MCP servers, yes. Put the servers behind Enterplace's MCP endpoint and each call is checked and recorded like a model call. MCP tools
