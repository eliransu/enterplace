The wrangler template `cloudflare`, which ships inside the `gantry` image, runs gateways in Cloudflare Containers behind a Worker, keeps each gateway's audit chain in R2, and keeps keys, kill switches and budgets in Postgres.

## What it creates

| Resource | Why |
|---|---|
| A Worker on your hostname | Sends each request to one of `GATEWAYS` gateway instances, named `gateway-0`, `gateway-1` and on. Serves `GET /_gantry/audit/<instance>`, the whole audit chain of one instance |
| Durable Object class `GantryGateway` and its container application | One gateway per instance, from an image built of the Gantry image and your policy. Instances start on the first request and stop after 30 minutes without one |
| R2 bucket, bound as `AUDIT` | Each instance's sealed audit segments, under `audit/<instance id>/` |
| Workers secrets | `DATABASE_URL`, `GANTRY_LICENSE`, provider keys and the rest. The Worker passes them to the container as environment variables when it starts |

**The audit chain in R2.** A container's disk is new at every start, and the audit log is one hash-chained file. So the gateway seals its log every `GANTRY_AUDIT_SEAL_SECONDS` (60 by default), or as soon as it reaches `GANTRY_AUDIT_SEAL_BYTES` (1 MiB), and writes each sealed segment to R2. Only once R2 has a segment does the gateway remove it from disk, with an `audit_retired` record in the chain that names it and its SHA-256. A graceful stop (a deploy, or an idle instance going to sleep) seals and writes the rest first. On a start with an empty disk, the gateway fetches its newest segments back from R2 and continues the chain from the last hash. The segments in R2, in name order, followed by the records not yet sealed, are one chain from record 1 that `gantry audit verify` proves.

**No R2 access key.** The gateway sends its S3 requests to `http://audit.gantry.internal`, a name that exists only inside the container: the Worker answers it from the bucket binding. It keeps each instance in its own folder, so one gateway cannot write another's chain, has no delete, and refuses to overwrite a segment with different bytes.

**Postgres over TLS, not Hyperdrive.** Hyperdrive is a binding for Worker code. A container reaches its Worker over HTTP only, so the gateway connects to Postgres itself, with TLS checked against the Mozilla roots built into it. Use a Postgres that is reachable from the internet and whose certificate chains to a public authority, such as Neon.

**Why wrangler and not Terraform.** `wrangler deploy` builds the image, pushes it to your account's registry and deploys the Worker, the Durable Object class and the container application in one command, and rolls the containers when the image changes. The Cloudflare Terraform provider does not build or push images, so it would still need wrangler beside it.

## Prerequisites

- A Cloudflare account on the Workers Paid plan, which Containers need, with R2 enabled and a zone for the gateway's hostname.
- Node.js 20 or later, and Docker running: wrangler builds the image locally for `linux/amd64`.
- A Postgres database reachable over TLS from the internet, and its connection string with `sslmode=require`.
- The registry token Gantry gave you with your license, which reads `ghcr.io/ggantry/gantry`, and the user name that goes with it.
- Your license key, a provider key, and the image version you were given.

## Deploy

<Steps>

1. Copy the template out of the image you will run, and install wrangler beside it.

   ```bash
   docker login ghcr.io -u <your user name>
   docker create --name gantry-files ghcr.io/ggantry/gantry:<version>
   docker cp gantry-files:/deploy/cloudflare ./gantry-cloudflare && docker rm gantry-files
   cd gantry-cloudflare
   npm ci
   npx wrangler login
   ```

2. Edit the four lines marked `EDIT` in `wrangler.jsonc`: the Worker's name, the image version in `image_vars`, the bucket name, and your hostname. Edit `gantry.policy.yaml` for your providers and rules, and keep its last two lines:

   ```yaml title="gantry.policy.yaml"
   audit: { path: /var/lib/gantry/gantry-audit.jsonl }
   store: { postgres_url_env: DATABASE_URL }
   ```

3. Create the bucket, deploy, and set the secrets. The first deploy builds and pushes the image, which takes a few minutes.

   ```bash
   npx wrangler r2 bucket create gantry-audit
   npx wrangler deploy
   npx wrangler secret put DATABASE_URL
   npx wrangler secret put GANTRY_LICENSE
   npx wrangler secret put OPENAI_PROVIDER_KEY
   openssl rand -hex 32 | npx wrangler secret put GANTRY_MASTER_KEY
   openssl rand -hex 32 | npx wrangler secret put GANTRY_EXPORT_KEY
   openssl rand -hex 32 | tee audit-read-token.txt | npx wrangler secret put GANTRY_AUDIT_READ_TOKEN
   ```

   Every secret or variable named `GANTRY_*`, `DATABASE_URL`, `AWS_*` or `*_PROVIDER_KEY` reaches the gateway. Keep a copy of the master key outside Cloudflare: a lost master key cannot be recovered. A running gateway reads its environment when it starts, so a secret set later reaches it at its next start: run `npx wrangler deploy` again to roll the instances.

</Steps>

### Settings

| Setting | Where | Default | Description |
|---|---|---|---|
| `GATEWAYS` | `vars` | `2` | Gateway instances requests are spread over |
| `max_instances` | `containers` | `4` | At least `GATEWAYS`, plus one for each instance still stopping during a rollout |
| `instance_type` | `containers` | `basic` | The container's size. See the instance types in the Containers documentation |
| `GANTRY_AUDIT_SEAL_SECONDS` | `vars` | `60` | How often the audit log is sealed and written to R2, when it holds new records |
| `GANTRY_AUDIT_SEAL_BYTES` | `vars` | `1048576` | Seal sooner when the open file reaches this size |
| `sleepAfter` | `src/index.ts` | `30m` | How long an idle instance runs before it stops. Each start fetches its newest segments from R2 |

## Verify

<Steps>

1. Check the gateway answers. The first request starts an instance, which takes a few seconds.

   ```bash
   export GATEWAY=https://gantry.example.com
   curl -s $GATEWAY/healthz
   ```

2. Find the one-time link to make the first admin. The gateway prints it once at start.

   ```bash
   npx wrangler tail --format pretty | grep "First run"
   ```

   Open the link with `http://127.0.0.1:8080` replaced by `$GATEWAY`, give your name and team, keep the admin key it shows once, and sign in at `$GATEWAY/console`. With more than one instance, the setup link and single sign-on reach the instance that made them only by chance: set `GATEWAYS` to 1 for this step, then raise it.

3. Issue a key with the admin API and make a governed call.

   ```bash
   export GANTRY_ADMIN_KEY=gantry_...
   KEY=$(curl -s -X POST $GATEWAY/admin/keys \
     -H "Authorization: Bearer $GANTRY_ADMIN_KEY" -H 'Content-Type: application/json' \
     -d '{"name":"maya.cohen","team":"payments"}' | sed -n 's/.*"key":"\([^"]*\)".*/\1/p')
   curl -s $GATEWAY/v1/chat/completions \
     -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
     -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"Say hi"}]}'
   ```

4. Verify the audit chain of an instance: its segments from R2, then the records it has not sealed yet, as one file.

   ```bash
   curl -s -H "Authorization: Bearer $(cat audit-read-token.txt)" $GATEWAY/_gantry/audit/gateway-0 > chain.jsonl
   docker run --rm -v "$PWD":/w:ro ghcr.io/ggantry/gantry:<version> audit verify /w/chain.jsonl
   ```

   ```text
   /w/chain.jsonl: 13 records in an unbroken chain from record 1 to record 13.
   6 requests, 2 configuration records, 2 admin records, 3 usage records.
   Last hash: 9e2fe69fc6e327b2622ef8fb16456c3e3e9659ffef392331d969cb2d470dd31d
   ```

   The admin records are the `audit_retired` records, one each time segments left a container's disk for R2.

5. Restart and verify again. `npx wrangler deploy` rolls every instance: each one seals and writes its last records, stops, and the new one continues the chain from R2. Make another governed call, then repeat step 4: the record count grows and the chain still holds from record 1.

</Steps>

## Known limits

- **A killed container loses its unsealed records.** A graceful stop loses nothing. A container that is killed (out of memory, a host failure) loses the records written since the last seal, at most `GANTRY_AUDIT_SEAL_SECONDS` of them; the chain then continues from the last segment in R2 and still verifies. Lower the interval to narrow the window; each seal adds one `audit_retired` record and one R2 write.
- **A chain per organization ships under its own folder.** With `audit: { per_org: true }`, each organization's chain is sealed and written to R2 as the instance's is, under `<instance folder>/orgs/<org>`, and fetched back on a start with an empty disk for each organization listed under `orgs:`. See [a chain per organization](/governance/audit-log/#a-chain-per-organization).
- **Hyperdrive is not used.** See above: the gateway connects to Postgres directly over TLS. A database whose certificate comes from a private authority, such as Cloud SQL, is refused.
- **Requests are spread at random.** Keys, kill switches and budgets are shared through the store, so any instance answers any request. The answer cache is per instance, and a single sign-on callback must reach the instance that started the sign-in: with single sign-on, run one instance.
- **The store is required for more than one instance.** Without `store:`, each instance has its own keys file baked into the image and forgets spend at every start, because it is replayed from the audit log on disk.
- **Every start reads the bucket listing.** A start lists the instance's folder in R2 to find the newest segment, one request per 1,000 segments. At one segment a minute that is about 45 requests after a month of traffic. Set a lifecycle rule on the bucket only after you have copied older segments where you keep evidence, since a rule deletes them for good.
- **Each start records a refused `GET /`.** The Containers runtime checks the port with a request to `/` when an instance starts, and the gateway records it as a refusal with `no_key`. Filter these out by path in reports.
- **No metrics port.** The Worker reaches the gateway's one port, so `/metrics` is not exposed. Use Workers observability and OpenTelemetry traces.
- **One region per instance.** Cloudflare places each instance near its first request. Put Postgres close to where your callers are.

## Production checklist

- **TLS.** The custom domain has a Cloudflare certificate. The Worker reaches the container inside Cloudflare.
- **Secrets.** Every secret is a Workers secret, set with `wrangler secret put` and never in `wrangler.jsonc`. Never change the master key in place: the credentials sealed with it would no longer open.
- **Backups.** Turn on your Postgres provider's backups with point-in-time recovery. The audit chain is in R2: copy the bucket, or each instance's folder, to storage where the account that runs Gantry cannot delete, and keep each instance's last hash from step 4 outside Cloudflare.
- **Monitoring.** A health check on `$GATEWAY/healthz` (Cloudflare Health Checks, or your own), Workers observability for errors, and an alert on the log line `warning: audit segments`, which means a segment could not be written to R2 and stays on the container's disk until it can.
- **Upgrades.** Take a database backup first, since a newer Gantry may update the schema and an older one refuses a database a newer one has written. Change `GANTRY_IMAGE` in `image_vars` and run `npx wrangler deploy`. Instances roll one by one; each seals and writes its chain before it stops.
- **Rollback.** Put the previous version back in `image_vars` and deploy again. Each instance continues its chain from R2. If the older version refuses the database because the new one changed the schema, restore the backup first. `npx wrangler rollback` rolls back the Worker code only, not the containers.

### What to watch

| Signal | Meaning | Do |
|---|---|---|
| `gateway_not_ready` answers | The container did not start: a policy it cannot use, a missing secret, or a chain in R2 that does not verify | `npx wrangler tail`: the error names the fix |
| `warning: audit segments` in the log | R2 did not take a segment. It stays on disk, and is written when R2 answers again | Check the bucket binding and R2's status |
| Refusals with `store_unavailable` | Postgres cannot be reached. Budgeted requests are refused; others are served | Check the database and `DATABASE_URL` |
| License warning in the log | The license is in its 30-day grace period | Set the renewed license with `wrangler secret put GANTRY_LICENSE` and deploy |
