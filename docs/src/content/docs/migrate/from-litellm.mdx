`enterplace import litellm` reads a LiteLLM proxy `config.yaml` and writes an Enterplace policy that passes `enterplace check`. Everything it cannot carry across is listed with what to do instead. Given an export of LiteLLM virtual keys, it also writes team rules and one `enterplace key new` command per key.

This page is for replacing a LiteLLM proxy. To keep the LiteLLM Python SDK in your code and point it at Enterplace, see [LiteLLM SDK](/integrations/litellm-sdk/).

## Concepts

| LiteLLM proxy | Enterplace | Notes |
|---|---|---|
| `config.yaml`, plus models and settings kept in the database | The [policy file](/governance/policy/), one YAML file checked by `enterplace check`. With `store: { policy_from: store }` it is kept in Postgres as versions | An unknown key in the policy is an error with its line, not ignored |
| `model_list` entry (a deployment) | A model under a provider's `models:` | A provider is declared once and lists its models |
| `model_name` shared by several deployments | An [alias](/routing/aliases/) with `deployments` | Callers send the alias; rules decide on it |
| `router_settings.routing_strategy` | The alias's [`balance`](/routing/strategies/): `round_robin`, `least_busy`, `lowest_latency`, `lowest_cost`, `adaptive` | Per alias, not global |
| `fallbacks`, `context_window_fallbacks`, `content_policy_fallbacks` | A provider's `fallback`, an alias's deployments, and the alias's `context_window_fallback` and `content_policy_fallback` | See [Retries and fallbacks](/routing/retries-and-fallbacks/) |
| Virtual key (`sk-...`) | A [Enterplace key](/governance/keys/) (`enterplace_...`), stored as a hash, shown once | Each key has a name and a team |
| Master key | An admin key (`enterplace key new <name> --team <team> --admin`), or console sign-in through [single sign-on](/governance/single-sign-on/) | `ENTERPLACE_MASTER_KEY` is something else: it seals stored provider credentials |
| Team, organization | The key's team and [organization](/governance/policy/#organizations); [teams](/governance/teams/) with owners and members in the policy | Rules match on `principals: { team: ... }` |
| Internal user | The person a key is named for. `enterplace login` issues a personal key named by email | |
| End user (customer) | An [end customer](/governance/budgets-and-rate-limits/#end-customers-and-tags): `customer` on a key, or the `x-enterplace-customer` header where the rule allows it | |
| Tags | [Tags](/governance/budgets-and-rate-limits/#end-customers-and-tags) on a key or in `x-enterplace-tags`, allowed per rule | |
| Budgets and rate limits per key, team, user | `budget`, `rate` (`rpm`, `tpm`) and `parallel` on a rule, on a key, and per scope in the [`limits:` list](/governance/budgets-and-rate-limits/#scopes-and-the-limits-list) | A budget reserves a request's worst case before it is sent |
| Model access per key or team | A rule's `models:` list, narrowed per key with `--models` | The first matching rule decides |
| Guardrails | [Guardrails](/governance/guardrails/) named in the policy and listed on a rule | Built-in secrets and personal data detectors, vendors, webhooks |
| Callbacks (`success_callback`, `callbacks`) | The [audit log](/governance/audit-log/), Prometheus [metrics](/operations/observability/), and [observability integrations](/operations/observability-integrations/) such as Langfuse and Datadog | The audit log is written before a request is forwarded |
| Spend logs | `usage` records in the audit log, and the [request log](/operations/request-log/) with its analytics | No prompt or answer text unless a rule captures it |
| `cache`, `cache_params` | [`cache:` on a rule](/routing/caching/), exact or semantic | Kept per replica, never in the database |
| Postgres and Redis | Files for one process, or a Postgres [store](/operations/store/) shared by replicas. No Redis | |
| `os.environ/NAME`, secret managers | `key_env: NAME`, with a [secret manager reference](/operations/secret-managers/) as the variable's value | |
| Credentials added in the UI | [Provider credentials](/governance/provider-credentials/) sealed under `ENTERPLACE_MASTER_KEY` | |
| Pass-through endpoints | [Passthrough](/governance/policy/#passthrough) paths listed per rule | |
| MCP gateway | The [MCP gateway](/governance/mcp-gateway/) | |
| Admin UI | The [console](/operations/console/) | |

## Import a config

<Steps>

1. Run the import. `--out` names the policy to write (default `enterplace.policy.yaml`); `--keys-from` is optional.

   ```bash
   enterplace import litellm config.yaml --out enterplace.policy.yaml
   enterplace import litellm config.yaml --keys-from keys.json --out enterplace.policy.yaml
   ```

2. Read the report. Each line is an item that was not mapped, or that needs a hand, with the fix.

3. Read the policy. The last rule, `everyone`, allows every imported model to anyone with an Enterplace key, as a LiteLLM proxy allows any valid key every model by default. Narrow it before you serve.

4. Reissue the keys with the commands from the report, then start the gateway with `enterplace serve enterplace.policy.yaml`.

</Steps>

The import never replaces an existing file. If `--out` exists, it stops with an error and writes nothing. After writing, it runs `enterplace check` on the result.

## Import a running proxy

With the proxy's address and its master key in an environment variable, the import reads the proxy's management API instead of files: its model list, every virtual key and every team.

```bash
export LITELLM_MASTER_KEY=sk-...
enterplace import litellm --url https://litellm.internal.example.com --master-key-env LITELLM_MASTER_KEY \
  --out enterplace.policy.yaml --keys-out enterplace.keys.yaml
```

```text
Read 2 models from the proxy, 2 keys and 2 teams.
Wrote enterplace.policy.yaml.
Issued 2 keys in enterplace.keys.yaml for the LiteLLM keys. Each is shown once: hand it to its owner.
  maya (token 88dc28d0f030...) -> maya (team payments): enterplace_3f9a...
  dana (token a1b2c3d4e5f6...) -> dana (team search): enterplace_8a41...
Everything in the proxy was mapped.
```

- Models come from `GET /model/info`; give the `config.yaml` as well to carry its router and general settings across.
- Keys come from `GET /key/list` page by page, or `GET /key/info` for a key listed by its token. LiteLLM keeps only key hashes, so every key is issued again: the mapping prints each LiteLLM key's alias and token prefix beside the Enterplace key that replaces it, shown once. The new keys file holds only their hashes.
- A team's budget, `rpm_limit`, `tpm_limit` and `max_parallel_requests` become one `limits:` entry, for example `{ team: payments, budget: { usd: 500, per: month }, rate: { rpm: 600, tpm: 90000 }, parallel: 8 }`. Budget durations are read as described under [Keys](#keys).
- A route the proxy does not serve is reported and skipped; a wrong master key stops the import with the proxy's answer.
- The master key is read from the variable, sent only to `--url`, and never printed. Plain http is refused except to `127.0.0.1` or `localhost`.

## Example

This LiteLLM config serves one OpenAI model and one Anthropic model under its own name:

```yaml title="config.yaml"
model_list:
  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o
      api_key: os.environ/OPENAI_API_KEY
  - model_name: claude-sonnet
    litellm_params:
      model: anthropic/claude-sonnet-4-5
      api_key: os.environ/ANTHROPIC_API_KEY
general_settings:
  master_key: sk-1234
  database_url: postgres://litellm@db/litellm
```

And this key export holds one key:

```json title="keys.json"
[{"key_alias": "maya", "team_alias": "payments", "models": ["gpt-4o"], "max_budget": 20, "budget_duration": "30d", "tpm_limit": 50000, "rpm_limit": 10}]
```

```bash
enterplace import litellm config.yaml --keys-from keys.json --out enterplace.policy.yaml
```

```text
Wrote enterplace.policy.yaml.
Not mapped, or needs a hand (3 items):
  - key maya: reissue with `enterplace key new maya --team payments --budget 20/month --models gpt-4o --tpm 50000 --rpm 10` (LiteLLM keeps only key hashes, so keys cannot move).
  - general_settings.master_key: Enterplace has no master key. Make an admin key: enterplace key new <name> --team <team> --admin.
  - general_settings.database_url: not needed. Enterplace keeps keys in enterplace.keys.yaml and records in its audit log.
See https://docs.enterplace.dev/migrate/from-litellm/. Checking it now:
enterplace.policy.yaml is valid: 2 rules, 0 keys, 2 providers: openai (openai) at https://api.openai.com, anthropic (anthropic) at https://api.anthropic.com.
```

The policy it writes:

```yaml title="enterplace.policy.yaml"
# Imported from a LiteLLM config by `enterplace import litellm`. Check it with `enterplace check`.
version: 1
providers:
- name: openai
  kind: openai
  url: https://api.openai.com
  key_env: OPENAI_API_KEY
  models:
  - gpt-4o
- name: anthropic
  kind: anthropic
  url: https://api.anthropic.com
  key_env: ANTHROPIC_API_KEY
  models:
  - claude-sonnet-4-5
aliases:
- name: claude-sonnet
  deployments:
  - provider: anthropic
    model: claude-sonnet-4-5
rules:
- name: team-payments
  principals:
    team: payments
  models:
  - gpt-4o
- name: everyone
  principals:
    any: true
  models:
  - gpt-4o
  - claude-sonnet
```

`claude-sonnet` became an alias, because callers send a name that differs from the deployment's model. `gpt-4o` is listed directly under its provider.

<Aside type="tip">
The import keeps LiteLLM's variable names in `key_env`. If Claude Code will run through Enterplace, rename `ANTHROPIC_API_KEY` to a variable of its own, such as `ANTHROPIC_PROVIDER_KEY`: Claude Code reads `ANTHROPIC_API_KEY` for its own key, which is an Enterplace key.
</Aside>

## What maps

| LiteLLM | Enterplace |
|---|---|
| `model_list[].model_name` | The model name callers send. One deployment whose model has the same name is listed under its provider's `models`. Several deployments, or one under another name, become an [alias](/routing/aliases/) with that name. |
| `litellm_params.model` with `openai/`, or a bare `gpt-*` | `kind: openai`, `url: https://api.openai.com` |
| `anthropic/`, or a bare `claude-*` | `kind: anthropic` |
| `azure/<deployment>` with `api_base`, `api_version` | `kind: azure` with `deployments` and `api_version` |
| `bedrock/<model id>` with `aws_region_name` | For a Claude model (`anthropic.` in the ID), `kind: bedrock`; for any other model, and for `bedrock/converse/<model id>`, `kind: bedrock_converse`. Each with `region` and `model_ids`. Enterplace signs with its own `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`. |
| `cohere/`, `cohere_chat/` | `kind: cohere` at `https://api.cohere.com/v2`, key in `COHERE_API_KEY` unless the config names another variable |
| `gemini/` | `kind: gemini` |
| `vertex_ai/gemini-*` with `vertex_project`, `vertex_location` | `kind: vertex` with the `/publishers/google` URL |
| `vertex_ai/claude-*` with `vertex_project`, `vertex_location` | `kind: vertex_anthropic` with the `/publishers/anthropic` URL, and an alias from the `model_name` to the Vertex model name (`claude-sonnet-4-5@20250929`) |
| `groq/`, `mistral/`, `together_ai/`, `fireworks_ai/`, `deepseek/`, `openrouter/`, `ollama/`, `ollama_chat/`, `lm_studio/`, `hosted_vllm/` | `kind: openai` with the vendor's base URL from [Providers](/providers/overview/), or `api_base`. A local server gets `allow_private: true` and no key. |
| `api_key: os.environ/NAME` | `key_env: NAME`. A key written in the config is not copied: the report names the variable to set. |
| Credentials added in the LiteLLM UI, encrypted with `LITELLM_SALT_KEY` | Add each again in the console's Provider credentials page or with `POST /admin/credentials`, with `ENTERPLACE_MASTER_KEY` set, and name it with `credential:` on the provider. See [Provider credentials](/governance/provider-credentials/). Not imported: Enterplace never reads another product's encrypted values. |
| A client sending its own `api_key` in the request body | The rule's `caller_provider_key: allowed`, with the key in the `x-enterplace-provider-key` header. The body is forwarded as sent, so an `api_key` field there is not a credential to Enterplace. See [A caller's own provider key](/governance/provider-credentials/#a-callers-own-provider-key). |
| `litellm_params.weight` | The deployment's `weight` |
| `model_info.input_cost_per_token`, `output_cost_per_token` | `prices:` in dollars per million tokens, under the name Enterplace sends |
| A deployment named by its owner (`azure/gpt-4o-eastus`) | Priced as the model it runs: `model_info.base_model` when set, else the LiteLLM model string, else the `model_name`, written under `prices:` for the deployment's name. A team budget or a key `tpm` then works on the imported alias. |
| `router_settings.routing_strategy` `simple-shuffle`, `least-busy`, `latency-based-routing`, `cost-based-routing` | Alias `balance: round_robin`, `least_busy`, `lowest_latency`, `lowest_cost` |
| `rpm`, `tpm`, `max_parallel_requests` of a deployment | The alias deployment's `rpm`, `tpm` and `max_parallel`: a deployment at its limit is passed over. A model with one deployment is listed on its provider and the limit is reported: serve it from an alias to keep it. |
| `litellm_params.timeout` | The alias deployment's `timeouts: { total_ms }`, or its provider's for a model listed directly |
| `router_settings.timeout`, `litellm_settings.request_timeout` | `timeouts: { total_ms }` on each provider that has none of its own |
| `router_settings.cooldown_time` | Alias `cooldown_seconds` (up to 3600) |
| `num_retries` (router or litellm settings) | Each provider's `retries` (up to 5) |
| `fallbacks` | The alias's `fallbacks`, in order. A fallback may speak the other API: the request is translated as it is sent. |
| `context_window_fallbacks`, `content_policy_fallbacks` | The alias's `context_window_fallback`, `content_policy_fallback`. Enterplace follows one target, so the first is used. |

Check the price of an imported alias with `enterplace prices <alias> --policy enterplace.policy.yaml`. A deployment that none of the price sources above covers is reported, with the `prices:` line to add.

## What is reported instead

These are not written into the policy. Each appears in the report with the fix.

| LiteLLM | What to do in Enterplace |
|---|---|
| Other `routing_strategy` values (`usage-based-routing`, custom) | The alias is written with `round_robin`. Pick a `balance` by hand; `adaptive` weighs latency, errors and cost together. See [Strategies](/routing/strategies/). |
| `default_fallbacks` | Enterplace has no fallback for every model: give each alias `fallbacks:`. |
| `stream_timeout` | No exact equivalent. Bound a stream with `timeouts: { first_byte_ms, idle_ms }` on the provider, alias or deployment. |
| `general_settings.master_key` | Make an admin key with `enterplace key new <name> --team <team> --admin`. |
| `general_settings.database_url`, `redis_*` | Not needed for one process: keys are a file and records are the audit log. For several replicas, add a Postgres [store](/operations/store/), which shares keys, budgets, rate limits and cooldowns. There is no Redis. |
| `litellm_settings.drop_params` | Enterplace never drops a parameter silently. |
| `cache`, `cache_params` | Add `cache: { ttl_seconds: N }` to a rule, with `semantic:` for matches in other words. See [Caching](/routing/caching/). |
| `success_callback`, `callbacks` | Every request is in the [audit log](/governance/audit-log/), and `/metrics` serves Prometheus. For Langfuse, Arize Phoenix, Datadog or an OTLP endpoint, see [Observability integrations](/operations/observability-integrations/). |
| `guardrails` | Not written, since each vendor's settings are written differently. The report names the Enterplace type of each (`presidio`, `lakera`, `aporia`, `bedrock_guardrail`, `openai_moderation`, `azure_content_safety`, `azure_prompt_shield`, `model_armor`, `pangea`, `lasso`, `guardrails_ai`, and the built-in secrets detector for `hide-secrets`), or the webhook for one with none. Define each under `guardrails:` and list it on a rule. See the [vendor reference](/governance/guardrails/#vendor-reference). |
| `general_settings.alerting` | Not written. See [Alerting](/operations/alerting/), an enterprise feature. |
| Vertex AI models other than Gemini and Claude | Not served by Enterplace. Left out. |
| A provider the import has no mapping for | Left out. Check the [provider list](/providers/overview/) before giving up on it. If the provider speaks the OpenAI API, add it as `kind: openai` with its `url`. |
| Anything else | Reported as not mapped. |

## Keys

LiteLLM stores only the hashes of its virtual keys, as Enterplace does, so keys cannot move. Every key is reissued.

`--keys-from` reads an export of LiteLLM virtual keys: a JSON list, an object with the list under `keys` or `data`, or CSV with a header row.

| Export field | Used as |
|---|---|
| `key_alias` (else `user_email`, `user_id`, `key_name`) | The person's name |
| `team_alias` (else `team_id`) | The team. A key with neither goes to team `default`. |
| `models` | The key's `--models`, kept to models this config serves. In CSV the column may be quoted with commas inside (`"gpt-4o,gpt-4o-mini"`). |
| `max_budget` with `budget_duration` | `--budget N/<period>`. LiteLLM resets `24h`, `7d` and `30d` on the UTC day, Monday and the 1st, so they become `day`, `week` and `month` (`1mo` too). Other durations keep their length: `30m` is `30min`, `6h`, `14d`, `3mo`; seconds count in whole minutes. A duration under a minute or over a year, or none (a lifetime budget), is reported and left off. |
| `expires` | `--expires` with its date. A key already expired is reported and gets no command. |
| `tpm_limit` | `--tpm` |
| `rpm_limit` | `--rpm` |
| `max_parallel_requests` | `--parallel` |

From the export the import writes:

- A rule `team-<team>` for each team, before `everyone`, allowing the models its keys list. When one of its keys lists none, the rule allows `["*"]`, because an empty list in LiteLLM means every model.
- One command per key, in the report:

```bash
enterplace key new maya --team payments --budget 20/month --expires 2027-01-01 --models gpt-4o,gpt-4o-mini --tpm 50000
```

Run each command and send the printed key to its owner through your secret manager. Developers can instead get their own key with `enterplace login`. See [Keys and identity](/governance/keys/).

## What differs

- **The policy decides, not the key.** In LiteLLM a key carries its models, budget and limits. In Enterplace a key carries a name and a team, the first matching rule decides, and a key can only narrow its rule. Start from the teams, not from the keys.
- **A record before every request.** Each request, allowed or refused, gets a hash-chained [audit record](/governance/audit-log/) before it is forwarded. If the record cannot be written, the request is refused.
- **Nothing is dropped.** There is no `drop_params`. A parameter Enterplace does not know is forwarded as sent, or refused by name where a translation cannot carry it.
- **Unknown config is an error.** `enterplace check` names the file, the line and the nearest known word for every mistake, and `enterplace serve` does not start on one.
- **Budgets reserve.** A request under a budget reserves the most it could cost before it is sent and gives the rest back when the answer ends, so a budget cannot be overrun by requests in flight. A small budget with large `max_tokens` refuses requests that would have fitted. See [how a budget is counted](/governance/budgets-and-rate-limits/#how-a-budget-is-counted).
- **Model names.** Callers send bare model names or aliases, not `provider/model`. To keep clients that send a prefixed name, add an alias with that name.
- **Fewer providers.** LiteLLM lists far more providers than Enterplace has kinds. Check each of yours against the [provider list](/providers/overview/) before you plan a date.
- **No prompt text by default.** The audit log and the request log hold no prompt or answer text. A rule can [capture bodies](/operations/request-log/#bodies) for named viewers.
- **Client changes.** Each client gets a new key and base URL. A client that sent `api_key` or `api_base` in the request body to pick a deployment must stop: see [a caller's own provider key](/governance/provider-credentials/#a-callers-own-provider-key).

## Two regions of one model

Two deployments of `gpt-4o` at two OpenAI-compatible URLs become two providers and one alias `gpt-4o`. A model name belongs to one provider, so the second provider lists it as `gpt-4o@<provider>`. Callers send `gpt-4o`, and the alias sends the real name to whichever deployment it picks.

For Azure and Bedrock, the `@` name is a key of `deployments` or `model_ids`, so it also works when sent directly.

No LiteLLM source code was read. The import is tested against sample configs in those shapes, not against a running LiteLLM.
