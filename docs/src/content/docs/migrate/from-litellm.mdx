`gantry import litellm` reads a LiteLLM proxy `config.yaml` and writes a Gantry policy that passes `gantry check`. Everything it cannot carry across is listed with what to do instead. Given an export of LiteLLM virtual keys, it also writes team rules and one `gantry key new` command per key.

## Import a config

<Steps>

1. Run the import. `--out` names the policy to write (default `gantry.policy.yaml`); `--keys-from` is optional.

   ```bash
   gantry import litellm config.yaml --out gantry.policy.yaml
   gantry import litellm config.yaml --keys-from keys.json --out gantry.policy.yaml
   ```

2. Read the report. Each line is an item that was not mapped, or that needs a hand, with the fix.

3. Read the policy. The last rule, `everyone`, allows every imported model to anyone with a Gantry key, as a LiteLLM proxy allows any valid key every model by default. Narrow it before you serve.

4. Reissue the keys with the commands from the report, then start the gateway with `gantry serve gantry.policy.yaml`.

</Steps>

The import never replaces an existing file. If `--out` exists, it stops with an error and writes nothing. After writing, it runs `gantry check` on the result.

## Example

This LiteLLM config serves one OpenAI model and one Anthropic model under its own name:

```yaml title="config.yaml"
model_list:
  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o
      api_key: os.environ/OPENAI_API_KEY
  - model_name: claude-sonnet
    litellm_params:
      model: anthropic/claude-sonnet-4-5
      api_key: os.environ/ANTHROPIC_API_KEY
general_settings:
  master_key: sk-1234
  database_url: postgres://litellm@db/litellm
```

And this key export holds one key:

```json title="keys.json"
[{"key_alias": "maya", "team_alias": "payments", "models": ["gpt-4o"], "max_budget": 20, "budget_duration": "30d", "tpm_limit": 50000, "rpm_limit": 10}]
```

```bash
gantry import litellm config.yaml --keys-from keys.json --out gantry.policy.yaml
```

```text
Wrote gantry.policy.yaml.
Not mapped, or needs a hand (4 items):
  - key maya: reissue with `gantry key new maya --team payments --budget 20/month --models gpt-4o --tpm 50000` (LiteLLM keeps only key hashes, so keys cannot move).
  - key maya: rpm_limit 10 has no per-key equivalent; a rule's rate: { rpm: 10 } limits each person.
  - general_settings.master_key: Gantry has no master key. Make an admin key: gantry key new <name> --team <team> --admin.
  - general_settings.database_url: not needed. Gantry keeps keys in gantry.keys.yaml and records in its audit log.
See docs/migrate-litellm.md. Checking it now:
gantry.policy.yaml is valid: 2 rules, 0 keys, 2 providers: openai (openai) at https://api.openai.com, anthropic (anthropic) at https://api.anthropic.com.
```

The policy it writes:

```yaml title="gantry.policy.yaml"
# Imported from a LiteLLM config by `gantry import litellm`. Check it with `gantry check`.
version: 1
providers:
- name: openai
  kind: openai
  url: https://api.openai.com
  key_env: OPENAI_API_KEY
  models:
  - gpt-4o
- name: anthropic
  kind: anthropic
  url: https://api.anthropic.com
  key_env: ANTHROPIC_API_KEY
  models:
  - claude-sonnet-4-5
aliases:
- name: claude-sonnet
  deployments:
  - provider: anthropic
    model: claude-sonnet-4-5
rules:
- name: team-payments
  principals:
    team: payments
  models:
  - gpt-4o
- name: everyone
  principals:
    any: true
  models:
  - gpt-4o
  - claude-sonnet
```

`claude-sonnet` became an alias, because callers send a name that differs from the deployment's model. `gpt-4o` is listed directly under its provider.

<Aside type="tip">
The import keeps LiteLLM's variable names in `key_env`. If Claude Code will run through Gantry, rename `ANTHROPIC_API_KEY` to a variable of its own, such as `ANTHROPIC_PROVIDER_KEY`: Claude Code reads `ANTHROPIC_API_KEY` for its own key, which is a Gantry key.
</Aside>

## What maps

| LiteLLM | Gantry |
|---|---|
| `model_list[].model_name` | The model name callers send. One deployment whose model has the same name is listed under its provider's `models`. Several deployments, or one under another name, become an [alias](/gantry/routing/aliases/) with that name. |
| `litellm_params.model` with `openai/`, or a bare `gpt-*` | `kind: openai`, `url: https://api.openai.com` |
| `anthropic/`, or a bare `claude-*` | `kind: anthropic` |
| `azure/<deployment>` with `api_base`, `api_version` | `kind: azure` with `deployments` and `api_version` |
| `bedrock/<model id>` with `aws_region_name` | `kind: bedrock` with `region` and `model_ids`. Gantry signs with its own `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`. |
| `gemini/` | `kind: gemini` |
| `vertex_ai/gemini-*` with `vertex_project`, `vertex_location` | `kind: vertex` with the `/publishers/google` URL |
| `vertex_ai/claude-*` with `vertex_project`, `vertex_location` | `kind: vertex_anthropic` with the `/publishers/anthropic` URL, and an alias from the `model_name` to the Vertex model name (`claude-sonnet-4-5@20250929`) |
| `groq/`, `mistral/`, `together_ai/`, `fireworks_ai/`, `deepseek/`, `openrouter/`, `ollama/`, `ollama_chat/`, `lm_studio/`, `hosted_vllm/` | `kind: openai` with the vendor's base URL from [Providers](/gantry/providers/overview/), or `api_base`. A local server gets `allow_private: true` and no key. |
| `api_key: os.environ/NAME` | `key_env: NAME`. A key written in the config is not copied: the report names the variable to set. |
| `litellm_params.weight` | The deployment's `weight` |
| `model_info.input_cost_per_token`, `output_cost_per_token` | `prices:` in dollars per million tokens, under the name Gantry sends |
| A deployment named by its owner (`azure/gpt-4o-eastus`) | Priced as the model it runs: `model_info.base_model` when set, else the LiteLLM model string, else the `model_name`, written under `prices:` for the deployment's name. A team budget or a key `tpm` then works on the imported alias. |
| `router_settings.routing_strategy` `simple-shuffle`, `least-busy` | Alias `balance: round_robin`, `least_busy` |
| `router_settings.cooldown_time` | Alias `cooldown_seconds` (up to 3600) |
| `num_retries` (router or litellm settings) | Each provider's `retries` (up to 5) |
| `context_window_fallbacks`, `content_policy_fallbacks` | The alias's `context_window_fallback`, `content_policy_fallback`. Gantry follows one target, so the first is used. |

Check the price of an imported alias with `gantry prices <alias> --policy gantry.policy.yaml`. A deployment that none of the price sources above covers is reported, with the `prices:` line to add.

## What is reported instead

These are not mapped. Each appears in the report with what to do in Gantry.

| LiteLLM | What to do in Gantry |
|---|---|
| Other `routing_strategy` values | The alias uses `round_robin`. |
| `fallbacks` | Gantry fails over between an alias's deployments, or from a provider to its `fallback` provider for the same model. Add the fallback as a deployment of the alias if it may also take a share of traffic. |
| `rpm`, `tpm` per deployment | Gantry limits people, teams and keys: `rate:` on a rule, `tpm` on a key. See [Budgets and rate limits](/gantry/governance/budgets-and-rate-limits/). |
| `general_settings.master_key` | Make an admin key with `gantry key new <name> --team <team> --admin`. |
| `general_settings.database_url`, `redis_*` | Not needed. Keys are a file, records are the audit log, cooldowns are in memory on one node. |
| `litellm_settings.drop_params` | Gantry never drops a parameter silently. |
| `cache`, `cache_params` | Add `cache: { ttl_seconds: N }` to a rule. |
| `success_callback`, `callbacks` | Every request is in the [audit log](/gantry/governance/audit-log/), and `/metrics` serves Prometheus. |
| Vertex AI models other than Gemini and Claude | Not served by Gantry. Left out. |
| A provider with no Gantry kind and no OpenAI-compatible URL | Not served by Gantry. Left out. If it speaks the OpenAI API, add it as `kind: openai` with its `url`. |
| Anything else | Reported as not mapped. |

## Keys

LiteLLM stores only the hashes of its virtual keys, as Gantry does, so keys cannot move. Every key is reissued.

`--keys-from` reads an export of LiteLLM virtual keys: a JSON list, an object with the list under `keys` or `data`, or CSV with a header row.

| Export field | Used as |
|---|---|
| `key_alias` (else `user_email`, `user_id`, `key_name`) | The person's name |
| `team_alias` (else `team_id`) | The team. A key with neither goes to team `default`. |
| `models` | The key's `--models`, kept to models this config serves. In CSV the column may be quoted with commas inside (`"gpt-4o,gpt-4o-mini"`). |
| `max_budget` with `budget_duration` | `--budget N/day` for `1d` or `24h`; `--budget N/month` for `30d`, `1mo` or `1m`. Any other duration is reported. |
| `expires` | `--expires` with its date. A key already expired is reported and gets no command. |
| `tpm_limit` | `--tpm` |
| `rpm_limit` | Reported. A key has no requests-per-minute limit; a rule's `rate: { rpm: N }` limits each person. |

From the export the import writes:

- A rule `team-<team>` for each team, before `everyone`, allowing the models its keys list. When one of its keys lists none, the rule allows `["*"]`, because an empty list in LiteLLM means every model.
- One command per key, in the report:

```bash
gantry key new maya --team payments --budget 20/month --expires 2027-01-01 --models gpt-4o,gpt-4o-mini --tpm 50000
```

Run each command and send the printed key to its owner through your secret manager. Developers can instead get their own key with `gantry login`. See [Keys and identity](/gantry/governance/keys/).

## Two regions of one model

Two deployments of `gpt-4o` at two OpenAI-compatible URLs become two providers and one alias `gpt-4o`. A model name belongs to one provider, so the second provider lists it as `gpt-4o@<provider>`. Callers send `gpt-4o`, and the alias sends the real name to whichever deployment it picks.

For Azure and Bedrock, the `@` name is a key of `deployments` or `model_ids`, so it also works when sent directly.

<Aside type="note">
The config format was read from LiteLLM's public docs on 2026-11-13 ([configs](https://docs.litellm.ai/docs/proxy/configs), [reliability](https://docs.litellm.ai/docs/proxy/reliability), [config settings](https://docs.litellm.ai/docs/proxy/config_settings), [virtual keys](https://docs.litellm.ai/docs/proxy/virtual_keys)). The import is tested against sample configs in those shapes, not against a running LiteLLM.
</Aside>
