Gantry's state is four files. This page covers changing them while Gantry runs, keeping them safe, and what to do when the disk fills up.

## Health check

```text
GET /healthz
```

| Status | Body `status` | Meaning |
|---|---|---|
| 200 | `ok` | Gantry can do its job |
| 503 | `the audit log cannot be written` | A write failed, or the log was deleted, moved, replaced or cut short. Every request is refused until a restart |

The body also names the versions in use and any rejected version on disk:

```json
{"status":"ok","policy_sha256":"5d41...","keys_sha256":"7c21...","rejected":null}
```

`rejected` is `{"policy_sha256": ..., "keys_sha256": ...}` while a saved change fails the check. The health check needs no key and is not recorded. Any method other than `GET` on `/healthz` is refused with `unknown_route` and recorded.

## Change policy and keys without a restart

Save the policy file or the keys file and Gantry uses the new version within 2 seconds. Gantry compares the SHA-256 of both files once a second, so an editor that saves by renaming a new file into place, and a symlink switched to another file, are both noticed.

<Tabs>
<TabItem label="On save">

```bash
$EDITOR /etc/gantry/gantry.policy.yaml
```

</TabItem>
<TabItem label="At once with SIGHUP">

```bash
kill -HUP "$(pgrep -x gantry)"
```

</TabItem>
</Tabs>

A change is checked with the same rules as `gantry check`:

- **It passes.** Gantry writes a `config_loaded` record first, then decides every later request with it. The policy and keys switch together. A request decided before the switch finishes under the decision it got, its stream included.
- **It fails.** Gantry keeps the version it has, prints every problem to stderr with its file and line, and writes one `config_rejected` record per distinct pair of files. It uses the next save that passes. A missing file is a failed change too.

```text
/etc/gantry/gantry.policy.yaml:12: "modles" is not a key Gantry knows. Did you mean "models"?
gantry: the change to /etc/gantry/gantry.policy.yaml or /etc/gantry/gantry.keys.yaml is not used: 1 problem above. Gantry keeps deciding with the version it has (policy 5d41402a, keys 7c211433) and uses the next save that passes `gantry check`.
```

### What needs a restart

| Change | Restart |
|---|---|
| Rules, keys, guardrails, prices, aliases | No |
| A provider's `models`, `deployments`, `model_ids`, `retries`, `fallback`, `accept_chat` | No |
| A provider's `name`, `kind`, `url`, `key_env`, `allow_private`, `region`, `api_version` | Yes |
| Adding or removing a provider | Yes |
| The audit log path | Yes |
| A provider key (its environment variable) | Yes |
| The TLS certificate and key | Yes |

A change that needs a restart is rejected while Gantry runs, with that reason, and recorded as `config_rejected`. A reload that names a guardrail credential variable that is not set is rejected too.

<Aside type="tip">
A key removed by hand works for up to 2 seconds, until the reload picks the change up. Revoke through the console or `DELETE /admin/keys/<prefix>` to stop it at once.
</Aside>

## Signals and shutdown

| Signal | Effect |
|---|---|
| `SIGHUP` | Checks the policy and keys files at once. The `config_loaded` record's `trigger` is `signal` |
| `SIGTERM` or Ctrl-C | Stops accepting connections and gives requests in flight 30 seconds to finish |
| A second `SIGTERM` or Ctrl-C | Ends the wait |

Before the process ends, every record already handed to the audit writer is written and synced, including the usage record of an answer that ended just before the stop.

## Limits and timeouts

| Limit | Value | When reached |
|---|---|---|
| Request body | 32 MiB | `body_too_large`, 413 |
| Request bodies in memory, all callers | 256 MiB | `busy`, 503, `Retry-After: 1` |
| Request bodies in memory, one caller | 64 MiB | `busy`, 429, `Retry-After: 1` |
| Strings from the caller in an audit record | 200 characters | Cut |

| Wait | Default | On expiry |
|---|---|---|
| Client sends its request headers | 10 s | Connection closed |
| Client sends its request body | 30 s | `body_timeout`, 408 |
| TCP connect to the provider | 5 s | `upstream_unreachable`, 502 |
| Provider starts answering | 120 s | `upstream_timeout`, 504 |
| Requests in flight after a stop signal | 30 s | Process exits |

These values are fixed. A streamed answer has no time limit once it starts. Memory for a body is reserved as its bytes arrive and released once the request is handed to the provider. Nobody waits in a queue for it, so a large request cannot hold small ones up. Gantry serves HTTP/1.1.

### Memory

Idle, Gantry uses a few MiB. Beyond that, memory is mostly request bodies in flight (at most 256 MiB), a few hundred bytes per key, and one small entry per caller that has sent a request since start. A container memory limit of 384 MiB leaves room for the full body budget. Measure under your own load before setting it lower.

## Audit log on disk

Each record reaches the operating system before the request is forwarded, and the file is synced to disk once a second. A process crash loses no records; a power loss can lose up to about a second of them.

A decision record is about 650 bytes and a usage record about 700, so a million forwarded requests make about 1.35 GB. Gantry reads and verifies the whole file at every start, and the time that takes grows with the file. A new audit log is created with mode `0600`.

### Start a new chain

Rotation is not built in. To start a new chain:

<Steps>

1. Verify the log and keep its count and last hash.

   ```bash
   gantry audit verify /var/lib/gantry/gantry-audit.jsonl
   ```

2. Stop Gantry.

3. Move the file aside and keep it.

   ```bash
   mv /var/lib/gantry/gantry-audit.jsonl /var/lib/gantry/gantry-audit-2026-11.jsonl
   ```

4. Start Gantry. It writes a new log from record 1.

</Steps>

## Backups

| File | Holds | How to keep it |
|---|---|---|
| `gantry.policy.yaml` | Providers, rules, guardrails, prices, console settings | Version control. It holds no secrets |
| `gantry.keys.yaml` | The SHA-256, name, team and limits of each key | Back up with the same care as the policy: whoever can write it decides who may call. It holds no keys |
| `gantry-audit.jsonl` | Every decision, usage and admin action | Ship it as it is written ([Observability](/operations/observability/#shipping-the-audit-log)), and keep old chains moved aside |
| `gantry.kills.json` | Active kill switches, beside the keys file | Optional. Deleting it turns every switch off |

Keep the count and last hash of the audit log where the Gantry host cannot write, on a schedule. A chain cannot show records removed from its end; the kept hash can.

```bash
gantry audit verify /var/lib/gantry/gantry-audit.jsonl | sed -n 's/^Last hash: //p'
```

Later, check that the log still holds it:

```bash
gantry audit verify /var/lib/gantry/gantry-audit.jsonl --expect-last <kept hash>
```

Provider keys live only in environment variables. Keep them in your secret manager.

## Disk full and audit repair

When an audit write fails, every later request is refused with `audit_unavailable`, `/healthz` answers 503, `gantry_audit_broken` turns 1, and stderr says what happened. Gantry does not write to that file again until it is restarted.

A write that fails part way can leave the last line cut short. `gantry serve` then refuses to start and names the command to run.

<Steps>

1. Free the space and stop Gantry.

2. See the cut line. Nothing is changed, and the command exits 1.

   ```bash
   gantry audit repair /var/lib/gantry/gantry-audit.jsonl
   ```

   It prints the byte where the chain stops holding and the cut line itself.

3. Remove only that line.

   ```bash
   gantry audit repair /var/lib/gantry/gantry-audit.jsonl --yes
   ```

   It appends an `audit_repaired` record holding what was removed (`removed_bytes`, `removed_sha256`, `removed_text`), so the repair is itself in the chain.

4. Start Gantry.

</Steps>

Repair removes a last line only when it is the start of the next record cut short: it does not parse as JSON and begins as that record must (`{"n":<next number>,` or a shorter piece of it). Anything else is refused and left in place:

- a changed or missing record anywhere in the chain, reported as `gantry audit verify` reports it,
- a last line that is whole JSON without its newline,
- a log that grows between the check and the removal.

A log changed in the middle is evidence, not something to repair. If the removed line was a usage record, its charge is gone from budgets after the restart; its text is kept in `removed_text`.

### The lock file

While Gantry has the log open it keeps `gantry-audit.jsonl.lock` beside it, holding its process ID.

- `audit repair --yes` refuses while the lock file exists.
- A second `gantry serve` on the same log refuses to start while the process the lock names is running.
- After `kill -9` or a crash the lock file stays. The next `gantry serve` takes it over once that process is gone. For a repair, delete it once Gantry is surely stopped.

## Stop all traffic

```bash
gantry kill --all --reason "provider incident, stopping all AI traffic"
gantry unkill --all
```

`gantry kill --all` refuses every request with `killed` within 1 second on every node serving the same files. The admin API stays open so an admin can turn it off. See [Kill switches](/governance/kill-switches/).

## Bench

`gantry-bench` measures what Gantry adds to a request.

```bash
cargo run --release -p gantry-bench -- --rps 1000 --secs 10 --max-p99-overhead-us 1000
```

It runs a mock model server and the gateway in one process, sends the same open-loop load to each, and prints two figures:

| Figure | Measures |
|---|---|
| added | Latency through the gateway minus latency to the mock alone, as the client sees it. Can be negative, because both runs carry noise |
| self-time | The time Gantry reports for identifying, deciding and recording, from its `Server-Timing: gantry;dur=` header. Shown, not gated |

With the policy on (the default: 1,000 keys and a `secrets` guardrail that blocks on every rule), the run also fails unless the audit log holds exactly one decision record and one usage record per request, in an unbroken chain.

| Flag | Default | Description |
|---|---|---|
| `--rps N` | `5000` | Requests per second |
| `--secs N` | `10` | Seconds of load |
| `--stream` | off | Streamed answers |
| `--messages` | off | Send to `/v1/messages`. Needs the policy |
| `--no-policy` | off | Measure forwarding alone |
| `--max-p99-overhead-us N` | none | Exit 1 when added latency at p99 is above N microseconds, or when the mock alone has a p99 above N (too noisy to measure) |

Read the numbers as a comparison between builds on one machine. The mock, the gateway and the load generator share one process and its CPU, so this is not a benchmark of the gateway alone.

`scripts/ci.sh` gates at 1,000 microseconds added at p99, at 1,000 requests a second: a 2-second warm-up that is not judged, then up to three 5-second attempts, each printed after the output of `uptime`. The gate passes when one attempt passes. `scripts/ci.sh --no-bench` skips it on a machine that cannot time anything.

## Upgrades

<Steps>

1. Build the new release and run `gantry check` from the new binary on your current policy and keys files.

   ```bash
   gantry check /etc/gantry/gantry.policy.yaml --keys /var/lib/gantry/gantry.keys.yaml
   ```

2. Keep the audit log's last hash.

3. Stop Gantry with `SIGTERM`. Requests in flight get 30 seconds.

4. Replace the binary or image, and start it on the same files.

5. Confirm the start line says the chain continues, and check the version.

   ```bash
   gantry version
   ```

</Steps>

### Rolling back

Stop the new version and start the previous one on the same files. Nothing is restored from a backup: the previous version serves the keys the new one issued, continues the same audit chain, and `gantry audit verify` from either version checks the whole log. Every release is held to this by `scripts/rollback_check.py <old binary> <new binary>`, which runs the old version, upgrades, rolls back on one folder and verifies the chain with both.

A policy that uses a field only the new version knows stops the old one at start, with the field's name and line: keep the previous policy file beside the new one until the upgrade has settled, and put it back when you roll back.

The new process verifies the whole audit log before it serves and continues the same chain. Its first `config_loaded` record has `trigger: start`, and its "before" hashes are the last version the log recorded, so a change made while Gantry was stopped shows. On Kubernetes the `Recreate` strategy leaves a few seconds with no gateway.
