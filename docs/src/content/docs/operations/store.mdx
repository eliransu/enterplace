Without a store, each Gantry process keeps its keys in a file, its kill switches beside it, and its spend, rate limits and console sessions in memory. That is right for one process. To run two or more behind a load balancer, give them one Postgres database: the store. They then act as one gateway.

- A key issued on any replica is accepted by all within 2 seconds. A revoked key is refused by all within 2 seconds.
- A kill switch set on any replica stops traffic on all within 1 second.
- A budget is enforced once across all replicas: what they charge together never passes it by more than one request's estimate.
- A rate limit (`rpm`, `tpm`) is enforced once across all replicas: together they never admit more than the limit in any 60 seconds.
- A deployment of an alias that fails on one replica is passed over by all within about a second.
- A console sign-in on one replica is good on all. Signing out, or removing the person, ends it on all.
- With `GANTRY_MASTER_KEY` set, provider keys can be kept here too, sealed with AES-256-GCM, and a rotation reaches all within 2 seconds. See [Provider credentials](/governance/provider-credentials/).

## When to use it

Use a store when you run more than one replica, for availability or for load. With one process, the files are simpler: there is nothing to run and nothing to back up but the volume.

## Configuration

Add a `store:` section to the policy. It names the environment variable that holds the connection string, never the string itself, which carries a password.

```yaml
store:
  postgres_url_env: DATABASE_URL
```

Set the variable on every replica:

```bash
export DATABASE_URL='postgres://gantry:...@db.example.com:5432/gantry'
gantry serve gantry.policy.yaml
```

- **Start.** `gantry serve` refuses to start, naming the fix, if the variable is unset or the database cannot be reached. `gantry check` checks the section without connecting.
- **Tables.** Gantry creates its tables on first start, in the database the string names. The user needs `CREATE` on it. The schema is versioned in the binary (the `gantry_schema` table); a newer Gantry updates it. See Rolling upgrades below for which versions may share a database.
- **Commands.** `gantry key new`, `key list`, `key revoke` and `key prune` change the store when the policy beside the keys file (or `--policy`) has `store:`, with the variable set. `gantry kill` and `unkill`, the admin API and the console change it through any replica.

### TLS

Gantry reads the libpq parameters `sslmode` and `sslrootcert` in the connection string, in URL form (`?sslmode=verify-full&sslrootcert=/etc/gantry/ca.pem`) or key=value form.

| `sslmode` | Encrypted | What is checked |
|---|---|---|
| `verify-full` (the default) | yes | The certificate is signed by a trusted root and names the host in the string. |
| `verify-ca` | yes | The certificate is signed by a trusted root. Any host name. |
| `require` | yes | Nothing, as libpq does. With `sslrootcert`, it checks as `verify-ca`. |
| `disable` | no | Nothing. Gantry starts with a warning that the connection is not encrypted. |

`prefer` and `allow` are refused: they fall back to plain text without saying so.

The trusted roots are the Mozilla set built into the binary (no system certificates are read), plus the certificates in the PEM file `sslrootcert` names. For `verify-ca` with `sslrootcert`, the file's certificates are the only roots.

Managed databases often sign with a CA of their own. Amazon RDS does: give its bundle.

```bash
curl -sSfo /etc/gantry/rds-global-bundle.pem https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem
export DATABASE_URL='postgres://gantry:...@mydb.abc123.eu-west-1.rds.amazonaws.com:5432/gantry?sslrootcert=/etc/gantry/rds-global-bundle.pem'
```

Cloud SQL and Azure Database for PostgreSQL publish their server CA the same way: download it and name it with `sslrootcert`. When the certificate is not trusted, `gantry serve` refuses to start and says to add `sslrootcert`.

A Unix socket never leaves the machine and Postgres offers no TLS on one, so Gantry connects to a socket in plain text whatever `sslmode` says, with no warning, as libpq does. A host that starts with `/` is a socket directory.

The two common clouds:

- **AWS, Amazon RDS directly** (not through RDS Proxy): the RDS endpoint with `sslrootcert` naming the RDS bundle, as above. `verify-full` holds, since the certificate names the endpoint.
- **GCP, Cloud SQL through the Cloud SQL Auth Proxy or connector**: the connector encrypts to Cloud SQL and gives a Unix socket, so name the socket and nothing else:

  ```bash
  export DATABASE_URL='host=/cloudsql/my-project:europe-west1:gantry user=gantry password=... dbname=gantry'
  ```

A Postgres inside your Kubernetes cluster, on a private address and without TLS, needs `sslmode=disable`. Use it only on a network you trust: key hashes, kill switches and spend then cross it in plain text.

Changing the store's `postgres_url_env` or `policy_from` needs a restart. The rest of the policy still reloads within 2 seconds. With `policy_from: store` the policy itself is kept in the store as versions: see [Policy versions](/governance/policy/#policy-versions-in-the-store).

### Moving an existing keys file in

```bash
gantry store import --keys gantry.keys.yaml --policy gantry.policy.yaml
```

This copies every key of the file, and the kill switches in `gantry.kills.json` beside it, into the store. Keys already there are left as they are, so running it twice is safe. The file itself is not changed. While the policy has `store:`, Gantry does not read it: keep it as a backup or delete it.

## What is stored, and what is not

| In the store | Not in the store |
|---|---|
| Keys: name, team, the SHA-256 of the key, admin, expiry, budget, models, tpm. Never a key itself. | The policy. It stays a file, reviewed in git, and every replica reads its own copy. |
| Kill switches, with their reason, who set them and when. | Prompts and answers. Gantry never stores them, here or anywhere. |
| Spend and reservations, per team, person and key, per day and month. | The audit log. Each replica keeps its own hash-chained file. |
| Provider credentials, sealed with AES-256-GCM under the master key, with their name, vendor, last 4 characters and who added and rotated them. | The master key. It stays in each replica's environment or a file it names. |
| Rate-limit leases: how much of each `rpm` and `tpm` each replica took, for the last minute. | The answer cache, unless `answer_cache: true` (see below). |
| Request counts per hour, day and session (`rph`, `rpd`, `session_requests`), beside spend. | |
| Budget raises: the scope, amount, end, reason, who asked and who decided. | |
| Each replica's heartbeat: its name, host, version, schema, when it started and when it last wrote. | |
| Session pins: the SHA-256 of the person and session, the deployment, and when it last sent. Never the session ID itself. | |
| Each replica's last 32 times to first byte per alias deployment, for `lowest_latency`. | |
| Cooldowns of alias deployments that failed, until when. | Requests in flight per deployment, for `least_busy`. Each replica counts its own. |
| Console sessions: the SHA-256 of the session ID, who it is for, and when it ends. Never the ID itself. | A single sign-on sign-in in progress. Its callback must reach the replica that started it. |

Spend in the store counts requests under a budget (a rule's or a key's). Requests without a budget never reach the database, so their cost is in the audit log and in each replica's memory only.

## How it works

Keys and kill switches are read from memory, as without a store. Each replica polls a version row every 500 ms and reloads them when the version changes, so a request never waits on the database for its key or a switch. A change reaches every replica, the one that made it included, within about a second.

A request under a budget reserves the most it could cost with one atomic statement, which fails when the reservation would pass the budget. Two replicas reserving at the same moment are ordered by Postgres, so they cannot both pass. When the answer ends, a second statement replaces the reservation with what the request cost, off the request path. A request with no budget makes no database call.

### Budget leases

Most budgeted requests make no database call either. A replica reserves eight requests' worth of a budget in one statement, admits the next requests from that lease in memory, and gives back what it did not use after one second. What a lease holds is reserved in Postgres like any request's reservation, so:

- **Overshoot: none.** All replicas together never reserve more than the budget. A test sends 340 requests at once through two replicas against a budget that fits 300, and exactly 300 are admitted.
- **Lease size.** Eight times what the request could cost, and never more than 1% of the budget. A request that could cost more than 1% of its budget is reserved exactly, with no lease.
- **Near the limit.** When a lease does not fit, the replica reserves exactly what each request needs for the next 5 seconds, so the budget is spent to its last request.
- **Cost.** A replica can hold up to 1% of a budget unused for up to a second. A request can be refused with `budget_exceeded` while other replicas hold that much each; it is never let past the budget.

Hourly, daily and session request counts (`rph`, `rpd`, `session_requests`) are counted the same way, in the same table.

### Budget raises

A [budget raise](/governance/budgets-and-rate-limits/#budget-raises) asked for or decided on one replica is read by the others with the 500 ms poll, from memory, so a request never waits on the database for it. The table is `gantry_raises`, in the migration namespace `gantry_ha`.

### Heartbeats

Each replica writes a row to `gantry_replicas` every 2 seconds: a name that is new at each start, its host name (`HOSTNAME`), its Gantry version, the store schema it knows by namespace, when it started and when it last wrote. A replica counts as healthy for 10 seconds after its last write, and its row is deleted a day after it. An embedding binary reads the list through the store interface (`Store::replicas`).

### Rate limits

Rate limits are leased, so most requests make no database call. A replica takes a slice of a limit from Postgres in one atomic statement, admits requests from that slice in memory for one second, and gives back what it did not use. A slice is a twentieth of the limit, or what one request needs if that is more. Postgres takes a slice only if it fits the limit with every slice taken in the last minute, and counts each slice until half a second after its replica stopped using it. So:

- **Overshoot: none.** All replicas together never admit more than `rpm` requests, or `tpm` tokens as estimated at admission, in any 60 seconds. Tests hold three replicas to this under a burst of three times the limit.
- **Cost.** A slice taken and not used blocks the other replicas until it is given back, up to 1.5 seconds. Near the limit a replica can be refused while another holds part of the minute; it is never let past it.
- **Database calls.** About one per slice: at the limit's pace, one every three seconds per replica, person (`rpm`) and team, person or key (`tpm`). What requests give back is written twice a second, in one statement.

`tpm` with a store counts a request's tokens when it is admitted, the most it could use, and corrects them to what the provider reported when its answer ends. Without a store, a request holds its tokens until its answer ends.

### Cooldowns

When a deployment of an alias fails, the replica passes it over at once and writes until when to the store. The other replicas read the store's cooldowns with keys and kill switches, every 500 ms, and pass the deployment over until then. The replica it failed on probes it when the time is up, as described in [Aliases](/routing/aliases/#behavior); an answer from it on any replica ends the cooldown on all. A normal answer makes no database call.

### Session pins and latency

An alias with `session_affinity: true` keeps a coding agent's session on one deployment. With a store, every replica pins the session to the same deployment, and an alias with `balance: lowest_latency` ranks its deployments on the 90th percentile of every replica's recent answers pooled, so all replicas pick the same one.

Neither costs a database call on the request path. A replica reads the pins and the latency rows from memory, refreshed with the 500 ms poll, and writes what it pinned and measured with the next poll. A pin is written again at most every 5 minutes while its session keeps sending, so other replicas know it is in use. A session pinned on one replica reaches the others within about a second; a coding agent's next request comes after its first answer, so it lands on the same deployment. Two replicas pinning a new session in the same instant settle on one within a poll. Pins idle for an hour and latency rows not written for 10 minutes are deleted. The tables are `gantry_affinity` and `gantry_latency`, in their own migration namespace, `gantry_routing`. Deployment limits (`max_parallel`, `rpm`, `tpm`) are shared the same way: each replica writes its load on each deployment with the poll (`gantry_deployment_load`, migration 3 of `gantry_routing`), and a replica that stops writing counts for nothing after 10 seconds.

Without a store, each gateway keeps its own pins and measurements, as before.

### Sessions an events plugin ended

When an [events plugin](/governance/plugin-events/) ends a session, the replica that was told refuses the session at once and writes its end to the store: the SHA-256 of a text made from the session id, the guardrail's name, and when the refusal runs out. The other replicas read the ended sessions from memory, refreshed with the 500 ms poll when one more ends, so they refuse the session within a second and no request waits on the database for it.

### Console sessions

A console session is a row in the store, read on every console page. A session opened on one replica is found by all, and signing out deletes the row, so the session ends on every replica at once. Removing an admin key or a person's single sign-on access ends their sessions on every replica as it already did on one: the key is gone from every replica within 2 seconds, and the policy is read on each page. A row holds the SHA-256 of the session ID, so reading the database does not let anyone sign in. Sessions in the store rather than signed cookies: no signing key to share between replicas, and a sign-out takes effect at once, with no list of ended sessions to keep. Console pages are not on the request path, so the lookup adds nothing to API requests.

### The answer cache

The answer cache is per replica unless you share it. By default no answer is written to Postgres, and with N replicas the first identical request on each still goes to the provider.

```yaml
store:
  postgres_url_env: DATABASE_URL
  answer_cache: true
```

With `answer_cache: true`, every answer a rule caches is also kept in the store, and a replica that misses its own memory asks the store before the provider.

- **Scope.** A row is read back only under the cache key and the scope it was written for (the rule, and the person or team). The scope is kept as its SHA-256.
- **Guardrails.** Nothing changes: request guardrails run before the lookup, an answer waits for the answer guardrails' pass before it is kept, and a hit is checked again.
- **Semantic cache.** Embeddings are stored beside the answers. A lookup reads the newest 512 of its partition and compares them in the gateway.
- **Bounds.** A row is deleted when its `ttl_seconds` run out. Past 1 GiB of answers, the least recently used go first.
- **Cost.** A hit in memory takes microseconds. A miss in memory adds one round trip, on rules with `cache:` only.

<Aside type="caution">
`answer_cache: true` writes model answers to Postgres as the provider returned them, for at most `ttl_seconds`. They are not sealed with the master key. Leave it off where answers must not be at rest outside the audit trail's own controls.
</Aside>

The tables are `gantry_answer_cache` and `gantry_answer_vectors`, in the migration namespace `gantry_ha`.

## Several replicas

Run every replica with the same policy and the same `DATABASE_URL`, each with its own volume for its audit log. On Kubernetes that is a StatefulSet with a volume per pod, as the Helm chart runs it: see [Kubernetes](/deploy/kubernetes/). Put a load balancer in front, with its health check on `GET /healthz`.

- Each replica's audit log is a chain of its own. Verify each with `gantry audit verify`, and ship each to your SIEM.
- A replica that restarts reads the keys and switches from the store, and spend is in the store: nothing is lost.
- Console single sign-on: the identity provider's callback must reach the replica that started the sign-in, which sealed its state with a key of its own. Use session affinity on `/console/sso/`. Once signed in, the session is good on every replica.

## When Postgres is down

Gantry fails closed for spend and stays up for everything else:

- **Known keys keep working** from memory. A key issued or revoked during the outage cannot be: the command says the store cannot be reached, and nothing is changed.
- **Kill switches keep their last state.** A new switch cannot be set until the store is back.
- **A request under a budget is refused** with `503` and the code [`store_unavailable`](/reference/refusal-codes/#store_unavailable): Gantry cannot reserve its cost, and it never lets it through unchecked. Requests without a budget are served.
- **A request under `rpm` or `tpm` is refused** the same way once its replica's slice is spent or its second is over: counted per replica, the replicas could admit the limit each.
- **The console signs no one in.** A session cannot be looked up, and it may have ended on another replica. A sign-out during the outage is retried for 10 minutes, so the session does not come back with the database.
- **Cooldowns keep their last state.** A deployment that fails on a replica is still passed over there; the others learn of it when the store is back.
- **What requests cost** while the database comes and goes is retried for 10 minutes. A reservation that is never settled keeps counting against its budget until the period ends: an outage can make a budget stricter, never looser.

Each replica writes one line to stderr when the store goes away and one when it is back. Budgeted and rate-limited requests are served again within a second of the database answering.

<Aside type="caution">
A replica that dies with requests in flight leaves their reservations held until the budget's period ends (the next UTC day or month). Size budgets with that in mind, or raise one by hand if a crash holds too much of it.
</Aside>

## Rolling upgrades

Two Gantry versions one minor version apart (0.2.x and 0.3.x) run on one database at the same time, so replicas can be replaced one by one while the gateway keeps serving:

- The newer version applies its migrations when it starts. The older replicas keep serving, accept keys the newer one issues, and the newer accepts theirs.
- An older replica that restarts mid-rollout starts on the schema the newer one moved ahead.
- A Gantry two or more minor versions behind refuses the database at start, naming its own version and the newer one (`the store was written by a newer Gantry (0.4.0, ...; this one is 0.2.1 ...)`). Upgrade it, or upgrade in steps of one minor version.

How it holds: every migration only adds (tables, columns, indexes). A change that removes or renames something an older version reads ships two minor versions later, when the version that read it can no longer run beside the database. The database records the newest version that started on it (`gantry_writer`), and an older binary compares itself with that. The release workflow runs `scripts/mixed_version_check.py`: the previous version and the new one on one Postgres at once, serving traffic while the new one migrates.

The guarantee starts with the release that adds it: a version released before it refuses any newer schema when it restarts, so for that one upgrade, keep old pods from restarting during the rollout or replace every replica together.

Rolling back past a migration still needs the backup taken before the upgrade: an older version beside a newer schema is supported only within one minor version.
