With a license that includes `alerts` (see [License key](/operations/license/)), Enterplace adds an **Alerts** page to the console. You define rules there; Enterplace evaluates them against the audit records of every replica and sends each alert to the channels you pick. Every alert names the audit records behind it and is written to the audit chain itself.

## Before you start

- The policy needs a `store:` section: rules, channels and alert history live in the same Postgres as the [store](/operations/store/).
- Set `ENTERPLACE_EXPORT_KEY` on every replica to the same 64 hex characters (`openssl rand -hex 32`). Channel credentials (webhook URLs, routing keys, SMTP passwords, signing secrets) are kept encrypted with it.
- Optional: set `ENTERPLACE_CONSOLE_URL` to the console's address as people reach it, such as `https://enterplace.example.com`. Links in alerts then open the alert and its audit records directly. Without it, links are relative to the console.

<Steps>

1. Open **Alerts** in the console and add a channel. **Send a test alert** checks it end to end.
2. Add a rule, pick its kind, set its parameters, and list the channel numbers it sends to.
3. Watch **Recent alerts**: each one lists its records, each a link to that decision in the audit page, and how delivery went.

</Steps>

## Channels

| Kind | URL | Secret | Sent as |
|---|---|---|---|
| Slack | The incoming webhook URL | None: the URL is the credential, kept encrypted | A message with the summary, links to each record and to the alert |
| Microsoft Teams | The workflow's "when a webhook request is received" URL, or an incoming webhook URL | None: the URL is kept encrypted | An Adaptive Card 1.4 in a `message`, with facts, record links and an **Open in Enterplace** button |
| PagerDuty | Empty (`https://events.pagerduty.com/v2/enqueue`) | The integration's routing key | Events API v2 `trigger`, `dedup_key` `enterplace-<rule>-<subject>` so repeats group into one incident, the alert as `custom_details` |
| Email | `smtps://host:465` (TLS from the start) or `smtp://host:587` (STARTTLS) | The SMTP password, with a username | A plain text message to every To address, with the records and links |
| Webhook | Your HTTPS endpoint | Made by Enterplace (`whsec_...`), shown once | A JSON POST signed the [Standard Webhooks](https://www.standardwebhooks.com/) way |

STARTTLS is required unless the SMTP server is this machine. Webhook URLs must be `https://`, or `http://` to this machine only.

### Webhook body and signature

```json
{"type":"enterplace.alert","alert":42,"rule":"Payments budget","kind":"budget","severity":"warning","subject":"team:payments:2026-11","summary":"team:payments has spent $81.20 in 2026-11, reaching $80.00.","time":"2026-11-14T10:02:11.120Z","link":"https://enterplace.example.com/console/alerts#alert-42","records":[{"replica":"pod-0-84347ac2b1f0","n":1204,"hash":"9c1f...","id":"01M7969SBMMKV7S7HFP6Q99SPJ"}]}
```

Each POST carries `webhook-id` (`alert_<id>`), `webhook-timestamp` (seconds) and `webhook-signature: v1,<base64>`, the HMAC-SHA256 of `<webhook-id>.<webhook-timestamp>.<raw body>` under the base64-decoded part of the secret after `whsec_`. Any Standard Webhooks library verifies it. Reject a timestamp more than five minutes old.

## Rules

| Kind | Fires when | Parameters | Subject |
|---|---|---|---|
| `budget` | Spend of a scope reaches an amount this day or month, or a **percent** of each budget the policy sets for the scope ([below](#a-percent-of-a-policy-budget)); with **Forecast**, when spend at the current rate would reach it by the period's end (checked once a tenth of the period has passed) | scope (`all`, `team`, `person`, `key`; with a percent also `org`, `customer`, `tag`, `model`), name (empty: each one), period, amount in USD, or percent | scope, name and period: once per period |
| `rate_limit` | `count` requests refused with `rate_limited` within `minutes` | count, minutes, group by | the group |
| `refusals` | `count` refusals with any of the codes within `minutes`, such as `budget_exceeded,key_budget_exceeded` | codes, count, minutes, group by | the group |
| `provider_errors` | `count` provider failures within `minutes`: answers with status 5xx or 429, failed tries in [attempts records](/reference/audit-records/#attempts), and every request no provider answered ([upstream error records](/reference/audit-records/#upstream-error)), retried or not | count, minutes, provider | the provider |
| `latency` | `count` requests slower than `ms` within `minutes`, timed from the decision record to the usage record (the answer's end) | ms, count, minutes, provider | the provider |
| `guardrail_block` | `count` requests refused with `guardrail_blocked`, or answers a guardrail withheld, within `minutes` | count, minutes, group by | the group |
| `kill_switch` | A kill switch is set (an `admin` record with action `set_kill`) | none | the record: once each |
| `new_ip` | A key is used from an address it has not used before. A key's first addresses are learned, not alerted on | none | key and address: once each |
| `after_hours` | A key is used outside working hours or on a weekend | hours, such as `08-19` or `08-19+0200` | key and day: once a day |
| `unusual_spend` | A person's spend today is `factor` times their daily average of the last 14 days, and at least the amount | factor (3), amount in USD (5) | person and day: once a day |
| `unusual_requests` | A scope's requests today are `factor` times its daily average of the last 14 days, and at least `count` | by (`team`, `key`, `provider`; default team), factor (3), count (100) | scope and day: once a day |
| `unusual_errors` | A scope's error rate today (answers with status 5xx or 429, and requests no provider answered) is `factor` times its rate over the last 14 days, with at least `count` errors | by, factor (3), count (10) | scope and day: once a day |
| `unusual_latency` | A scope's average latency today is `factor` times its average over the last 14 days, over at least `count` requests | by, factor (2), count (20) | scope and day: once a day |
| `deployment_down` | `count` failures of a provider within `minutes` and not one answer from it in that time | count, minutes | the provider |
| `credential_failing` | `count` answers with status 401 or 403 from a provider within `minutes`: it refuses Enterplace's credential | count, minutes | the provider |
| `guardrail_vendor_failing` | `count` requests or answers whose guardrail service could not be reached within `minutes`, whether it failed open or closed | count, minutes | the guardrail |
| `key_expiring` | A key expires within `days`. Checked once a minute against the keys | days (7) | key and expiry: once each |
| `export_lagging` | An audit export destination has records older than `minutes` that it has not sent. Checked once a minute | minutes (15) | replica and destination |
| `daily_digest` | Every day once the local time reaches `at`: the last 24 hours of every replica, with spend, requests, refusals and their commonest codes, the five top users by spend, and the alerts fired by kind. With [watch mode](/integrations/claude-team/), the spend and the top users include what Claude Code reported on Claude seats, and a second line, `Watched:`, says how much of the spend that was. Sent to each of the rule's channels. A rule added after that time sends today's digest at once | at, such as `09:00` or `09:00+0200` (default `09:00` UTC) | the local day: once a day |
| `region_outage` | Every [alias deployment](/routing/aliases/) whose `region:` is the region has `count` failures within `minutes`, and not one of them answered in that time. A region with one deployment still answering does not fire | region (empty: each region), count (1), minutes (5) | the region |
| `config_rejected` | A reload refuses a change to the policy or keys file (a `config_rejected` record, with the first problem), or a policy version sent through the admin API is refused as `invalid_policy` | none | the refused change, or the record: once each |
| `kill_cleared` | A kill switch is cleared (an `admin` record with action `clear_kill`) | none | the record: once each |
| `circuit_open` | An alias deployment fails (no answer, a 429 or a 5xx) and is passed over for its alias's `cooldown_seconds` | none | the deployment (`provider/model`), once per quiet period |
| `system` | The audit log cannot be written, this replica's records cannot be read into Postgres, the alert tables cannot be read, or requests are refused with `store_unavailable` or `kills_unreadable`, or a refresh cannot read a [secret manager](/operations/secret-managers/) (`secret_refresh_failed`) | none | replica and problem (for a secret, the variable) |

Group by is `all` (default), `person`, `team` or `key`. The unusual kinds compare by `team` (default), `key` or `provider`: their requests, errors and latency are kept per scope and day in Postgres from the first record read, so the baseline is there when a rule is added. A replica new to alerting reads the records of the last 14 days before the month began, so the baseline is whole from the start.

Each failure counts once: a try that was retried is in the attempts record, and the last try is in the usage record when the provider answered (a 5xx or 429 passed on) or in the upstream error record when none did. A failure Enterplace made itself, such as a model with no deployment (`unknown_model`), is not a provider's and does not count.

### Watched spend

With [watch mode](/integrations/claude-team/), the cost Claude Code estimates for each request on a Claude Team or Enterprise seat counts for `budget` rules by amount and for `unusual_spend`, under the person and team of the watch token. A rule with a percent counts only requests that went through Enterplace, as the policy's budgets do.

### A percent of a policy budget

A `budget` rule with **percent** set watches the budgets the policy itself sets, instead of an amount of its own:

| Field | Example | Meaning |
|---|---|---|
| percent | `80` | Fires when spend reaches 80% of the budget |
| scope, name | `team`, `payments` (or scope `team:payments`) | The counter, as the policy names it: `global`, `org:acme`, `team:payments`, `person:maya.cohen`, `key:1a2b3c4d`, `customer:globex-shop`, `tag:search`, `model:o3`. Inside an organization, `team:acme/payments`. A kind alone (`team`) watches each one of it |
| forecast | on | Fires when spend at the current rate would reach the percent by the period's end |

For each request's usage, the rule asks the policy in force which budgets the cost counted against (`Policy::applied`: the rule's own, the key's, and every `limits:` entry for the caller, customer, tags and model) and checks each one the scope names against its own amount and period: a `per: month` budget for this month, a `per: 6h, tz: Europe/Berlin` one for the current six hours in Berlin, a `per: { sliding: 24h }` one for the last 24 hours. Spend is read from the gateway's own counter in the store, the one enforcement reserves against, so the alert and the refusal agree. A policy change applies from the next record.

It fires once per budget and period (subject `team:payments|month|2026-11`). A sliding window has no periods: its subject is `team:payments|sliding:24h`, quiet for the rule's quiet period after each alert, and it has no end to forecast to, so forecast reads what is spent.

```json
{"kind":"budget","subject":"team:payments|month|2026-11","summary":"team:payments has spent $81.20 of its $100.00 budget per month in 2026-11 (81%), reaching 80%."}
```

`region_outage` and `circuit_open` read alias deployments by `provider/model`, as attempts records name them, and the answer of each usage record that carries an `alias`. Region labels come from the policy in force, read when a region rule has something to check.

## Deduplication and rate limits

- After an alert, the same rule and subject stay quiet for the rule's **quiet period** (60 minutes by default). Matching records are counted, not sent.
- Kinds whose subject names a period or an event (budget, kill switch set or cleared, new address, after hours, the unusual kinds, key expiring, daily digest, config rejected) fire once per subject.
- A rule sends at most **At most per hour** alerts an hour (10 by default). The rest are counted as suppressed.
- Each replica evaluates its own records once, and counts, spend and known addresses live in Postgres. A rule therefore sees every replica, and one alert goes out however many replicas there are.
- Records older than an hour when first read (a new install, a replica catching up) count toward spend and the baseline but never fire.
- When Postgres cannot be reached, `system` rules still fire from the last rules and channels read, once per quiet period per replica.

## In the admin API

Alert rules are in the [admin API](/reference/admin-api/#alert-rules) too, with the same checks as this page: `GET /admin/alerts/rules`, `POST /admin/alerts/rules`, `PUT` and `DELETE /admin/alerts/rules/<id>`, `GET /admin/alerts/channels` (never their secrets) and `GET /admin/alerts` (what fired lately). Reading needs `see_records`, changing `edit_policy`.

```bash
curl -X POST http://127.0.0.1:8080/admin/alerts/rules -H "Authorization: Bearer $ENTERPLACE_ADMIN_KEY" \
  -d '{"name": "Payments volume", "kind": "unusual_requests", "params": {"by": "team", "factor": "3", "count": "200"}, "channels": [1]}'
```

## What is recorded

- Every change to a channel or rule is an `admin` record written before the change: `alert_channel_saved`, `alert_channel_tested`, `alert_channel_removed`, `alert_rule_saved`, `alert_rule_enabled`, `alert_rule_disabled`, `alert_rule_removed`. A refused change is recorded with its code (`read_only`, `invalid_url`, `invalid_rule`). Credentials never appear in records.
- Every alert is an `alert` record in the replica's chain:

```json
{"n":1290,"event":"alert","id":"01M79B2Q8V3K0N7Z5X4R1T9WD0","time":"2026-11-14T10:02:11.140Z","alert":42,"rule":"Payments budget","rule_id":3,"kind":"budget","subject":"team:payments:2026-11","summary":"team:payments has spent $81.20 in 2026-11, reaching $80.00.","records":[{"replica":"pod-0-84347ac2b1f0","n":1204,"hash":"9c1f...","id":"01M7969SBMMKV7S7HFP6Q99SPJ"}],"prev":"...","hash":"..."}
```

- The console keeps the last alerts with their delivery outcome per channel.

Viewers see the page and change nothing. Without the license feature the page answers `license_required` and the nav does not offer it.
