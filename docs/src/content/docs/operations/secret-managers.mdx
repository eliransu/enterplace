Any variable the policy names with `*_env` (a provider's `key_env`, `console.sso.client_secret_env`, a guardrail's or MCP server's headers) may hold a reference to a secret manager instead of the secret. `enterplace serve` reads each reference at start, keeps the value in memory, and reads it again on reload and every 5 minutes, so a key rotated in the manager is used without a restart. This is the enterprise feature `secrets`.

```bash
export OPENAI_PROVIDER_KEY='vault://secret/data/enterplace#openai'
export ANTHROPIC_PROVIDER_KEY='aws-sm://prod/enterplace/anthropic'
enterplace serve enterplace.policy.yaml
```

The policy does not change: `key_env: OPENAI_PROVIDER_KEY` stays as it is.

## References

| Manager | Reference | Read with |
|---|---|---|
| HashiCorp Vault | `vault://<path>#<field>`, such as `vault://secret/data/enterplace#openai` (KV v2) or `vault://kv/enterplace#openai` (KV v1) | `GET <VAULT_ADDR>/v1/<path>` |
| AWS Secrets Manager | `aws-sm://<name or ARN>[#<field>]` | `GetSecretValue` |
| Google Secret Manager | `gcp-sm://projects/<project>/secrets/<name>[/versions/<n>][#<field>]` (latest unless a version is named) | `versions.access` |
| Azure Key Vault | `azure-kv://<vault name>/<secret>[/<version>][#<field>]` | Get Secret, API version 7.4 |
| CyberArk Conjur | `conjur://<variable id>[#<field>]`, such as `conjur://prod/enterplace/openai` | `GET <CONJUR_APPLIANCE_URL>/secrets/<account>/variable/<id>` |
| AWS KMS | `aws-kms://<key id, alias or ARN>#<base64 ciphertext>` | `Decrypt` |
| Google Cloud KMS | `gcp-kms://projects/<p>/locations/<l>/keyRings/<r>/cryptoKeys/<k>#<base64 ciphertext>` | `cryptoKeys.decrypt` |
| Azure Key Vault keys | `azure-kv-key://<vault name>/<key>[/<version>]#<base64url wrapped key>` | Unwrap Key, `RSA-OAEP-256` |

`#<field>` takes one field of a secret that holds a JSON object. A Vault secret with one field needs none.

## A master key wrapped by a cloud key

The last three references hold a value encrypted with a key that never leaves its cloud service, and Enterplace asks that service to decrypt it. This is how to keep `ENTERPLACE_MASTER_KEY` wrapped rather than in plain text anywhere:

```bash
# Once: encrypt the master key's 64 hex characters with your KMS key.
openssl rand -hex 32 | tr -d '\n' > master.hex
aws kms encrypt --key-id alias/enterplace --plaintext fileb://master.hex --query CiphertextBlob --output text
# Then, on every gateway:
export ENTERPLACE_MASTER_KEY='aws-kms://alias/enterplace#AQICAHh...'
```

A decrypted value that is text is used as it is. One that is raw bytes, such as a 32-byte data key from `aws kms generate-data-key`, is used as hex, which is the master key's 64 characters. The gateway's identity needs `kms:Decrypt` on the key (AWS), `roles/cloudkms.cryptoKeyDecrypter` (Google Cloud), or the `unwrapKey` permission, as in the **Key Vault Crypto User** role (Azure). Revoking that permission stops new gateways from starting; running ones keep the key in hand and record each failed refresh. `AWS_ENDPOINT_URL_KMS` and `CLOUDSDK_API_ENDPOINT_OVERRIDES_CLOUDKMS` reach private endpoints.

## Signing in to each manager

Each manager is signed in to the way its own SDKs do, so a workload with an identity needs no static credential. Enterplace never runs a cloud command line tool.

<Tabs syncKey="manager">
<TabItem label="Vault">

- `VAULT_ADDR`: the address, https (plain http only to this machine).
- A token from `VAULT_TOKEN`, else `~/.vault-token`, else the [Kubernetes auth method](https://developer.hashicorp.com/vault/docs/auth/kubernetes) with `VAULT_K8S_ROLE`, the pod's service account token (`VAULT_K8S_TOKEN_PATH` to read it elsewhere) and the mount `VAULT_K8S_MOUNT` (`kubernetes` unless set).
- `VAULT_NAMESPACE` for Vault Enterprise namespaces.

</TabItem>
<TabItem label="AWS">

The AWS default chain, as for [Bedrock](/providers/bedrock/): access keys in the environment, IRSA on EKS, ECS task roles and EKS Pod Identity, then the EC2 instance profile (IMDSv2). The region comes from the ARN, else `AWS_REGION` or `AWS_DEFAULT_REGION`. `AWS_ENDPOINT_URL_SECRETS_MANAGER` reaches a VPC endpoint.

</TabItem>
<TabItem label="Google Cloud">

Application Default Credentials, as for [Vertex AI](/providers/vertex/): `GOOGLE_APPLICATION_CREDENTIALS`, gcloud's application default credentials, then the metadata server (GCE, GKE Workload Identity, Cloud Run). The service account needs `roles/secretmanager.secretAccessor` on the secret.

</TabItem>
<TabItem label="Azure">

In the order of the Azure SDKs' DefaultAzureCredential: a client secret (`AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`), workload identity on AKS (`AZURE_FEDERATED_TOKEN_FILE` with the tenant and client), the App Service and Container Apps identity endpoint (`IDENTITY_ENDPOINT`, `IDENTITY_HEADER`), then the VM's managed identity. `AZURE_CLIENT_ID` picks a user-assigned identity. The identity needs the **Key Vault Secrets User** role, or a get permission in the vault's access policy.

</TabItem>
<TabItem label="Conjur">

- `CONJUR_APPLIANCE_URL`: the address, https (plain http only to this machine), with `/api` for Conjur Cloud. `CONJUR_ACCOUNT`: the account.
- A host's API key: `CONJUR_AUTHN_LOGIN` (such as `host/enterplace`) and `CONJUR_AUTHN_API_KEY`.
- Or the workload's own JWT through the JWT authenticator (`authn-jwt`): `CONJUR_AUTHN_JWT_SERVICE_ID`, with the token at `CONJUR_JWT_TOKEN_PATH` (the pod's service account token unless set).
- Access tokens are kept for their 8 minutes, then Enterplace signs in again.

</TabItem>
</Tabs>

## When secrets are read

- **At start.** Every variable holding a reference is read. One that cannot be read stops the start with the variable, the reference and the cause: Enterplace does not serve with a provider it cannot sign in to.
- **Every `ENTERPLACE_SECRETS_REFRESH_SECONDS`** (300 unless set, at least 10), and at once on `SIGHUP`. A changed value is put on the provider's route within a second, for new requests; a request already sent keeps its key. The gateway prints `provider "openai" now uses the key in OPENAI_PROVIDER_KEY.`
- **On a failure after start**, the value in hand stays in use and the failure is printed with the fix.

Each refresh writes an audit record for every variable whose value changed (`secret_rotated`) and every one it could not read (`secret_refresh_failed`, with the reason): the variable, its reference, the manager and the time, never the value ([fields](/reference/audit-records/#secret_rotated)). `/metrics` counts them as `enterplace_secret_rotations_total` and `enterplace_secret_refresh_failures_total` by manager. With the `alerts` feature, a [`system` alert rule](/operations/alerting/) fires on a failed refresh, so a revoked credential is fixed before the value in hand stops working. A Prometheus rule works too:

```yaml
- alert: EnterplaceSecretRefreshFailing
  expr: increase(enterplace_secret_refresh_failures_total[15m]) > 0
```

Values live in memory only: never on disk, in the audit log or in an error.

## Without the license feature

The open source gateway, and the image without a license that has `secrets`, refuse to start on a reference, naming the variable and the fix. They never send the reference itself as a key.

<Aside type="note">
`enterplace node` keeps its own `--secrets NAME=<source>` flags, which write keys to files the managed gateway reads. See [Hybrid](/operations/hybrid/).
</Aside>
