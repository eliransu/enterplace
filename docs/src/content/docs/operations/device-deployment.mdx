The device agent is the `gantry device` command of the Gantry Enterprise binary. Every install needs the same three things on the machine: the binary, the enrolment token in a file, and something that starts the agent. The files for each are in `deploy/mdm` of the repository. See [Devices](/operations/devices/) for what the agent does and for creating the token.

| OS | Runs as | Token file | Started by |
|---|---|---|---|
| macOS | root | `/Library/Application Support/Gantry/device-token` | A LaunchDaemon, `me.gantry.device` |
| Linux | root | `/etc/gantry/device-token` | A systemd unit, `gantry-device` |
| Windows | the signed-in person | `C:\ProgramData\Gantry\device-token` | A scheduled task at sign-in, `Gantry device agent` |

`GANTRY_DEVICE_TOKEN`, then the file `GANTRY_DEVICE_TOKEN_FILE` names, win over the token file. As root the agent works for the person signed in at the screen and writes Claude Code's managed settings; as a person it writes that person's own settings.

Each person runs `gantry login <gateway url>` once on their machine. The agent sends the key that saves with every report, and a machine where nobody has signed in is refused with `person_key_required` until someone does.

## Windows with Intune

`deploy/mdm/windows/install.ps1` copies the binary to `C:\Program Files\Gantry\gantry.exe`, writes the token file (people may read it, administrators change it) and registers the scheduled task for every person who signs in. It is a script, not an MSI: Intune deploys a script as a Win32 app the same way, and the script is plain text you can read and sign with your own certificate.

<Steps>

1. **Get the binary.** Build it on Windows with `cargo build --release -p gantry-enterprise` and rename `target\release\gantry-enterprise.exe` to `gantry.exe`, or take `gantry-enterprise-windows-x86_64` from a run of the `device-agent` CI job on `main`. For arm64 machines build with `--target aarch64-pc-windows-msvc`.

2. **Package.** Put `gantry.exe` and `install.ps1` in one folder and wrap it with Microsoft's Win32 Content Prep Tool:

    ```bat
    IntuneWinAppUtil.exe -c .\gantry-device -s install.ps1 -o .\out
    ```

3. **Add the app** in Intune: Apps, Windows, Add, Windows app (Win32), and upload `install.intunewin`.

    | Setting | Value |
    |---|---|
    | Install command | `powershell.exe -ExecutionPolicy Bypass -File install.ps1 -ControlPlane https://gantry.example.com -Token gantry_dev_...` |
    | Uninstall command | `powershell.exe -ExecutionPolicy Bypass -File install.ps1 -Uninstall` |
    | Install behavior | System |
    | Detection rule | File `C:\Program Files\Gantry\gantry.exe` exists |

4. **Assign** it to a device group. The agent starts at each person's next sign-in.

</Steps>

To keep the token out of the install command, deliver `C:\ProgramData\Gantry\device-token` with a separate Intune platform script that runs before the app, and leave `-Token` out: the installer keeps a token file that is already there. A token expires after the days it was made for, so the same script delivers the next one.

<Aside type="caution">
The Windows agent and its installer follow each tool's documentation and Microsoft's for scheduled tasks. They are built and unit-tested by the `device-agent` CI job, and have not yet been run on a Windows fleet. Try one machine with `--dry-run` first.
</Aside>

The shell env file the agent writes (`%USERPROFILE%\.config\gantry\env`) is not read by Windows shells. Tools that take their endpoint from the environment only need `ANTHROPIC_BASE_URL` and `OPENAI_BASE_URL` set by Intune or Group Policy.

## macOS with Jamf or Kandji

Build the package on a Mac. It installs the binary in `/usr/local/bin` and loads the LaunchDaemon:

```bash
cargo build --release
deploy/mdm/build-pkg.sh https://gantry.example.com
productsign --sign "Developer ID Installer: <your org>" deploy/mdm/gantry-device-<version>.pkg gantry-device-signed.pkg
```

The token travels as a managed preference, in `deploy/mdm/gantry-device-token.mobileconfig` with `PASTE_ENROLMENT_TOKEN` replaced. A script then copies it to the file the agent reads:

```bash
mkdir -p "/Library/Application Support/Gantry" && umask 077 && \
/usr/bin/defaults read "/Library/Managed Preferences/me.gantry.device" EnrolmentToken \
  > "/Library/Application Support/Gantry/device-token"
```

| Step | Jamf Pro | Kandji |
|---|---|---|
| The token | Configuration Profiles, Upload, the `.mobileconfig` | Library, Add new, Custom Profile |
| The token script | Settings, Scripts, then a Policy that runs it at recurring check-in | Library, Custom Script, run once per device, or as the Custom App's preinstall script |
| The package | Settings, Packages, then the same Policy installs it after the script | Library, Custom App, install type Package |
| Scope | The Policy's and the profile's scope | The Blueprint both are assigned to |

The agent's log is `/var/log/gantry-device.log`. To deliver a new token before the old one expires, change the profile and run the script again.

## Linux

`deploy/mdm/install-linux.sh` installs the binary, the token and the systemd unit, and starts it:

```bash
sudo GANTRY_DEVICE_TOKEN=gantry_dev_... deploy/mdm/install-linux.sh https://gantry.example.com ./gantry
sudo deploy/mdm/install-linux.sh --uninstall
```

Run it from your configuration tool (Ansible, Fleet, Intune for Linux) or by hand. It is a script, not a deb or rpm: the agent is one static file and one unit. The log is `journalctl -u gantry-device`. As root the agent finds the signed-in person with `who` and works in `/home/<user>`; run as a user unit or by hand, it writes that user's own files.

## Try it first

```bash
GANTRY_DEVICE_TOKEN=gantry_dev_... gantry device --control-plane https://gantry.example.com --dry-run
```

It prints each file it would write, each MCP server it would take out, and the report it would send, and changes nothing.
