Enterplace serves an admin console at `/console` on the gateway's own address, under `enterplace start` and `enterplace serve` alike. It reads the policy, keys and audit files on every page, and every sign-in, issue and revoke it performs is a record in the same audit chain.

## Open it

`enterplace start` prints a link that signs you in once, from the same machine, within 10 minutes, and opens it in your browser. No key to paste: see the [Quickstart](/getting-started/quickstart/). Later, go to `http://127.0.0.1:8080/console` (or your gateway's address). The start line names it:

```text
Console: http://127.0.0.1:8080/console (sign in with an admin key)
```

The console exists only when Enterplace serves from a policy file. It is not served with `--unchecked`.

## Sign in

<Tabs>
<TabItem label="Admin key">

Paste an Enterplace key whose entry in the keys file says `admin: true`. `enterplace start` printed one (`export ENTERPLACE_KEY=...`). Without it, make one on the command line:

```bash
enterplace key new noa.bar --team platform --admin
```

A key that is not an admin's is refused and recorded with code `not_admin`. The page gives the same answer for an unknown key, so it does not tell which keys exist.

</TabItem>
<TabItem label="Single sign-on">

With `console.sso` in the policy, the sign-in page shows "Sign in with single sign-on". Enterplace runs the OpenID Connect authorization code flow with PKCE against your identity provider and takes the person's role from a claim in the ID token. Setup is in [Single sign-on](/governance/single-sign-on/). For SAML 2.0 sign-in, see [SAML](/governance/saml/).

If `client_secret_env` names a variable that is not set, Enterplace starts with a warning and every single sign-on fails. Signing in with an admin key still works.

</TabItem>
</Tabs>

The browser gets a random session ID in the `enterplace_console` cookie, never the key or a token. The cookie is `HttpOnly` and `SameSite=Strict`, and `Secure` when the browser reached Enterplace over TLS, directly or through a proxy that sends `X-Forwarded-Proto: https`. A session lasts 8 hours. Forms are accepted only from console pages on the same address.

## Roles

| Role | Signs in with | May |
|---|---|---|
| Admin | An admin key, or single sign-on with a value from `admin_values` in the role claim | Everything: read every page, issue and revoke keys, including admin keys |
| Read only | Single sign-on with a value from `read_only_values` | Read every page. Issuing or revoking a key is refused and recorded with code `read_only` |

There is no default role: a person whose claim holds neither value is refused with `sso_role`. A [console role](/governance/policy/#console-roles) from `roles:` in the policy grants a narrower set of permissions, and can keep its holders to one organization or to some teams.

## Issue and revoke keys

A key issued in the console is appended to the keys file exactly as `enterplace key new` appends it, and works as soon as the page answers. The key is shown once.

Revoking removes the entry from the keys file and stops the key at once. The console refuses to revoke the only admin key: mark another key `admin: true` first, so someone can still sign in.

<Aside type="caution">
The console and the admin API write the keys file. Mount it writable, and keep it readable by Enterplace's user only.
</Aside>

### Lockout after failed sign-ins

Five failed sign-ins within 15 minutes lock out where they came from for 30 minutes.

| Counted per | Applies to |
|---|---|
| Source address (an IPv6 address by its /64) | Admin key sign-in, and email and password sign-in ([Members](/operations/members/)) |
| Account (the email) | Email and password sign-in |

- While locked out, every sign-in from that address or to that account answers `429` with `Retry-After` and the code `sign_in_locked`. The key or password is not checked, the right one included.
- A good sign-in forgets the failures counted before it. An empty form is not an attempt.
- With a [store](/operations/store/), failures are counted in Postgres: five failures spread over several replicas lock out on all of them. Without one, each process counts its own.
- Behind a load balancer, list it under [`trusted_proxies`](/governance/access-control/#behind-a-load-balancer). The source is then the address it names in `X-Forwarded-For`, not the balancer's, which every person shares.
- The failure that locks a source or an account out is recorded once as `console_sign_in_locked`. Attempts refused during the lockout are not recorded one by one, so a flood cannot fill the audit log.
- To end a lockout early with a store: `DELETE FROM enterplace_sign_in_failures WHERE scope = 'source:203.0.113.7'`. Without one, restart Enterplace.

Single sign-on is not counted: the identity provider checks the password and applies its own lockout.

## What is recorded

Each action is an `admin` record with `"via": "console"`, written before the action is done. An action that cannot be recorded is not done.

| `action` | When |
|---|---|
| `console_sign_in` | A sign-in, allowed or refused. For single sign-on, `target.via` is `sso` and `target.role` is `admin` or `read_only`; a refusal carries an `sso_*` code |
| `console_sign_out` | A sign-out |
| `issue_key`, `revoke_key` | A key issued or revoked, with its name, team, hash prefix and admin flag in `target` |
| `self_issue_key` | A key issued to a person by `enterplace login` |
| `console_sign_in_locked` | The failed sign-in that locked out a source address or an account: `target.scope` (`source:<address>` or `account:<hash of the email>`), `target.failures`, `target.within_seconds` and `target.locked_seconds` |
| `console_sso_starts` | 100 or more single sign-on starts in one minute, written at most once a minute |
| `console_sso_refusals` | Refused sign-ins from one client address past the first 100 in a minute, summed in one record with the count per code |

Record fields are in [Audit records](/reference/audit-records/#admin). The sign-in refusal codes are in [Refusal codes](/reference/refusal-codes/#single-sign-on-codes).

## Sessions

Without a store, console sessions and single sign-ons in progress are held in the Enterplace process, and a restart signs everyone out. With a Postgres [store](/operations/store/), sessions are shared by every replica. Removing `console.sso`, or a person's email or domain from it, ends their session at their next page, because the policy is read on every page. A change of role at the identity provider applies at the next sign-in.
