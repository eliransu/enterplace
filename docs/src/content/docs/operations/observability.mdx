Gantry gives you two signals: Prometheus metrics for dashboards and alerts, and the audit log for what happened to each request. The audit log is the record; metrics are counts.

## Metrics

```bash
gantry serve gantry.policy.yaml --metrics 127.0.0.1:9464
```

```text
Metrics: http://127.0.0.1:9464/metrics
```

`GET /metrics` is served in the Prometheus text format on that address only. It is off unless `--metrics` names an address, and that address must differ from `--listen`. The gateway's own address never serves `/metrics`, so a caller with a Gantry key cannot read it. Scrapes are not written to the audit log.

<Aside type="caution">
`/metrics` takes no key and shows team, model and provider names and what each team spent. Keep it on loopback or a network only your scraper reaches. Gantry warns at start when the metrics address is not loopback.
</Aside>

### Metric reference

| Metric | Type | Labels | Counts |
|---|---|---|---|
| `gantry_requests_total` | counter | `route`, `verdict`, `code`, `provider` | Every decision, as the audit log records it |
| `gantry_upstream_responses_total` | counter | `provider`, `outcome` | Every attempt at a provider, retries and fallbacks included |
| `gantry_provider_key_switches_total` | counter | `provider`, `status` | A [key pool](/routing/key-pools/) key set aside after a 401, 403 or 429 |
| `gantry_upstream_seconds` | histogram | `provider` | Time from sending to a provider to its answer's headers |
| `gantry_overhead_seconds` | histogram | none | Gantry's own time on a forwarded request: identify, decide, guardrails, record, and handing the answer back. The same figure as the `Server-Timing: gantry;dur=` header |
| `gantry_audit_write_seconds` | histogram | none | Time of each write to the audit log. Under load one write carries many records |
| `gantry_audit_queue_depth` | gauge | none | Records waiting for the audit writer |
| `gantry_audit_broken` | gauge | none | `1` when the audit log cannot be written and every request is refused until a restart |
| `gantry_spend_usd_total` | counter | `team`, `model` | US dollars charged since Gantry started, as usage records write them |
| `gantry_secret_rotations_total` | counter | `source` | Gantry Enterprise: secrets a refresh found changed in their [secret manager](/operations/secret-managers/), by manager (`vault`, `aws-sm`, `gcp-sm`, `azure-kv`) |
| `gantry_secret_refresh_failures_total` | counter | `source` | Gantry Enterprise: secrets a refresh could not read from their manager, by manager. The value read before stays in use |
| `gantry_cache_saved_usd` | gauge | `team`, `kind` | US dollars caching saved since start: `answer` (Gantry's answer cache) or `prompt` (a provider's prompt cache, net of cache writes) |
| `gantry_refusals_total` | counter | `code` | Requests refused, by refusal code: the refused part of `gantry_requests_total`, summed over route and provider |
| `gantry_tokens_total` | counter | `team`, `model`, `kind` | Tokens providers reported: `input`, `output`, `cached` (read from a prompt cache) or `cache_write`. Answers from Gantry's cache add none |
| `gantry_request_seconds` | histogram | `model` | Time from a request reaching Gantry to the end of its answer, streamed or not |
| `gantry_first_byte_seconds` | histogram | `provider` | Time from a request reaching Gantry to its answer's headers leaving for the caller |
| `gantry_guardrail_findings_total` | counter | `kind` | What guardrails found on requests, by detector kind, such as `email_address`; `unavailable` when a guardrail service could not be reached |
| `gantry_cache_lookups_total` | counter | `outcome` | Answer cache lookups of rules with `cache:`: `hit` or `miss` |
| `gantry_deployment_up` | gauge | `deployment` | `1` while a deployment of an alias (`provider/model`) takes requests and its last [health probe](/routing/health-probes/), if it has one, got an answer; `0` while it cools down after failures or its probe fails |
| `gantry_deployment_cooldowns_total` | counter | `deployment` | Times a deployment was put to cool down after a failure (no answer, a 429 or a 5xx) |
| `gantry_budget_limit_usd` | gauge | `scope`, `name`, `per` | A budget of `limits:` in the policy |
| `gantry_budget_remaining_usd` | gauge | `scope`, `name`, `per` | What that budget has left this period: its limit less what was spent and what requests in flight hold. Counted by the store when the policy has one |
| `gantry_store_up` | gauge | none | With a store: `1` when it answers, `0` when requests under a budget or rate limit would be refused |

| Label | Values |
|---|---|
| `route` | `chat_completions`, `messages`, `count_tokens`, `responses`, `embeddings`, `models`, or `other` for every other path |
| `verdict` | `allow` or `refused` |
| `code` | The [refusal code](/reference/refusal-codes/), empty when allowed |
| `outcome` | The provider's HTTP status, or the Gantry code when it gave none, such as `upstream_timeout`. On `gantry_cache_lookups_total`, `hit` or `miss` |
| `scope` | The scope kind of a `limits:` entry: `global`, `org`, `team`, `person`, `key`, `customer`, `tag` or `model` |
| `name` | The entry's name, `org/name` when it is kept to an organization; empty for `global` |
| `per` | The budget's period, as the policy writes it: `day`, `month`, `6h`, `month@America/New_York` |

### Label cardinality

Every label value comes from the policy (routes, codes, providers, models, teams, deployments, detector kinds), never from what a caller sends, so the number of series is bounded by the policy. Budget gauges are the one family that could grow with people: by default they cover the `global`, `org`, `team` and `model` entries of `limits:`, and leave out entries for `*` (each member counted apart). Choose the scope kinds with `GANTRY_METRICS_BUDGET_SCOPES`, a comma-separated list such as `team,person`, or `none` for no budget gauges.

LiteLLM's Prometheus metrics, for orientation: requests (`gantry_requests_total`), tokens (`gantry_tokens_total`), spend (`gantry_spend_usd_total`), total latency (`gantry_request_seconds`), provider latency (`gantry_upstream_seconds`), time to first byte (`gantry_first_byte_seconds`), deployment state and cooldowns (`gantry_deployment_up`, `gantry_deployment_cooldowns_total`), remaining budgets (`gantry_budget_remaining_usd`), cache hits (`gantry_cache_lookups_total`), guardrail findings and errors (`gantry_guardrail_findings_total`). Key switches in a provider's key pool: `gantry_provider_key_switches_total`.

Histogram buckets run from 100 microseconds to 60 seconds: `0.0001`, `0.00025`, `0.0005`, `0.001`, `0.0025`, `0.005`, `0.01`, `0.025`, `0.05`, `0.1`, `0.25`, `0.5`, `1`, `2.5`, `5`, `10`, `30`, `60` and `+Inf`.

Counters start at zero when Gantry starts. Spend that counts against budgets is read back from the audit log at start, so budgets survive a restart even though `gantry_spend_usd_total` does not.

The metrics never hold a prompt, a key, a person's name or a decision ID.

### Scrape and alert

```yaml title="prometheus.yml"
scrape_configs:
  - job_name: gantry
    static_configs:
      - targets: ["127.0.0.1:9464"]
```

```yaml title="gantry-alerts.yml"
groups:
  - name: gantry
    rules:
      - alert: GantryAuditLogBroken
        expr: gantry_audit_broken == 1
        annotations:
          summary: Gantry cannot write its audit log and refuses every request. Look at the disk and restart it.
      - alert: GantryRefusalRateHigh
        expr: sum(rate(gantry_requests_total{verdict="refused"}[10m])) / sum(rate(gantry_requests_total[10m])) > 0.2
        for: 10m
        annotations:
          summary: More than a fifth of requests are refused. Group by code to see why.
      - alert: GantryTeamSpendHigh
        expr: sum by (team) (increase(gantry_spend_usd_total[1d])) > 500
        annotations:
          summary: A team spent more than $500 in a day.
```

## Traces

Gantry exports one OpenTelemetry span per request over OTLP/HTTP with JSON. Set the standard variables where `gantry serve` runs:

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318   # spans go to /v1/traces
OTEL_SERVICE_NAME=gantry                                  # the default
OTEL_EXPORTER_OTLP_HEADERS=authorization=Bearer%20abc     # optional, percent-encoded
```

`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` sets the full URL instead. Gantry speaks `http/json` only: a protocol variable set to anything else stops it at startup with a message saying so. Unset, nothing is exported.

When a request carries a W3C `traceparent`, its span joins that trace. The provider is sent a `traceparent` naming Gantry's span, so a trace reads caller, Gantry, provider.

| Span field | Value |
|---|---|
| Name | The method and path, such as `POST /v1/chat/completions` |
| `gantry.decision` | The decision ID, the same as the `x-gantry-decision` header and the audit record's `id` |
| `gantry.verdict`, `gantry.code`, `gantry.rule` | The decision and, for a refusal, its code |
| `gantry.team`, `gantry.provider`, `gen_ai.request.model` | Who, where and which model |
| `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gantry.charged_usd` | From the usage record |
| `http.response.status_code`, `gantry.ended` | How the answer ended |

The span lasts until the request's usage record, so a stream's span covers the whole stream. A span with no usage record (an upstream error, a route with no usage) ends when its answer was sent, five minutes later. Its status is an error only for a 5xx: a refusal is the policy working.

Spans carry what the audit log says and less: no prompt, no answer, no key and no person's name. They are built from the audit records, so traces need the audit log on, as it is under `gantry serve`.

Export never slows a request. Spans wait in memory and go out once a second. When the collector is down or slow, spans are dropped, and Gantry says so on standard error at most once a minute.

## Shipping the audit log

The audit log is a file of JSON lines, `gantry-audit.jsonl` or the `audit: { path: ... }` in the policy. Gantry only appends to it, so any shipper that tails a file can send it to Loki, Elasticsearch, Splunk or Datadog. Ship each line as it is: the `hash` and `prev` fields chain every record to the one before, and that chain is what `gantry audit verify` checks.

Fields worth indexing: `event` (absent on request records), `id`, `person`, `team`, `key`, `verdict`, `code`, `model`, `provider`, `charged_usd`. Every field is in [Audit records](/reference/audit-records/).

The recipes below read the file from its start and keep their place across restarts. They print to stdout: point the sink at your log system, and check the configuration against the version of the tool you run.

### Vector

```yaml title="vector.yaml"
sources:
  gantry_audit:
    type: file
    include: [/var/lib/gantry/gantry-audit.jsonl]
    read_from: beginning
transforms:
  gantry_parsed:
    type: remap
    inputs: [gantry_audit]
    # Keeps the original line in .line, so the chain can be checked from what was shipped.
    source: |
      .line = .message
      . = merge!(., object!(parse_json!(.message)))
sinks:
  out:
    type: console
    inputs: [gantry_parsed]
    encoding:
      codec: json
```

### Fluent Bit

```yaml title="fluent-bit.yaml"
pipeline:
  inputs:
    - name: tail
      path: /var/lib/gantry/gantry-audit.jsonl
      read_from_head: true
      db: /var/lib/fluent-bit/gantry-audit.db
      parser: json
      tag: gantry.audit
  outputs:
    - name: stdout
      match: gantry.audit
      format: json_lines
```

`parser: json` is the `json` parser from Fluent Bit's stock `parsers.conf`. To keep each line unparsed as well, leave the parser out and parse in the log system.

### OpenTelemetry Collector

Gantry has no OTLP exporter of its own. The Collector's `filelog` receiver, in the contrib distribution `otelcol-contrib`, turns each audit line into an OpenTelemetry log record and sends it on over OTLP.

```yaml
receivers:
  filelog/gantry:
    include: [/var/lib/gantry/gantry-audit.jsonl]
    start_at: beginning
    storage: file_storage
    operators:
      - type: json_parser
        parse_to: attributes
        timestamp:
          parse_from: attributes.time
          layout_type: gotime
          layout: "2006-01-02T15:04:05.000Z07:00"
extensions:
  file_storage:
    directory: /var/lib/otelcol/storage
processors:
  batch: {}
exporters:
  otlphttp:
    endpoint: https://otel.example.com:4318
  debug:
    verbosity: detailed
service:
  extensions: [file_storage]
  pipelines:
    logs:
      receivers: [filelog/gantry]
      processors: [batch]
      exporters: [otlphttp, debug]
```

- Each record's fields become log attributes (`attributes.person`, `attributes.code`). The original line stays in the log record's body: export that for verification.
- The record's `time`, always UTC with milliseconds such as `2026-11-12T14:02:11.482Z`, becomes the log record's timestamp.
- `file_storage` keeps the receiver's place across Collector restarts, so records are neither skipped nor sent twice. Its folder must exist and be writable by the Collector.
- `otlphttp` sends to `<endpoint>/v1/logs`. Replace the endpoint with your backend's and drop `debug` once it works. Recent Collector releases name this exporter `otlp_http` and accept `otlphttp` as a deprecated alias.

On Kubernetes, run the shipper as a second container in the Gantry pod. See [Kubernetes](/deploy/kubernetes/).

## Verify what was shipped

A copy in a log system can be edited or lose records like any other copy. Check it the same way as the file.

<Steps>

1. On Gantry's host, verify the log and keep the last hash where the host cannot change it, such as the log system or a ticket.

   ```bash
   gantry audit verify /var/lib/gantry/gantry-audit.jsonl
   ```

2. Export the original lines from the log system (the `line` field from Vector, or the log record body from the Collector), sorted by `n`, into a file.

3. Verify the export against the kept hash.

   ```bash
   gantry audit verify exported.jsonl --expect-last <hash kept in step 1>
   ```

   It passes only if every record up to that hash is there, unchanged and in order.

</Steps>

A shipped copy that starts in the middle of the log does not verify on its own. Export from record 1, or verify the file on the host.
