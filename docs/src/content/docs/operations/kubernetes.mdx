Gantry ships a Helm chart in `deploy/helm/gantry` and plain manifests in `deploy/kubernetes/gantry.yaml`. Both run the container image from `scripts/release.sh image` as one replica, with the audit log and keys file on a persistent volume.

## One replica, one audit chain

The audit log is one hash chain in one file, and budgets, rate limits and the cache are counted in one process. Two replicas would each write a chain of their own and each count a budget from zero. The chart therefore:

- refuses any `replicaCount` other than `1`: `helm template` fails with the reason,
- uses the `Recreate` strategy, so the old pod lets go of the volume before the new one starts (a few seconds with no gateway on every upgrade),
- keeps the audit log and keys file on one `ReadWriteOnce` volume annotated `helm.sh/resource-policy: keep`, so `helm uninstall` does not delete the record.

## Install

<Tabs>
<TabItem label="Helm">

<Steps>

1. Build the image and push it to your registry.

   ```bash
   scripts/release.sh image
   docker tag gantry:local registry.example.com/gantry:0.0.1
   docker push registry.example.com/gantry:0.0.1
   ```

2. Create a Secret with one entry per provider `key_env`.

   ```bash
   kubectl create secret generic gantry-provider-keys --from-literal=OPENAI_PROVIDER_KEY=sk-...
   ```

3. Install the chart.

   ```bash
   helm install gantry deploy/helm/gantry \
     --set image.repository=registry.example.com/gantry --set image.tag=0.0.1
   ```

4. Make the first admin key. The image has no shell, so `kubectl exec` runs the binary directly.

   ```bash
   kubectl exec deploy/gantry -- /gantry key new admin --team platform --admin \
     --keys /var/lib/gantry/gantry.keys.yaml
   ```

   The key works within 2 seconds.

</Steps>

</TabItem>
<TabItem label="Plain manifests">

`deploy/kubernetes/gantry.yaml` is the chart with its default values and metrics on, written out: a ConfigMap `gantry-policy`, a PersistentVolumeClaim `gantry-data` of `10Gi`, a Deployment `gantry` and a Service `gantry`. It runs the image `gantry:local`: change it to your registry's.

```bash
kubectl create secret generic gantry-provider-keys --from-literal=OPENAI_PROVIDER_KEY=sk-...
kubectl apply -f deploy/kubernetes/gantry.yaml
kubectl exec deploy/gantry -- /gantry key new admin --team platform --admin \
  --keys /var/lib/gantry/gantry.keys.yaml
```

</TabItem>
</Tabs>

Check it from your machine:

```bash
kubectl port-forward svc/gantry 8080:8080
curl http://127.0.0.1:8080/healthz
kubectl exec deploy/gantry -- /gantry audit verify /var/lib/gantry/gantry-audit.jsonl
```

## Chart values

| Value | Default | Description |
|---|---|---|
| `replicaCount` | `1` | Must be `1`. Any other value fails the install |
| `image.repository` | `gantry` | The image to run |
| `image.tag` | `local` | Its tag |
| `image.pullPolicy` | `IfNotPresent` | |
| `policy` | One OpenAI provider, one rule | The policy file as text. Its `audit: { path: ... }` must be under `/var/lib/gantry/` |
| `providerSecrets` | `[gantry-provider-keys]` | Secrets loaded as environment variables, one key per provider `key_env`. Gantry does not start while one is unset or empty |
| `persistence.size` | `10Gi` | The volume for the audit log and keys file. A million forwarded requests make about 1.35 GB of audit log |
| `persistence.storageClassName` | empty | The cluster default when empty |
| `persistence.existingClaim` | empty | Use a claim you made instead of one the chart makes |
| `tls.secretName` | empty | A `kubernetes.io/tls` Secret. Gantry serves HTTPS itself with `--tls-cert` and `--tls-key`, and the probes use HTTPS |
| `keysInit.image` | `busybox:1.36.1` | Runs once per start to write an empty keys file on a new volume |
| `service.type` | `ClusterIP` | |
| `service.port` | `8080` | |
| `metrics.enabled` | `false` | Serves `/metrics` on its own port, in the Service and never in the Ingress |
| `metrics.port` | `9464` | |
| `metrics.serviceMonitor.enabled` | `false` | A Prometheus Operator `ServiceMonitor` for the metrics port. Needs the `ServiceMonitor` CRD |
| `metrics.serviceMonitor.interval` | `30s` | |
| `ingress.enabled` | `false` | An Ingress for the gateway port |
| `ingress.className` | empty | |
| `ingress.host` | `gantry.example.com` | |
| `ingress.annotations` | ingress-nginx: buffering off, 32m bodies, 600 s read timeout | Answers must stream, and Gantry takes bodies up to 32 MiB |
| `ingress.tlsSecretName` | empty | TLS at the Ingress |
| `resources` | 100m CPU and 64Mi requested, 384Mi limit | The limit leaves room for the 256 MiB request body budget |
| `nodeSelector`, `tolerations`, `affinity` | empty | Passed to the pod |

## What the pod looks like

- **Least privilege.** User and group `65532`, never root, a read-only root filesystem, no privilege escalation, every Linux capability dropped, the runtime's default seccomp profile, and no service account token.
- **Policy.** A ConfigMap mounted as a folder at `/etc/gantry/policy`. A `helm upgrade` that changes the policy does not restart the pod: the kubelet updates the file within about a minute, and Gantry checks and uses it within 2 seconds, or keeps the old one and records `config_rejected`.
- **Data.** `/var/lib/gantry` is the volume, holding `gantry-audit.jsonl` and `gantry.keys.yaml`. The keys file is writable because the console and the admin API issue and revoke keys there.
- **Init container.** Writes `keys: []` to the keys file on a new volume, because `serve --keys` does not start on a keys file that does not exist. It never touches an existing file.
- **Probes.** Readiness and liveness call `/healthz`, which answers 503 when the audit log cannot be written. Gantry then refuses every request until a restart, which the liveness probe does after a minute.
- **Shutdown.** `SIGTERM` gives requests in flight 30 seconds. The pod gets 40 before it is killed, so the last audit sync happens.

<Aside type="caution">
Never expose the metrics port through the Ingress. `/metrics` takes no key and shows team names and spend.
</Aside>

## Ship the audit log from the pod

Run a log shipper as a second container in the Gantry pod, with the data volume mounted read-only at `/var/lib/gantry`. Containers of one pod can share a `ReadWriteOnce` volume. Give the shipper's own state an `emptyDir` or a volume of its own. Recipes are in [Observability](/operations/observability/#shipping-the-audit-log).

## Check the files

```bash
python3 scripts/check_deploy.py target/debug/gantry
```

It parses every YAML file in `deploy/`, checks the security settings above and the single replica, runs `gantry check` on the policy, and compares the chart's policy with the plain manifest's. With `helm` installed it also runs `helm lint` and `helm template`. It never contacts a cluster.
