An [alias](/routing/aliases/) serves one model name from several deployments. Its `balance` picks which deployment a request tries first, and every decision record says which one and why. A rule's `regions` keeps its requests in the regions you allow: a request with nowhere allowed to go is refused, never sent elsewhere.

## Example

```yaml title="gantry.policy.yaml"
version: 1
providers:
  - name: azure-eu
    kind: azure
    url: https://acme-eu.openai.azure.com
    key_env: AZURE_EU_KEY
    api_version: 2024-10-21
    models: [gpt-4o]
    deployments: { gpt-4o: gpt-4o-eu }
  - name: openai
    kind: openai
    url: https://api.openai.com
    key_env: OPENAI_API_KEY
    models: [gpt-4o-mini]
aliases:
  - name: smart
    balance: lowest_latency
    session_affinity: true
    deployments:
      - { provider: azure-eu, model: gpt-4o, region: eu }
      - { provider: openai, model: gpt-4o, region: us }
      - { provider: openai, model: gpt-4o-mini, region: us, for: { tag: batch } }
rules:
  - name: legal
    principals: { team: legal }
    models: [smart]
    regions: [eu]
  - name: everyone
    principals: { any: true }
    models: [smart]
    tags: [batch]
```

Team `legal` reaches only `azure-eu`. Everyone else gets the fastest of the two general deployments, and a request sent with `x-gantry-tags: batch` goes to `gpt-4o-mini`.

## Balance

| `balance` | Picks first | Recorded `reason` |
|---|---|---|
| `round_robin` (default) | In turn, each as often as its `weight` | `round_robin: its turn by weight` |
| `least_busy` | The fewest requests in flight through this gateway | `least_busy: 2 in flight` |
| `lowest_latency` | The lowest 90th percentile time to first byte over its last 32 answers on this gateway, or with a [store](/operations/store/#session-pins-and-latency) over the last 32 answers on each gateway, pooled, so every replica ranks deployments on the same numbers. A deployment not measured yet goes first, so each is measured before it is judged | `lowest_latency: p90 time to first byte 412 ms` |
| `lowest_cost` | The cheapest by its model's [price](/routing/pricing/), input plus output per million tokens. A deployment with no price goes after every priced one | `lowest_cost: $2.75 per million tokens in and out` |
| `adaptive` | The lowest score of latency, error rate and cost, weighted. See [Adaptive](#adaptive) | `adaptive: score 0.42 (p90 412 ms, errors 3%, $2.75 per million tokens)` |

Before any balance: a deployment cooling down after a failure is passed over, and once its cooldown ends one request probes it (`probe: ...`). The rest of the deployments follow as the chain of fallbacks, cooling ones last.

**Rate limits.** A deployment whose provider said in its last answer, within the last minute, that less than 5% of a rate limit is left goes after the deployments with room, before those cooling down. Gantry reads OpenAI's `x-ratelimit-remaining-requests` and `x-ratelimit-remaining-tokens` against their `x-ratelimit-limit-*`, and Anthropic's `anthropic-ratelimit-*-remaining` against `anthropic-ratelimit-*-limit`. This applies under every balance, so traffic moves off a nearly exhausted key before it starts getting 429s.

The 90th percentile is used rather than the average, so one slow answer does not move a deployment, while a deployment that stays slow loses its place within 32 answers. Each gateway measures its own path to the provider.

## Adaptive

`balance: adaptive` scores each deployment that is not cooling down and picks the lowest:

```text
score = weights.latency * (p90 / slowest p90) + weights.errors * error rate + weights.cost * (price / dearest price)
```

- **Latency** is the p90 time to first byte that `lowest_latency` uses, shared through the store when there is one. A deployment not measured yet counts as fastest, so each is measured.
- **Error rate** is a moving average of the deployment's attempts on this gateway: each failure (no answer, a timeout, a 429 or a 5xx) moves it a fifth of the way to 1, each answer a fifth of the way to 0. It is remembered after the circuit closes, so a deployment that just came back gets less traffic until it has answered for a while.
- **Cost** is its model's price, input plus output per million tokens. A deployment with no price counts as the dearest.

```yaml title="gantry.policy.yaml"
version: 1
providers:
  - name: openai
    kind: openai
    url: https://api.openai.com
    key_env: OPENAI_API_KEY
    models: [gpt-4o, gpt-4o-mini]
aliases:
  - name: smart
    balance: adaptive
    weights: { latency: 2, errors: 3, cost: 1 }
    deployments:
      - { provider: openai, model: gpt-4o }
      - { provider: openai, model: gpt-4o-mini }
rules:
  - name: everyone
    principals: { any: true }
    models: [smart]
```

Each weight is 0 to 100, not all 0. `gantry check` refuses `weights` on any other balance.

## Tags and teams pick deployments

A deployment with `for: { tag: <tag> }` or `for: { team: <team> }` is kept for those requests. [`when:`](/routing/conditional-routing/) keeps a deployment by more conditions the same way.

- A request whose team or tags match some kept deployments goes only to those, balanced among them.
- A request that matches none goes to the deployments kept for nobody.
- If every allowed deployment is kept for someone else, the request is refused with `no_deployment`.

A request's tags are its key's [`tags`](/governance/keys/#key-fields) plus those the caller sends in `x-gantry-tags` (comma separated). A caller may send only the tags its rule lists under `tags:`: any other is refused by name with `tag_not_allowed`, so a caller cannot reach a deployment kept for a tag or charge spend to one. The header is removed before the request is forwarded. Tags are recorded on the decision record.

## Residency: `regions`

Label each deployment with `region:` (`eu`, `us`, `eu-west-1`, any label you use). A rule with `regions: [eu]` reaches only deployments with one of those labels.

- The filter comes before the balance, cooldowns and fallbacks: a deployment outside the regions is never tried, even when every allowed one is failing.
- An alias with no deployment in an allowed region: refused with `region_not_allowed` before anything is sent.
- A model that is not an alias has no region label, so where it runs cannot be shown: refused with `region_not_allowed` under a residency rule.
- A named fallback (`context_window_fallback`, `content_policy_fallback`) is taken only when its own deployments are in an allowed region.
- [Passthrough](/governance/policy/#passthrough) calls go to a provider's own API as sent, with no region: refused under a residency rule.

The record carries `routing.regions` (what the rule allows) and `routing.region` (where the request went first).

<Aside type="caution">
The `region:` label is yours to set. Gantry enforces it exactly; it does not check where a provider runs. Label a deployment with the region of the endpoint and data processing terms you have with that provider.
</Aside>

## Session affinity for coding agents

A coding agent sends many requests in one conversation, and a provider's prompt cache is per deployment. With `session_affinity: true`, a session's requests stay on the deployment its first one went to, while that deployment answers.

The session is read from the first of these headers on the request: `x-gantry-session`, `x-claude-code-session-id` (Claude Code), `session_id` (Codex), `x-session-id`. It is kept per person, hashed, so one person's session ID never pins another's requests.

- The pinned deployment is used while it is not cooling down. When it fails, the session moves to the next deployment the balance picks, and stays there.
- A session idle for an hour is forgotten.
- Without a store, pins are kept per gateway: behind a load balancer without stickiness, a session may be pinned once on each gateway it reaches. With a [store](/operations/store/#session-pins-and-latency), pins are shared: a session pinned on one replica goes to the same deployment on every replica, within about a second.

The record says `session: pinned to <deployment>` when a pin decided.

## The record

Every request to an alias carries `routing` on its decision record:

```json
"routing": {"balance": "lowest_latency", "reason": "lowest_latency: p90 time to first byte 412 ms", "deployment": "azure-eu/gpt-4o", "region": "eu", "regions": ["eu"], "for": "tag:batch"}
```

| Field | Present | Description |
|---|---|---|
| `balance` | always | The alias's balance |
| `reason` | always | Why the first deployment was picked |
| `deployment` | always | The deployment tried first, as `provider/model` |
| `region` | the deployment has a label | Its region |
| `regions` | the rule has `regions` | The regions the rule allows |
| `for` | kept deployments matched | The tag or team that matched, as `tag:<tag>` or `team:<team>` |

Which deployments were actually tried and how each answered is in the [attempts record](/reference/audit-records/#attempts).

## Errors

| Code | Status | Cause |
|---|---|---|
| `region_not_allowed` | 403 | The rule has `regions` and the request has no deployment in one: an alias with none labelled so, a model that is not an alias, or a passthrough call. |
| `tag_not_allowed` | 403 | `x-gantry-tags` holds a tag the rule does not list. |
| `no_deployment` | 403 | Every allowed deployment is kept for another team or tag. |
