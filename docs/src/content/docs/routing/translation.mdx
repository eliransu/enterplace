By default a request reaches only providers that speak its API. Translation is an opt-in per provider: `accept_chat` lets chat completions clients use Claude, and `accept_messages` lets Claude Code and the Anthropic SDKs use any chat model.

| Field | Set on | Takes | Sends |
|---|---|---|---|
| `accept_chat: true` | `anthropic`, `bedrock`, `vertex_anthropic` | `POST /v1/chat/completions` | Messages |
| `accept_messages: true` | a kind that takes chat: `openai`, `azure`, `gemini`, `vertex`, `vertex_openai`, `bedrock_converse`, `cohere`, `watsonx` | `POST /v1/messages` | Chat completions (and on to the provider's own format for the kinds that translate chat) |
| `chat_as_responses: true` | `openai`, `azure` | `POST /v1/chat/completions` | The Responses API |
| none: always on | every kind but `openai` and `azure` | `POST /v1/responses` | Chat completions, and on to messages or the provider's own format |

Without the field, a request on the other route is refused with `wrong_route`. Each changes without a restart. Gemini, Vertex AI, Bedrock Converse, Cohere and watsonx.ai always take chat translated to their own format; how reasoning settings map is on the [providers overview](/providers/overview/#reasoning-across-providers).

## Example

<Tabs>
<TabItem label="accept_chat">

```yaml
providers:
  - name: anthropic
    kind: anthropic
    url: https://api.anthropic.com
    key_env: ANTHROPIC_PROVIDER_KEY
    models: [claude-sonnet-5-5]
    accept_chat: true
```

Cursor, Continue, Aider and the OpenAI SDKs can now ask for `claude-sonnet-5-5`.

</TabItem>
<TabItem label="accept_messages">

```yaml
providers:
  - name: openai
    kind: openai
    url: https://api.openai.com
    key_env: OPENAI_PROVIDER_KEY
    models: [gpt-5, gpt-5-mini]
    accept_messages: true
```

Claude Code can now run with `ANTHROPIC_MODEL=gpt-5` and `ANTHROPIC_SMALL_FAST_MODEL=gpt-5-mini`. See [Claude Code](/integrations/claude-code/).

</TabItem>
</Tabs>

## Nothing is dropped silently

A field that cannot be carried across is refused with `untranslatable`, naming it:

```text
Refused (untranslatable): The parameter "n" set to 2 has no equivalent in Anthropic's messages API, so Enterplace cannot translate it. Remove it, or use a model whose provider speaks the client's format. Decision 01M7....
```

The translation is decided before the record is written, so an untranslatable request is a recorded refusal. The record of a translated request says `"translated": true`. The few fields dropped on purpose are listed with their reasons in `enterplace_core::translate::SAFE_TO_DROP`.

## Chat to messages (accept_chat)

- A whole answer comes back as a `chat.completion`.
- A stream comes back as `chat.completion.chunk` events ending in `data: [DONE]`, with a final usage chunk when the request asked for `stream_options.include_usage`.
- Errors come back in OpenAI's error shape.
- A translated request to an `anthropic` provider carries `anthropic-version: 2023-06-01`.
- `reasoning_effort` `low`, `medium` and `high` become a thinking budget of 1024, 4096 and 16384 tokens; `xhigh` and `max` become `output_config.effort` with adaptive thinking. Claude's readable thinking comes back as `reasoning_content`.
- Dropped on purpose: `seed`, thinking signatures and a few others in `SAFE_TO_DROP`.

## Messages to chat (accept_messages)

**Carried over:** system prompts, images (base64 or URL), tools and tool results, `tool_choice`, `stop_sequences`, `temperature`, `top_p`, `metadata.user_id` (sent as `safety_identifier`; one longer than OpenAI's 64 characters, such as Claude Code's, is sent as its SHA-256) and `output_config.effort` (sent as `reasoning_effort`).

**Whole answers** become a `message`: text and `tool_use` blocks (arguments parsed to `input`), usage, and `stop_reason` from `finish_reason`:

| `finish_reason` | `stop_reason` |
|---|---|
| `stop` | `end_turn` |
| `length` | `max_tokens` |
| `tool_calls` | `tool_use` |
| `content_filter`, or a refusal | `refusal` |

**Streams** become Anthropic's events in the order Claude Code reads them: `message_start`; for each text or tool call `content_block_start`, `content_block_delta` (`text_delta`, or `input_json_delta` for tool arguments) and `content_block_stop`; then `message_delta` with `stop_reason` and usage; then `message_stop`. Enterplace asks the provider for `stream_options.include_usage`, so usage carries the provider's counts. A provider error in the stream becomes an `error` event. A stream cut before `data: [DONE]` is broken off, not ended as if complete.

**Errors** come back in Anthropic's error shape, typed by status (429 is `rate_limit_error`), with the message `Provider "<name>" answered <status>: <the provider's message> Decision <id>.`, the decision ID in `decision`, the provider's own `Retry-After`, and `x-should-retry: true` for 408, 409, 429 and 5xx (`false` otherwise).

**Mapped:** thinking of type `enabled` becomes the `reasoning_effort` its budget stands for (up to 1024 `low`, up to 4096 `medium`, above that `high`); adaptive thinking is let through.

**Refused with `untranslatable`:** thinking of another type, server tools (web search, code execution), `context_management` edits other than clearing thinking, document and other non-text tool result blocks, and any field Enterplace does not know.

**Dropped on purpose:** `cache_control`, thinking blocks, `defer_loading` on tools, `context_management` that only clears thinking, `safeguards` (Claude Code then runs its auto mode classifier itself), and the `anthropic-*` headers.

`POST /v1/messages/count_tokens` for these models is refused with `wrong_route`. It is served for `anthropic`, `bedrock` (Bedrock's CountTokens) and `vertex_anthropic` (Vertex AI's count-tokens endpoint).

<Aside type="caution">
Claude Code sends `output_config.effort` on every request, which Enterplace sends as `reasoning_effort`. A model that is not a reasoning model may refuse that field, and its 400 reaches Claude Code as the provider gave it.
</Aside>

## Responses to chat (Codex on any provider)

A `POST /v1/responses` request for a model on a provider that does not speak Responses is translated to chat completions, then on to messages (`anthropic`, `bedrock`, `vertex_anthropic`) or to the provider's own format (Gemini, Vertex AI, Bedrock Converse, Cohere, watsonx.ai). No opt-in is needed.

**Carried over:** `instructions` (as the system prompt), `input` as a string or as message, `function_call` and `function_call_output` items, text, image and inline file parts, function tools and `tool_choice`, `parallel_tool_calls`, `max_output_tokens`, `temperature`, `top_p`, `reasoning.effort` (mapped as on the overview), `text.format` (`json_schema`, `json_object`), `text.verbosity`, `user`, `safety_identifier`, `metadata`.

**Whole answers** become a `response` object with `output` items: a `reasoning` item for readable reasoning, a `message` item with `output_text`, and a `function_call` item per tool call; `status` is `incomplete` with `incomplete_details.reason: max_output_tokens` when the answer ran out of tokens.

**Streams** become Responses events: `response.created`, `response.in_progress`, then per item `response.output_item.added`, `response.content_part.added`, `response.output_text.delta` (or `response.function_call_arguments.delta`, `response.reasoning_summary_text.delta`), their `.done` events and `response.output_item.done`, and last `response.completed` with the usage. Each event carries its `sequence_number`.

**Refused by name:** `previous_response_id`, `conversation` and `prompt` (state the provider does not keep: send the whole conversation in `input`), `background: true`, tools other than functions (web search, file search, code interpreter, computer use, custom tools), `include` values other than `reasoning.encrypted_content`, file inputs by OpenAI file ID, and any field Enterplace does not know.

**Dropped on purpose:** `store`, `include: reasoning.encrypted_content`, reasoning items handed back in `input`, and the defaults `truncation: disabled` and `service_tier: auto`, listed in `enterplace_core::responses::SAFE_TO_DROP`.

## Chat to Responses (chat_as_responses)

On an `openai` or `azure` provider with `chat_as_responses: true`, a chat completions request is sent to the Responses API (`/v1/responses`, or Azure's `/openai/responses`) and its answer comes back as chat, streamed or whole, usage included. Use it for models served only through Responses. Messages become `input` items, tool calls `function_call` items, tool results `function_call_output` items, `max_tokens` `max_output_tokens`, `reasoning_effort` `reasoning.effort`, and `response_format` `text.format`. The request is sent with `store: false` unless the client set `store`.

## Order on the request path

Guardrails, cache, rate limits and budgets see the request in the form actually sent: translated when it was translated, masked when a guardrail masked it. A cached answer is the provider's own; a translated caller gets the hit translated, as the first answer was. Usage is read from the provider's answer before it is translated, so a translated chat stream sent without `stream_options.include_usage` still has its tokens and cost recorded.

For Gemini and Vertex AI, chat requests are always translated to generateContent; for Bedrock Converse to Converse; for Cohere to its v2 chat; for watsonx.ai to its text/chat. See the provider pages.
