Two kinds reach Amazon Bedrock, both signed with the same AWS credentials:

- `kind: bedrock` serves Claude models through InvokeModel. Claude Code and the Anthropic SDKs call Enterplace's `POST /v1/messages` as usual; Enterplace rewrites the body for InvokeModel, signs it, and streams Bedrock's answer back in Anthropic's format.
- `kind: bedrock_converse` serves every model family Bedrock offers through Converse (Anthropic, Meta Llama, Mistral, Cohere, Amazon Nova, AI21, DeepSeek, Qwen, OpenAI gpt-oss) on the chat completions and Responses routes, and Titan and Cohere embeddings. See [Bedrock Converse](#bedrock-converse).

## Setup

<Steps>

1. Map each model name callers send to a Bedrock model ID, inference profile ID or ARN your account has access to (from the Bedrock console):

    ```yaml title="enterplace.policy.yaml"
    version: 1
    providers:
      - name: bedrock
        kind: bedrock
        region: us-east-1
        models: [claude-sonnet-5-5, claude-haiku-5-5]
        model_ids:                                 # model name: Bedrock model ID
          claude-sonnet-5-5: us.anthropic.claude-sonnet-5-5-v1:0
          claude-haiku-5-5: us.anthropic.claude-haiku-5-5-v1:0
    rules:
      - name: everyone
        principals: { any: true }
        models: [claude-sonnet-5-5, claude-haiku-5-5]
    ```

2. Run Enterplace where it has an AWS role (EKS, ECS or EC2), or give it AWS keys in its environment, and start it:

    ```bash
    enterplace serve enterplace.policy.yaml
    ```

    The start line says which credentials it found, never their value:

    ```text
    enterplace: provider "bedrock" signs with AWS credentials from the container credentials endpoint http://169.254.170.2/v2/credentials/... (the ECS task role or EKS Pod Identity).
    ```

</Steps>

## Credentials

Enterplace looks for AWS credentials in the order of the AWS SDKs' default chain, and the first source that answers is used:

| Order | Source | Set up by |
|---|---|---|
| 1 | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and, for temporary keys, `AWS_SESSION_TOKEN` | You |
| 2 | `AWS_WEB_IDENTITY_TOKEN_FILE` and `AWS_ROLE_ARN`, traded at STS with AssumeRoleWithWebIdentity | IRSA on EKS |
| 3 | `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`, or `AWS_CONTAINER_CREDENTIALS_FULL_URI` with `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE` | The ECS task role; EKS Pod Identity |
| 4 | The EC2 instance metadata service, IMDSv2 | The EC2 instance profile |

Credentials from sources 2 to 4 expire after an hour or a few. Enterplace renews them in the background five minutes before they expire (or halfway through, for shorter ones) and keeps signing with the current ones meanwhile, so no request waits and nothing restarts. A failed renewal is printed and tried again every 30 seconds while the current credentials still hold. When no source answers, Enterplace does not start and names each source it tried and what it answered.

Enterplace makes these calls itself, as documented by AWS. It never runs the `aws` command and reads no AWS config file, so a profile in `~/.aws/config`, including an IAM Identity Center (SSO) profile, is not read. For local use, export the keys of such a profile into the environment first.

The role needs `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` on the models and inference profiles it serves (Converse and ConverseStream are authorized by the same two actions), and `bedrock:CountTokens` for token counts.

### IRSA on EKS

Annotate the service account Enterplace's pods run as with the role. EKS then sets `AWS_ROLE_ARN` and `AWS_WEB_IDENTITY_TOKEN_FILE` in the pod:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: enterplace
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/enterplace-bedrock
```

The role's trust policy allows `sts:AssumeRoleWithWebIdentity` from the cluster's OIDC provider for `system:serviceaccount:<namespace>:enterplace`. EKS Pod Identity works too: it sets the container credentials variables (source 3) instead.

### ECS task role

Give the task definition a `taskRoleArn`. ECS sets `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` in each container:

```hcl
resource "aws_ecs_task_definition" "enterplace" {
  task_role_arn = aws_iam_role.enterplace_task.arn   # may call bedrock:InvokeModel*
  # ...
}
```

The execution role (`execution_role_arn`) is not used for this: it only pulls the image and reads secrets at start.

### EC2 instance profile

Attach an instance profile whose role may call Bedrock. Enterplace asks IMDSv2 for a session token, then for the role's credentials. Set `AWS_EC2_METADATA_DISABLED=true` to skip this source.

### Another role

`role_arn` on the provider makes Enterplace assume that role (STS AssumeRole, signed) with whatever credentials the chain found, for Bedrock in another account:

```yaml
  - name: bedrock
    kind: bedrock
    region: us-east-1
    role_arn: arn:aws:iam::210987654321:role/bedrock-invoker
```

STS is called at `https://sts.<region>.amazonaws.com`, the region being `AWS_REGION` or the provider's. `AWS_ENDPOINT_URL_STS` names another endpoint, such as a VPC endpoint.

## Fields

| Field | Type | Default | Description |
|---|---|---|---|
| `region` | string | required | The AWS region, for example `us-east-1`. Needs a restart to change. |
| `model_ids` | map | required | Model name to Bedrock model ID, inference profile ID or ARN. Every model in `models` needs an entry. |
| `url` | string | `https://bedrock-runtime.<region>.amazonaws.com` | Set it for a VPC endpoint. |
| `role_arn` | string | none | An IAM role to assume with the credentials Enterplace finds. Needs a restart to change. |
| `key_env`, `key_file` | | not allowed | Bedrock is signed with AWS credentials, not a key. |

## What Enterplace sends

A request for `claude-sonnet-5-5` goes to InvokeModel, or InvokeModelWithResponseStream when the body says `"stream": true`:

```text
POST https://bedrock-runtime.us-east-1.amazonaws.com/model/us.anthropic.claude-sonnet-5-5-v1%3A0/invoke
POST https://bedrock-runtime.us-east-1.amazonaws.com/model/us.anthropic.claude-sonnet-5-5-v1%3A0/invoke-with-response-stream
```

The body is changed as Bedrock's Anthropic format requires:

- `model` and `stream` are removed, because the path carries both.
- `anthropic_version: bedrock-2023-05-31` is added.
- The values of the `anthropic-beta` header become the `anthropic_beta` list.

Every other field goes as it came. The request is signed with AWS Signature Version 4 (service `bedrock`), implemented in Enterplace and tested against AWS's published test vectors.

## Answers and errors

Bedrock streams its answer as an AWS event stream. Enterplace checks each message's checksums and turns each `chunk` into the Anthropic server-sent event it holds, so Claude Code and the Anthropic SDKs read it unchanged.

A Bedrock error, streamed or not, reaches the caller in Anthropic's error shape with Bedrock's message:

```json
{"type":"error","error":{"type":"invalid_request_error","message":"Amazon Bedrock ValidationException: ..."}}
```

## Token counts

`POST /v1/messages/count_tokens` goes to Bedrock's CountTokens (`/model/<id>/count-tokens`), with the InvokeModel body base64-encoded as it requires, and Bedrock's count comes back as Anthropic's `{"input_tokens": n}`. Counting is free and recorded.

## Limits

- Betas are passed on as sent. A beta Bedrock does not offer comes back as Bedrock's 400.
- `accept_chat: true` lets chat completions clients reach these models, translated. See [Translation](/routing/translation/).

## Batches

With a `batch:` section naming a bucket, `/v1/files` and `/v1/batches` run as Bedrock batch inference, on files Enterplace keeps in S3, owned, checked, reserved and metered per line like OpenAI batches. See [Bedrock and Vertex AI batches](/providers/batches-and-realtime/#bedrock-and-vertex-ai-batches).
## Bedrock Converse

```yaml title="enterplace.policy.yaml"
providers:
  - name: bedrock
    kind: bedrock_converse
    region: us-east-1
    models: [llama-3.1-70b, nova-pro, mistral-large, gpt-oss-120b, titan-embed]
    model_ids:
      llama-3.1-70b: meta.llama3-1-70b-instruct-v1:0
      nova-pro: amazon.nova-pro-v1:0
      mistral-large: mistral.mistral-large-2407-v1:0
      gpt-oss-120b: openai.gpt-oss-120b-1:0
      titan-embed: amazon.titan-embed-text-v2:0
    accept_messages: true            # Claude Code may use these models too
```

A chat completions request goes to Converse, or ConverseStream when it says `"stream": true`:

```text
POST https://bedrock-runtime.us-east-1.amazonaws.com/model/meta.llama3-1-70b-instruct-v1%3A0/converse
POST https://bedrock-runtime.us-east-1.amazonaws.com/model/meta.llama3-1-70b-instruct-v1%3A0/converse-stream
```

**Carried over:** system and developer messages (as `system`), user text, images (inline base64: png, jpeg, gif, webp) and documents (pdf, csv, txt, html, md), assistant tool calls (as `toolUse`) and tool results (as `toolResult`), function tools (as `toolConfig`) with `tool_choice` `auto`, `required` and a named tool, `max_tokens` or `max_completion_tokens`, `temperature`, `top_p`, `stop`, and `user` (as `requestMetadata.user`, which Bedrock keeps in its invocation logs). `reasoning_effort` becomes `additionalModelRequestFields`: a thinking budget for Claude, `reasoningConfig` for Nova, `reasoning_effort` for gpt-oss; it is refused for families that take none. See [Reasoning across providers](/providers/overview/#reasoning-across-providers).

**Answers** come back as chat completions: text, tool calls, `reasoning_content` from readable `reasoningContent`, the finish reason (`tool_use` is `tool_calls`, `max_tokens` is `length`, `guardrail_intervened` and `content_filtered` are `content_filter`) and usage, cache reads and writes included. A stream's AWS event stream is checked message by message and becomes `chat.completion.chunk` events, with the usage chunk when the client asked for it. Usage is read from Converse's own counts before translation, so a stream without `include_usage` is still metered exactly.

**Refused by name:** an image by URL (Converse takes inline images only), `response_format`, `n` above 1, `logprobs`, `parallel_tool_calls: false`, a tool with `strict`, `tool_choice: none` in a conversation that holds tool calls, a system message after the conversation started, and any field Enterplace does not know.

`POST /v1/responses` reaches these models translated to chat, then to Converse. With `accept_messages: true`, Claude Code reaches them translated to chat, then to Converse.

### Embeddings

`POST /v1/embeddings` for an Amazon Titan Text Embeddings model (`amazon.titan-embed-text-v2:0`, `amazon.titan-embed-text-v1`) or a Cohere Embed model (`cohere.embed-english-v3`, `cohere.embed-multilingual-v3`) goes to InvokeModel with the body that model takes, and comes back as OpenAI's embeddings list:

- Titan embeds one text per request: `input` as a list of more than one is refused, naming the fix. `dimensions` is carried over.
- Cohere takes a list; `input_type` (default `search_document`) and `dimensions` (as `output_dimension`) are carried over.
- Tokens are Titan's `inputTextTokenCount`, or Bedrock's `X-Amzn-Bedrock-Input-Token-Count` header for Cohere.

### Images

`POST /v1/images/generations` for an Amazon Titan Image Generator, Amazon Nova Canvas or Stability AI model goes to InvokeModel with the body that model takes, and comes back as OpenAI's `data` list of `b64_json` images:

- Titan and Nova Canvas: a `TEXT_IMAGE` task; `n` is `numberOfImages`, `size` is `width` and `height`, `quality: hd` is `premium`.
- Stability AI (Stable Image, SD3): one image per request; `size` becomes the nearest `aspect_ratio` the model takes. SDXL 1.0 takes its own older body.
- `response_format: url`, `style` and any field with no equivalent are refused by name, before anything is sent. Each image is charged the model's `per_image` price.

### Rerank

`POST /v1/rerank` (Cohere's shape) for `cohere.rerank-v3-5:0` or `amazon.rerank-v1:0` goes to InvokeModel and comes back as `{"results": [{"index": ..., "relevance_score": ...}]}`. Cohere's model gets `api_version: 2`; `rank_fields` and other fields Bedrock does not take are refused by name.

### Token counts

`POST /v1/messages/count_tokens` for a Converse model goes to Bedrock's CountTokens with the request as a Converse body (`input.converse`), and `inputTokens` comes back as `{"input_tokens": n}`.

### Prices

A model named for callers (`llama-3.1-70b`) is priced as the Bedrock model ID it is called by when the policy sets no price for it, and an inference profile (`us.meta...`) as its model: the LiteLLM price table holds Bedrock's IDs. Set `prices:` in the policy for a model the table lacks.

## Passthrough

`/bedrock/<path>` reaches Bedrock's own API, signed with the provider's AWS credentials, on paths a rule lists under `passthrough:` for the provider, for example `/bedrock/model/amazon.nova-pro-v1:0/converse` or Bedrock batch inference. The model ID in a `/model/<id>/...` path is decided by the rule under the name the policy knows it by, and the call is recorded and metered like any other. With several Bedrock providers, name one in `x-enterplace-provider`. A streamed answer (`invoke-with-response-stream`, `converse-stream`) is passed on as Bedrock's event stream, unchanged, and charged the usage its events report: the Anthropic `message_start` and `message_delta` counts inside InvokeModel's `chunk` events, or ConverseStream's `metadata` event. See [Passthrough](/governance/policy/#passthrough).

## The AWS SDKs

boto3 and the other AWS SDKs reach Enterplace on the Bedrock runtime's own routes: `/model/<id>/converse`, `/converse-stream`, `/invoke`, `/invoke-with-response-stream` and `/count-tokens`. Point the SDK at Enterplace and give it the Enterplace key as its Bedrock API key:

```bash
export AWS_ENDPOINT_URL_BEDROCK_RUNTIME=http://127.0.0.1:8080
export AWS_BEARER_TOKEN_BEDROCK=enterplace_...
```

The SDK sends the key as a Bearer token. An SDK that signs with AWS credentials can send the Enterplace key in `x-api-key` instead; its signature is removed, since Enterplace cannot check it, and Enterplace signs the request to Bedrock with the provider's own credentials. The model in the path is the Bedrock model ID or the name the policy gives it, decided by the caller's rule as on any model route, and no `passthrough:` entry is needed. The body and answer pass as Bedrock's own, streams included, metered like passthrough. A refusal comes back in the shape the SDKs read: `message`, the exception's name in `x-amzn-errortype` (`AccessDeniedException`, `ValidationException`, `ThrottlingException`), and Enterplace's code in `enterplace_code`.

## Errors from enterplace check

```text
enterplace.policy.yaml:26: a bedrock provider takes no key_env. Enterplace signs its requests with the AWS credentials it finds: the role of its pod, task or instance, or AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY in its environment. Remove the line.
```

A provider without `region` or `model_ids` is refused the same way, naming the missing field.
