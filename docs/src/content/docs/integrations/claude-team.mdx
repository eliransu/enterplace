Claude Code on Claude Team or Enterprise seats comes under Gantry in one of two ways:

- **Through Gantry, on the seats' own logins** (recommended). Claude Code keeps its Claude login, sends its requests to your gateway, and Gantry passes the login on to Anthropic unchanged. Rules, guardrails, kill switches and token limits apply; nobody needs an API key. See [Claude Code](/integrations/claude-code/#claude-subscriptions) and [Subscriptions](/governance/subscriptions/).
- **Watch mode**, below, when nothing may be routed. Claude Code sends its own usage telemetry (OpenTelemetry) to your Gantry gateway, and Gantry records who used it, with which models, how many tokens, at what estimated cost, and which tools ran or were rejected. It enforces nothing.

Both can run at once: the same managed settings block can hold the two lines of subscription passthrough and the telemetry lines.

Watch mode is part of Gantry Enterprise (license feature `watch`) and runs in your own gateway. It needs a [store](/operations/store/). Nothing is sent to Gantry the company, and Claude Code sends this telemetry only to the address you set.

## What watch mode can and cannot do

| | Watch mode | Requests through Gantry (subscription or API key) |
|---|---|---|
| Who used Claude Code, when, on which model | Yes | Yes |
| Tokens by type and estimated cost, per person, team and model | Yes, as Claude Code reports them | Yes, from the provider's answer |
| Tool calls accepted, rejected and failed, by tool | Yes | Tool calls in requests and answers |
| Lines changed, commits, pull requests, sessions, active time | Yes | No |
| The request log, analytics, `/admin/usage`, coverage, alerts, SIEM export, retention | Yes, as source `watch` | Yes |
| Block a model, a person or a request | No | Yes |
| Budgets, rate limits, kill switches | No | Yes. On subscriptions, limits are in tokens and requests ([Subscriptions](/governance/subscriptions/)) |
| Guardrails on prompts and answers | No | Yes |
| Prompt and answer text | Never kept | Only with `capture:` |

Watch mode observes. Claude Code talks to Anthropic directly, so Gantry cannot refuse or change anything. In the [five steps](/start/plan/), See, Know and Prove work on watch data; Limit and Protect need API traffic through Gantry. To enforce policy, [route Claude Code through Gantry](/integrations/claude-code/#claude-subscriptions) on the same seats: no API key is needed.

<Aside type="note">
Costs in watch mode are Claude Code's own estimates at list price. Usage within Team or Enterprise seats is not billed per dollar, so read them as relative usage, not an invoice.
</Aside>

## Set it up

<Steps>

1. Start the gateway with a license that has `watch` and a policy with `store:`. See [License](/operations/license/).

2. Create a watch token and print the settings. `--gateway` is the address Claude Code reaches your gateway at:

   ```sh
   export GANTRY_ADMIN_KEY=gantry_...
   gantry watch setup --gateway https://gantry.example.com --team engineering
   ```

   It prints a managed settings block with the token in it. The token is shown once: Gantry keeps its hash.

   ```json title="Managed settings"
   {
     "env": {
       "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
       "OTEL_METRICS_EXPORTER": "otlp",
       "OTEL_LOGS_EXPORTER": "otlp",
       "OTEL_EXPORTER_OTLP_PROTOCOL": "http/protobuf",
       "OTEL_EXPORTER_OTLP_ENDPOINT": "https://gantry.example.com/otlp",
       "OTEL_EXPORTER_OTLP_HEADERS": "Authorization=Bearer gantry_watch_..."
     }
   }
   ```

3. Apply the block for your plan, as below.

4. Within a few minutes of each developer's next Claude Code session, they appear:

   ```sh
   curl -H "Authorization: Bearer $GANTRY_ADMIN_KEY" https://gantry.example.com/console/watch/summary.json
   ```

</Steps>

## Where watched people show up

| Where | What |
|---|---|
| **Requests** (`/console/requests?source=watch`) | One row per model request Claude Code reported: person, team, model, tokens, estimated cost, latency. API errors and refusals are rows too |
| **Analytics** (`/console/analytics`) | Rank by **Source** to compare watched and routed usage, or filter `source=watch` and rank by person, team or model |
| [`/admin/usage`](/reference/admin-api/) | `?source=watch`, or `group_by=source` |
| [`gantry audit coverage`](/governance/coverage/) | Tool `claude-code (watch)` per person, beside the tools that reach Gantry |
| [Alerts](/operations/alerting/) | `budget` rules by amount and `unusual_spend` count watched cost |
| [Audit export](/operations/siem-export/) and [retention](/operations/retention/) | `watch` records ship and expire as every audit record does |
| The [daily digest](/operations/alerting/) | Watched cost is part of the spend and of the top users, and a `Watched:` line says how much of the spend it was |
| `GET /console/watch/summary.json?days=30` | Sums per person, model and tool: sessions, tokens by type, cost, lines, commits, pull requests, prompts, tool calls accepted, rejected and failed, who is not a known member, and where the five steps stand |

Watched requests never count against a budget and are never refused: Gantry did not forward them.

## What is kept

Each model request, API error, refusal, tool decision, tool result and prompt Claude Code reports becomes one [`watch` record](/reference/audit-records/#watch) in the audit chain. Its metrics (sessions, tokens, cost, lines, commits, pull requests, edit decisions, active time) are summed per day, person, model and tool in the store, and each export's new sums are one record too. An export sent twice is counted once.

Gantry keeps numbers and names: person, team, session, model, tokens, estimated cost, tool name, decision, error name, prompt length. It never keeps prompt, answer or tool text. If someone turns on `OTEL_LOG_USER_PROMPTS` or `OTEL_LOG_TOOL_DETAILS` in Claude Code, Gantry drops that text when it arrives and counts the event under `content_dropped`. Every other event Claude Code sends (plugins, hooks, settings) is dropped.

## One name per person

On a team token the person is the email address Claude Code reports. Gantry gives it the name that person's gateway traffic has, so both are one person on the Requests and Analytics pages, in `/admin/usage`, in coverage and in alerts:

| The email is | The person is |
|---|---|
| The `email` in a key's [`metadata`](/governance/keys/), such as `metadata: { email: maya.cohen@example.com }` on the key of `maya.cohen` | That key's name. The record keeps the reported address in `email` |
| A key's name, as [`gantry login`](/governance/teams/) names keys | That key's name |
| An owner or member of a team in the policy's [`teams:`](/governance/teams/), or a person in **Members** (invited, or provisioned by SCIM) | The email, which is the name a key issued to them at sign-in gets |
| None of these | The email, listed in `summary.json` under `not_known_members`, with `"known": false` on the person |

Letter case does not matter. The lookup is made when an export arrives, so a key added later names what arrives from then on; what was already recorded keeps the name it had. A token of one person (`--person`) names that person whatever Claude Code reports.

The daily sums follow the [retention](/operations/retention/) period and legal hold, 365 days on an install without the retention feature.

## Tokens

A watch token starts with `gantry_watch_`, lasts 1 to 365 days (90 unless `--days` says otherwise) and belongs to a team or to one person. Owners and admins create and revoke them, with an admin key or signed in to the console; a viewer can list them and read the summary. Every change is an [admin record](/reference/audit-records/#admin), a refused one with its code.

In an install with organizations (`orgs:` in the policy), `"org": "acme"` (`gantry watch setup --org acme`) makes a token that organization's: its records carry `org`, and with [`audit: { per_org: true }`](/governance/audit-log/) they go to that organization's chain. The organization must be one the policy lists under `orgs:`. Someone whose role is kept to one organization creates, lists and revokes that organization's tokens only.

A [role](/governance/access-control/) kept to teams (`teams:`) reaches the watch tokens of those teams only, with an admin key as with a console session. Such a role cannot create a token without a team, since that token would cover every team: the answer is `403` with `outside_role`. A token outside the role is not listed, and revoking it answers `404`. A role kept to `customers:` reaches no watch token.

`summary.json` follows the same reach: a role kept to an organization or to teams is given the people, models, tools and sums that came in with tokens of that organization and those teams, and nothing else. Sums watched before this release belong to no organization, so only an admin of the whole install (or a role kept to teams alone) reads them.

```sh
# List: label, team or person, expiry, last export, status
curl -H "Authorization: Bearer $GANTRY_ADMIN_KEY" https://gantry.example.com/console/watch/tokens
# Create
curl -X POST -H "Authorization: Bearer $GANTRY_ADMIN_KEY" https://gantry.example.com/console/watch/tokens \
  -d '{"label": "claude-team", "team": "engineering", "days": 90}'
# Revoke: exports with it are refused from then on
curl -X DELETE -H "Authorization: Bearer $GANTRY_ADMIN_KEY" https://gantry.example.com/console/watch/tokens/wt-1a2b3c4d
```

Replace a token before it expires: create a new one, put its settings in place of the old, then revoke the old.

## The receiver

| | |
|---|---|
| Routes | `POST /otlp/v1/metrics`, `POST /otlp/v1/logs` on the gateway's address |
| Encoding | OTLP over HTTP as protobuf (`http/protobuf`) or JSON (`http/json`), at most 4 MB an export |
| Compression | None, or gzip (`Content-Encoding: gzip`, which Claude Code sends with `OTEL_EXPORTER_OTLP_COMPRESSION=gzip`). The 4 MB limit is counted on the unpacked export |
| Not supported | OTLP over gRPC, and traces (`/otlp/v1/traces`, Claude Code's `OTEL_TRACES_EXPORTER`): leave the traces exporter unset |
| Sign-in | `Authorization: Bearer gantry_watch_...` |
| Claude Code | Tested with 2.1.325 |

| Status | Code | When |
|---|---|---|
| 401 | `invalid_token` | No token, an unknown one or a revoked one |
| 401 | `token_expired` | The token's days are over |
| 403 | `license_required` | The license does not have `watch` |
| 415 | `unsupported_protocol`, `unsupported_encoding` | gRPC or another content type; a compression other than gzip |
| 413 | `too_large` | More than 4 MB, as sent or once unpacked |
| 400 | `invalid_export` | Not an OTLP export, or marked gzip and not readable as gzip |
| 503 | `store_unavailable`, `audit_unavailable` | Nothing was kept; Claude Code sends the export again |

If nothing arrives, run `claude --debug-file /tmp/claude-debug.log` and search the file for `[3P telemetry]`: Claude Code logs its export errors there.

## Limits

- The console's **Watch** page shows the watched people; `summary.json`, the Requests and Analytics pages and coverage hold the rest.
- No gRPC and no traces: see [the receiver](#the-receiver).
- Metrics need `session.id` on each point, which Claude Code sends unless `OTEL_METRICS_INCLUDE_SESSION_ID=false`.
- A token without `org` writes to the install's chain, also with `audit: { per_org: true }`.
