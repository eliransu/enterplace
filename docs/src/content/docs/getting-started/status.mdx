Gantry is at version **{current[1]}**{current[2] === 'Unreleased' ? ', not yet released as a tag' : `, released ${current[2]}`}. See the [changelog](/getting-started/changelog/). It is pre-1.0. It runs as one node, or as several replicas sharing a Postgres store. This page is the one place that says what the binary does, what is planned, and how each integration was verified. Anything marked planned does not exist in the binary.

## Built and planned

| Area | Built | Planned |
|---|---|---|
| Identity | Gantry keys per person and workload (`gantry key new`, the admin API, the console), each with an optional expiry, budget, model list and tokens-per-minute limit. The first admin is made with `gantry key new --admin`. `gantry login` and `gantry logout` give a developer their own expiring key through OpenID Connect or SAML single sign-on, in the team the identity provider's groups name. JWTs from trusted issuers (`jwt:`), on the gateway and the admin API (`role_claim`). Console sign-in through OpenID Connect or SAML 2.0. Teams with owners and members (`teams:`, `/admin/teams`), and console roles kept to teams or customers. Gantry Enterprise: members with roles, and SCIM 2.0 provisioning from Okta and Microsoft Entra ID. | Two-step sign-in (TOTP) in Gantry Enterprise. |
| Policy | A policy file of rules by team, person or anyone, checked by `gantry check`. Kill switches with a reason (`gantry kill`, `gantry unkill`). Policy and keys reload without a restart, within 2 seconds. With a store: saved versions, a second admin's approval, a dry run over every replica's recent requests and one-click rollback. Observe mode. | |
| Guardrails | Built-in secrets and personal data detectors, with Gitleaks' rule set as the `gitleaks` pack, thirteen guardrail vendors, and outside services by webhook. On requests and on answers: whole answers always, streamed answers when the rule sets `buffer_stream: true`. Function tool permissions in requests and answers (refused or stripped), tool call arguments read by answer guardrails, MCP tools narrowed per key and per header, transforms that rewrite requests and answers, and guardrails on realtime sessions. | |
| Spend | Usage and cost of every answer, with prices built in for most models (`gantry prices`). Budgets per organization, team, person, key, customer, tag or model, shared by every replica on one Postgres store. Requests and tokens per minute and requests in flight, shared by every replica on the store. A cache per rule, per person or team, exact or semantic, with automatic Anthropic prompt caching and savings per team. Gantry Enterprise: alerts on budgets (by amount or percent), errors and guardrail blocks, per organization. | The cache shared across replicas (each replica keeps its own). |
| Chat completions | `POST /v1/chat/completions` to OpenAI-compatible providers, Azure OpenAI (key or Microsoft Entra ID, deployment paths or the v1 API) included, and translated to Gemini, Vertex AI, Amazon Bedrock Converse, Cohere, IBM watsonx.ai and Replicate. | Messages | `POST /v1/messages` and `/v1/messages/count_tokens` to providers that speak Anthropic's messages API. `/v1/messages` to Claude on Amazon Bedrock and Claude on Vertex AI (`vertex_anthropic`). Claude Code's messages requests translated to chat completions for a provider with `accept_messages: true`. | `count_tokens` for Bedrock, Vertex AI and translated models |
| Other routes | `GET /v1/models` (Anthropic's list for Claude Code, OpenAI's list for other callers). Images, audio transcription and speech, moderations, rerank and legacy completions to OpenAI-compatible providers. Image edits and variations. Videos (Sora, Veo) and code interpreter containers, owned by their creator and priced per second or per session. Async jobs (`/v1/async/<route>`). Signed passthrough to Bedrock and Vertex AI (`/bedrock/`, `/vertex/`, `/passthrough/<provider>/`). Files, batches, fine-tuning jobs and message batches, owned and metered per line at batch prices, and batches run as Bedrock batch inference (S3) and Vertex AI batch prediction (Cloud Storage) jobs. OpenAI Realtime and Gemini Live sessions. | |
| Routing | Retries and fallbacks per provider, followed hop by hop. Model aliases over several deployments: round robin by weight, least busy, lowest latency, lowest cost or adaptive; a circuit breaker per deployment; conditional routing (team, tag, customer, prompt size, tools, images, a header); session affinity; residency by region; rate-limit-aware routing; `max_parallel`, `rpm` and `tpm` per deployment. Alias fallbacks on the failures `fallback_on` names, across APIs, and a request's own `fallbacks` for models its rule allows. Timeouts per provider, alias and deployment, with `gantry check` printing each alias's worst-case wait. Health probes, recorded as `gantry-probe`, one replica probing each deployment. Key pools with weights. Per-provider headers and HTTP proxy. Wildcard models. With a store, cooldowns, session pins, latency and deployment limits are shared by every replica. | |
| Audit and observability | A hash-chained audit log and `gantry audit verify`, with Vector, Fluent Bit and OpenTelemetry Collector examples for shipping it, and a chain per organization (`audit: { per_org: true }`). `gantry audit coverage`: requests per person and coding tool, merged with device reports (`--devices`). A Helm chart (with autoscaling and a disruption budget) and plain Kubernetes manifests. Several replicas sharing keys, kill switches, budgets, rate limits, routing state and sessions through a Postgres store (`store:`), with rolling upgrades across versions. Signed images with an SBOM and provenance ([Verify a release](/operations/verify-release/)). Gantry Enterprise: one image, Docker Compose, a Helm chart for one or more replicas sharing a Postgres store, and Terraform modules for AWS (ECS, RDS, EFS), Google Cloud (Cloud Run, Cloud SQL, Filestore) and Azure (Container Apps, Azure Database for PostgreSQL, Azure Files), with a [guide for each](/deploy/overview/). | Certificate reload without a restart. More than one replica on Cloud Run and Container Apps. |

## Verification

**Run against real clients.** The OpenAI and Anthropic APIs were exercised live against mock servers, with the real Claude Code CLI and Codex CLI as clients:

- Claude Code 2.1.323, on the messages route and translated to a mock OpenAI chat server: a prompt, a Bash tool call and its result, streamed.
- Codex CLI 0.166.0 (`codex exec`) through the Responses route to a mock of the Responses API: answers, token counts, records and refusals.
- OpenCode 1.19.5 (`opencode run`) to a mock of the chat completions API: an answer, a `model_not_allowed` refusal and an `unknown_key` refusal, each recorded.
- Qwen Code 0.27.3 (`qwen -p`), GitHub Copilot CLI with a BYOK provider (`copilot -p`, `COPILOT_OFFLINE=true`) and Kilo CLI 7.8.27 (`kilo run`) to a mock of the chat completions API: an answer each, recorded with the tool's user agent.
- Gemini CLI 0.68.0 (`gemini -p`) on Google's Gemini API route to a mock of the Gemini API: an answer and a `model_not_allowed` refusal, each recorded with the tool's user agent.
- Claude Code 2.1.325 with telemetry on, exporting to a local receiver as OTLP JSON and protobuf, its model call answered by a local mock: the captured exports are the [watch mode](/integrations/claude-team/) test fixtures. Server-managed settings on a Claude Team or Enterprise organization were not exercised.

None of these ran against the real OpenAI or Anthropic service.

**Live provider matrix.** `scripts/live_matrix.py` runs every route against each real provider kind (OpenAI, Anthropic, Azure OpenAI, Bedrock, Gemini, Vertex AI, Groq, Mistral) every night, with a token cap per run. Until the provider keys are set, each cell is skipped. The [latest run](/providers/live-matrix/) is published per route and provider.

**Configured from public docs, tested against local mocks only.** These were built from each vendor's public documentation and tested against local mock servers. They have not been run against the real services.

| Integration | Verified by |
|---|---|
| Azure OpenAI | Local mocks |
| Amazon Bedrock | Local mocks with recorded fixtures of the documented format. Request signing tested against AWS's published Signature Version 4 test vectors. |
| Gemini, Vertex AI, Claude on Vertex AI | Local mocks |
| OpenAI-compatible vendors (Groq, Mistral, Together, Fireworks, DeepSeek, OpenRouter, Ollama, vLLM, LM Studio) | Each base URL checked against the vendor's docs; `gantry check` and `gantry serve` run on each example; the path Gantry calls confirmed against a local mock |
| Cursor, Continue, Cline, Aider, Roo Code, Zed, JetBrains AI Assistant, Claude Desktop, Claude for Office, LibreChat, Open WebUI, Copilot in VS Code and the Copilot app | Guides written from each tool's docs, not run through Gantry |
| OpenAI and Anthropic SDKs (Python, TypeScript) | Guides written from each SDK's docs and published source. The refusal bodies they parse were checked against a running Gantry with `curl`. |

**Build.** A CI workflow is defined in `.github/workflows/ci.yml` and runs `scripts/ci.sh`: format, clippy with warnings as errors, every test, the release build, every policy example through `gantry check`, the bench gate and the docs build. It has not yet run on a hosted CI service; `scripts/ci.sh` passes on a developer machine. The container image runs as user `65532` and passes `scripts/smoke_image.py`.

## Known limits

- One caller's requests in flight may hold at most 64 MiB of request bodies.
- The decision record says what Gantry decided, not how the provider answered. A usage record with the status, tokens and cost follows when the answer ends, and an `attempts` record when a request was tried more than once.
- A request that the HTTP library (hyper) rejects as malformed gets a bare 400 with no decision ID.
- Gantry serves plain HTTP unless started with `--tls-cert` and `--tls-key`. Use those, or put TLS in front of Gantry, before traffic leaves one machine.
