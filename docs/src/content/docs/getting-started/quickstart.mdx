One command starts Gantry with a provider key: every request gets an identity, a policy decision and a hash-chained audit record. You need Docker and a key for one provider (OpenAI in this guide). To run it in your cloud with Postgres instead, use a [one-click deploy](/deploy/one-click/): a few clicks on Render, Railway, Fly.io, DigitalOcean, Cloud Run, AWS or Azure.

## Run the image

```bash
docker run --name gantry -p 8080:8080 -v gantry-data:/var/lib/gantry -e OPENAI_API_KEY=sk-... ghcr.io/eliransu/gantry
```

The image is public: no login. The first start writes a policy in observe mode (every key may use every model, nothing is blocked, every request is recorded) and an admin key to the `gantry-data` volume, then serves on `http://localhost:8080`. It prints the admin key once, with the settings for Claude Code, Codex, Cursor and the OpenAI SDKs:

```text
Wrote /var/lib/gantry/gantry.policy.yaml: observe mode and one rule that lets every key use every model of openai. Nothing is blocked, and every request is recorded.

Admin key, shown once and kept nowhere (only its hash is in /var/lib/gantry/gantry.keys.yaml):

  export GANTRY_KEY=gantry_3f9c...

The same key signs in to the console at http://localhost:8080/console.
```

`ANTHROPIC_API_KEY` and `GEMINI_API_KEY` work the same way, alone or together. Later starts on the same volume serve that policy and keys and print no new key.

<Aside type="caution">
The admin key stays in the container's log until the container is removed. Copy it to your password manager, then read it back with `docker logs gantry 2>&1 | grep GANTRY_KEY` only if you lost it.
</Aside>

## Send a request

In a second terminal, export the key the container printed and call the OpenAI API through Gantry:

```bash
export GANTRY_KEY=gantry_...
curl http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer $GANTRY_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"Say hello."}]}'
```

The answer is the provider's, unchanged, with an `X-Gantry-Decision` header added. Open `http://localhost:8080/console` and sign in with the same key to see the request.

## Verify the audit log

The audit log is `/var/lib/gantry/gantry-audit.jsonl`, on the `gantry-data` volume beside the policy and the keys file. Check its chain with the image's own binary:

```bash
docker exec gantry /gantry audit verify /var/lib/gantry/gantry-audit.jsonl
```

```text
/var/lib/gantry/gantry-audit.jsonl: 3 records in an unbroken chain from record 1 to record 3.
1 request, 1 configuration record, 0 admin records, 1 usage record.
Last hash: 9be869bf...
```

Stop the gateway with Ctrl-C and start it again with `docker start -a gantry`. See [Audit log](/governance/audit-log/).

## With Postgres: Docker Compose

For a team, keys, kill switches and budgets live in Postgres, so they are shared and survive the container. The [Docker Compose](/deploy/docker/) guide holds the two files: `docker-compose.yml` (the gateway and Postgres 16) and `.env`. Save both in an empty folder, fill in `.env`, then:

```bash
docker compose up -d
docker compose logs gantry | grep 'First run'
```

The second line prints a one-time link that makes the first admin key in the console. The guide goes on to issue keys and verify the audit log.

## From source

You need Rust 1.88 or later. The repository pins it in `rust-toolchain.toml`, so `rustup` installs it on the first build.

```bash
git clone https://github.com/eliransu/gantry.git
cd gantry
cargo build --release
OPENAI_API_KEY=sk-... target/release/gantry start
```

`gantry start` does what the image does, in the current folder: it writes `gantry.policy.yaml` and `gantry.keys.yaml`, prints the admin key and serves on `http://127.0.0.1:8080`. The audit log is `gantry-audit.jsonl` beside the policy: `target/release/gantry audit verify gantry-audit.jsonl` checks it. This binary is the open source edition (Apache 2.0). The image runs the enterprise build, which without a license key is the same open source gateway.
