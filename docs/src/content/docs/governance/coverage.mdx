`gantry audit coverage` reads the audit log and counts requests per person and coding tool, with refusals and the last time each was seen. With the keys file, it also lists every person who holds a key and has sent nothing.

```bash
gantry audit coverage /var/lib/gantry/gantry-audit.jsonl --keys gantry.keys.yaml
```

```text
person	team	tool	requests	refused	last_seen
ana	dev	claude-code	2	0	2026-11-14T06:13:19.949Z
ana	dev	kilo-code	1	0	2026-11-14T06:13:07.391Z
ana	dev	qwen-code	2	0	2026-11-14T06:12:24.509Z
ana	dev	OpenAI/JS	1	0	2026-11-14T06:12:53.397Z
cara	dev	-	0	0	never
unknown	-	gemini-cli	1	1	2026-11-14T06:12:33.309Z
```

The output is tab-separated, one row per person and tool. It reads sealed segments too.

## How the tool is named

Every request record holds the caller's `user-agent` header as `user_agent`, cut to 200 characters. The report names the tool from it:

| User agent contains | Tool |
|---|---|
| `claude-cli` | `claude-code` |
| `codex` | `codex` |
| `GeminiCLI` | `gemini-cli` |
| `QwenCode` | `qwen-code` |
| `Kilo-Code` | `kilo-code` |
| `copilot` | `github-copilot` |
| `cursor`, `roo-code`, `cline`, `opencode` | that tool |

Matching ignores case. Any other user agent is shown by its first product without the version (`OpenAI/JS 5.20.1` is `OpenAI/JS`), and a request with none as `unknown`. The first four user agents above were seen from the real tools; the rest are matched by name.

## Reading the report

| Row | Means |
|---|---|
| A tool with requests | That person's tool reached Gantry with their key |
| A tool with only refusals | It reaches Gantry but is not allowed, or is misconfigured. Gemini CLI shows this way, refused with `no_key` |
| `unknown` person | Requests with no key Gantry knows: a tool configured with a wrong or missing key |
| Tool `-`, last seen `never` | The person holds a key and has sent nothing: their tools call providers directly, or they do not use AI tools |
| `OpenAI/JS`, `OpenAI/Python` and similar | A tool or script that sends its SDK's user agent |

<Aside type="caution">
The audit log shows what reached Gantry. It cannot show a tool that calls a provider directly. A person who uses Gantry from one tool and a provider key in another shows up as covered, until their devices report (below).
</Aside>

MCP calls (`/mcp`) carry `user_agent` too, so an MCP client counts under its tool.

## Devices: tools that bypass Gantry

The device agent of Gantry Enterprise (`gantry device`, license feature `devices`) reads each coding tool's documented configuration on every enrolled machine and reports one state per tool: `not_installed`, `installed`, `gantry` (pointed at the gateway) or `direct` (pointed at a provider, or holding a provider key or login). See [Devices](/operations/devices/) for enrolment and what is read for each tool. The agent runs on macOS, Linux and Windows, and each report also lists the MCP servers configured in Claude Desktop, Claude Code, Cursor, VS Code and Zed, and whether each goes through Gantry's MCP gateway.

The console's **Devices** page merges those reports with every replica's traffic (the store's request index), per person: the tools their traffic came from, their enrolled devices, and each tool going direct, as `codex on mbp-ana`. Its **Download devices.json** link gives the reports to the command line:

```bash
gantry audit coverage /var/lib/gantry/gantry-audit.jsonl --keys gantry.keys.yaml --devices devices.json
```

```text
person	team	tool	requests	refused	last_seen	devices	direct
ana	dev	claude-code	2	0	2026-11-14T06:13:19.949Z	1	0
ana	dev	codex	0	0	never	2	1
dan	web	-	0	0	never	1	0
```

| Column | Means |
|---|---|
| `devices` | The person's enrolled devices with the tool installed. For tool `-`, every enrolled device of theirs, none with a tool |
| `direct` | Of those, the devices where the tool is configured to call a provider directly |

A tool with requests and `direct` 0 is covered. A tool with `direct` above 0 reaches a provider from at least one device, whatever its traffic says. A row with 0 requests and `devices` above 0 is installed and has never reached Gantry.

Devices are matched to people by the Gantry key `gantry login` saved on the machine: the agent sends it, and the gateway takes the person from the key. A device whose user never ran `gantry login` is refused until someone does.
