Gantry serves the tools, prompts and resources of your upstream MCP servers at one endpoint, `/mcp`, and chosen tools of several servers at `/mcp/<bundle>`. A caller connects with their Gantry key or signs in with OAuth, sees only what their rule allows, and every `tools/call`, `prompts/get` and `resources/read` is checked against the rule and written to the audit log before it reaches a server. Tool calls also pass the rule's guardrails, can wait for an admin's approval, and are refused while a tool's description has changed and not been approved.

## Policy

List the servers under `mcp:` and give each rule a `tools:` list.

```yaml title="gantry.policy.yaml"
version: 1
providers:
  - name: anthropic
    kind: anthropic
    url: https://api.anthropic.com
    key_env: ANTHROPIC_PROVIDER_KEY
    models: [claude-sonnet-5-5]
mcp:
  - name: github
    url: https://api.githubcopilot.com/mcp
    headers_env: { Authorization: GITHUB_MCP_AUTHORIZATION }
  - name: docs
    url: http://127.0.0.1:9000/mcp
    allow_private: true
rules:
  - name: payments-team
    principals: { team: payments }
    models: [claude-sonnet-5-5]
    tools: [github.create_issue, github.list_issues, docs.*]
  - name: everyone-else
    principals: { any: true }
    models: [claude-sonnet-5-5]
```

### Servers

| Field | Required | Meaning |
|---|---|---|
| `name` | yes | Letters, digits, `-` and `_`, no dot. Callers see the server's tools as `<name>.<tool>`. |
| `url` | yes, unless `transport: stdio` | The server's MCP endpoint, for example `https://mcp.example.com/mcp`. With `transport: sse`, the address of its event stream. |
| `transport` | no | `http` (Streamable HTTP, the default), `sse` (the older HTTP+SSE transport) or `stdio` (a process the gateway starts). See [Transports](#transports). |
| `command`, `args`, `env` | with `transport: stdio` | The absolute path of the program to start, its arguments, and its environment as `{ <the process's variable>: <the gateway's variable> }`. |
| `call_price_usd` | no | What one call of any tool of the server costs, in US dollars. See [Tool prices](#tool-prices). |
| `tool_prices` | no | The price of single tools, by the server's own names: `{ create_issue: 0.01 }`. A tool not named here costs `call_price_usd`. |
| `headers_env` | no | Headers sent with every request to the server, each taken from an environment variable: `{ Authorization: GITHUB_MCP_AUTHORIZATION }`. The variable holds the whole header value, `Bearer ...` included. The value never goes in the file. |
| `allow_private` | no | Allow a url on this machine or a private network, as for providers. |
| `user_auth` | no | `headers` or `oauth`: every call runs with the caller's own credential instead of a shared one. See [Each person's own credential](#each-persons-own-credential). `token_exchange` or `on_behalf_of`: Gantry trades the caller's token for the server's. See [Token exchange](#token-exchange). |
| `token_url`, `audience`, `resource` | with `token_exchange` or `on_behalf_of` | The identity provider's token endpoint, and the audience and resource the traded token is asked for. |
| `user_headers` | no | With `user_auth: headers`, the headers each person gives. Default `[Authorization]`. |
| `oauth_scopes` | no | With `user_auth: oauth`, the scopes Gantry asks the server's authorization server for. |
| `oauth_client_id`, `oauth_client_secret_env` | no | With `user_auth: oauth`, a client registered by hand. Without them Gantry registers itself (dynamic client registration). The secret is read from the variable. |
| `tool_changes` | no | `record` (the default) records a tool whose description or schema changed and serves it; `block` records it and holds it until an admin approves it. See [Tool pins](#tool-pins-and-changed-tools). |

The variables are read when Gantry starts, and Gantry does not start when one is unset.

Servers change without a restart, like the rest of the policy: within 2 seconds of a saved policy file, at once on `SIGHUP`, or after `PUT` and `DELETE /admin/mcp/<name>` when the policy is kept in the store. A server reached as before keeps the sessions Gantry holds at it. A new server, or one whose address, transport, credential or price changed, is connected on its next call. A removed server serves nothing from the next request on, and a stdio server's process is stopped. A reload that names an unset variable, or a stdio command the gateway may not start, is rejected and the version in use stays, as for any policy that does not load. `/mcp` is served whenever Gantry runs with a policy, so the first server can be added the same way.

### Tools, prompts and resources in a rule

| Entry | Allows |
|---|---|
| `github.create_issue` | That one tool |
| `docs.*` | Every tool of server `docs`, including tools it adds later |
| `*` | Every tool of every server. List it alone, or beside deny entries |
| `!github.delete_repo` | Denies that tool, whatever else allows it |

`prompts:` and `resources:` take the same entries. A prompt is named `<server>.<prompt>`; a resource is allowed as `<server>.<uri>` with the server's own URI, for example `docs.file:///handbook.md`. A resource template is listed only under `<server>.*` or `*`, since one URI named exactly does not open every path a template reaches.

| Rule field | Meaning |
|---|---|
| `tools` | Tools the rule allows |
| `prompts` | Prompts the rule allows |
| `resources` | Resources the rule allows |
| `approve_tools` | Tools, in the same entries, whose calls wait for an admin to approve them. See [Approvals](#approvals) |
| `approval_timeout_seconds` | How long such a call waits before it is refused, from 10 to 3600. Default 300 |
| `mcp_clients` | The MCP client applications that may use the gateway under this rule. See [Client allowlist](#client-allowlist) |

A key's `mcp_tools` and a request's `x-gantry-mcp-tools` header narrow these further, never widen them: see [Tool permissions](/governance/tool-permissions/#mcp-tools-per-key-and-per-request). The same `tools:` list also decides the function tools a model request declares, written `function.<name>`.

A rule with no `tools:` allows no MCP tool, and the same for prompts and resources. As for models, the first rule that names the caller decides: in the example `everyone-else` can use the model and no tool.

`gantry check` names every mistake with its file and line: a tool, prompt or resource on a server that is not defined, one without a server, a server name with a dot, a private url without `allow_private`, a `headers_env` value that is not a variable name, a header sent both from `headers_env` and as each person's own, an approval timeout out of range, a stdio command that is not an absolute path, a price that is not a number of dollars, an `mcp_clients` entry that is not a client.

### Bundles: virtual MCP servers

A bundle serves chosen tools of several servers under one name, at `/mcp/<name>`, for the teams it lists. A caller still sees only the tools their rule allows of it.

```yaml title="gantry.policy.yaml"
version: 1
providers:
  - name: anthropic
    kind: anthropic
    url: https://api.anthropic.com
    key_env: ANTHROPIC_PROVIDER_KEY
    models: [claude-sonnet-5-5]
mcp:
  - name: github
    url: https://api.githubcopilot.com/mcp
    user_auth: oauth
  - name: docs
    url: https://docs-mcp.example.com/mcp
mcp_bundles:
  - name: payments-tools
    tools: [github.create_issue, docs.search]
    teams: [payments]
rules:
  - name: payments-team
    principals: { team: payments }
    models: [claude-sonnet-5-5]
    tools: [github.*, docs.*]
```

| Field | Required | Meaning |
|---|---|---|
| `name` | yes | Letters, digits, `-` and `_`. Served at `/mcp/<name>`; its `initialize` names itself so. |
| `tools` | yes | The tools it serves, as in a rule. |
| `teams` | no | The teams that may connect. Empty lets every team. |

A bundle serves tools only. Calling a tool outside it is refused with `not_in_bundle`, and a caller of another team with `bundle_not_allowed`. Bundles change on reload, like rules.

## Connect a client

The endpoint is `<gantry url>/mcp` (or `/mcp/<bundle>`). A client either sends a Gantry key as `Authorization: Bearer <key>`, as on the model routes, or signs in with OAuth.

### Sign in with OAuth

Clients that follow MCP's authorization specification (Claude Desktop, Claude Code, Cursor and others) need no key in their configuration: add the URL and the client opens a browser to sign in.

1. Gantry answers a call without a credential with `401` and `WWW-Authenticate: Bearer resource_metadata="<gantry url>/.well-known/oauth-protected-resource/mcp"`.
2. The client reads that and `/.well-known/oauth-authorization-server`, registers itself at `/oauth/register` (dynamic client registration), and opens `/oauth/authorize` with PKCE (S256 only).
3. The person says who they are on Gantry's page: with their Gantry key, or with **Sign in with single sign-on**, which goes through the console's identity provider (`console.sso`). Single sign-on is offered when `console.sso.self_issue` is set; it decides who may have personal access and which team they are in, as for `gantry login`.
4. The client trades the code at `/oauth/token` for an access token (one hour) and a refresh token (30 days, replaced on each use). The token is bound to the address the client asked for (`resource`), so a token for `/mcp` does not work at a bundle's address.

Every call made with a token is the person's: checked against their rule and recorded under their name with `via: "oauth"`. A token from a Gantry key stops working when that key is revoked, expires or is killed; a token from single sign-on names the person and team the identity provider gave. Tokens and clients are kept in the store (`store:`), or without one in `gantry.mcp.json` beside the policy, as hashes only.

## What Gantry answers

| Method | Answer |
|---|---|
| `initialize` | Gantry's own: the `tools`, `prompts` and `resources` capabilities, server name `gantry` (or the bundle's name), and an `Mcp-Session-Id` under which Gantry remembers what the client said it supports. Protocol versions `2025-11-25`, `2025-06-18` and `2025-03-26`. |
| `ping` | An empty result |
| `tools/list` | The tools of every server that the caller's rule allows, named `<server>.<tool>`, all in one page. A server that does not answer is left out, with a line on Gantry's standard error. |
| `tools/call` | Checked against the rule, the guardrails, approvals and pins, then forwarded with the tool's own name. The server's result or error comes back with the caller's id, streamed when the client accepts an event stream. |
| `prompts/list`, `prompts/get` | The prompts the rule allows, named `<server>.<prompt>`; a `prompts/get` is checked and recorded like a call |
| `resources/list`, `resources/templates/list`, `resources/read` | The resources the rule allows, each URI shown as `gantry://<server>/<the server's URI>`; a `resources/read` is checked and recorded like a call |
| Notifications | `202 Accepted` |
| A client's answer to a server's request | Passed to the server it came from. See [Requests from servers](#requests-from-servers-and-streaming) |
| Any other method | JSON-RPC error `-32601` |

`DELETE` on `/mcp` ends the client's session. `GET` answers `405`: requests from servers come inside the stream that answers a call, not on a stream of Gantry's own. Resource subscriptions are not offered.

A refusal is a JSON-RPC error with code `-32001`, a message that names the cause and the fix, and `data.gantry_code` and `data.decision`:

```json
{"jsonrpc":"2.0","id":9,"error":{"code":-32001,"message":"Refused (tool_not_allowed): rule \"payments-team\" does not allow tool \"github.delete_repo\" for \"maya.cohen\" of team \"payments\". It allows: github.create_issue, github.list_issues, docs.*. Ask a Gantry admin to add it to the rule's tools if you need it. Decision 01J....","data":{"gantry_code":"tool_not_allowed","decision":"01J..."}}}
```

A missing or unknown key is refused with HTTP 401 before the message is read. Every other refusal comes with HTTP 200, so the client shows its message as the answer to that call. The codes are those of the model routes (`no_key`, `unknown_key`, `key_expired`, `killed`, `no_rule`, `audit_unavailable`), plus:

- `tool_not_allowed`, `prompt_not_allowed`, `resource_not_allowed`: the caller's rule does not list it.
- `unknown_tool`: the name is not `<server>.<tool>` of a configured server. Run `tools/list` for the names.
- `unknown_bundle`, `not_in_bundle`, `bundle_not_allowed`: a bundle's address that does not exist, a tool the bundle does not serve, a team the bundle is not for.
- `guardrail_blocked`: a guardrail found something in the tool's arguments.
- `approval_denied`, `approval_timeout`: the tool needs an admin's approval, and it was denied or did not come in time.
- `tool_changed`: the server changed the tool since it was approved, and holds changed tools.
- `credential_needed`: the server runs calls with each person's own account, and the caller has not connected one. This one has JSON-RPC code `-32042` (MCP's URL elicitation) and carries the link in `data.elicitations[0].url`.
- `wrong_resource`: an OAuth token used at another address than the one it was issued for.

When a server gives no answer, the error has code `-32603` and `data.gantry_code` `upstream_` followed by the outcome its `mcp_result` record names, for example `upstream_timeout`. The tool may or may not have run.

### Kill switches

A switch on a person, a team, a key or everyone stops their tool calls and tool lists too. A switch on a model named like a tool stops that one tool for everyone:

```bash
gantry kill --model github.delete_repo --reason "deleting repositories is paused"
```

The console's **MCP tools** page sets and clears the same switch with **Stop tool** and **Start tool**.

## Each person's own credential

With `user_auth`, a server runs every call with the caller's own credential, so the call happens as the person at the server too, and Gantry records which credential went (`upstream_auth: "user_headers"` or `"user_oauth"`). Each person gets their own session with the server.

The first time a person calls such a server, Gantry refuses with `credential_needed` and a one-use link, good for ten minutes. In `tools/list` the server shows one tool, `<server>.connect`, until the person has connected; calling it returns the link.

- `user_auth: headers`: the link opens a form for the person's header values, for example their own `Authorization: Bearer ...` token.
- `user_auth: oauth`: the link sends the person to the server's own OAuth authorization server. Gantry finds it from the server's protected resource metadata (RFC 9728) and the authorization server's metadata, registers itself there unless `oauth_client_id` is set, signs in with PKCE, and keeps the token. It refreshes the token when it runs out; when the server stops taking it, the next call returns a new link.

Credentials are sealed with AES-256-GCM under the master key, as provider credentials are: with a store, the store's `GANTRY_MASTER_KEY`; without one, `GANTRY_MASTER_KEY` (or `GANTRY_MASTER_KEY_FILE`) of the gateway, sealing into `gantry.mcp.json`. Gantry does not start with a `user_auth` server and no master key.

## Token exchange

With `user_auth: token_exchange`, Gantry trades the token the caller holds at your identity provider for a token the server takes, on every person's behalf, so nobody connects an account by hand. The caller sends its own access token in the `x-gantry-subject-token` header beside its Gantry key. Gantry posts it to `token_url` as an RFC 8693 token exchange (`grant_type=urn:ietf:params:oauth:grant-type:token-exchange`, the token as `subject_token`, with `audience`, `resource` and `oauth_scopes` when set), signed in as `oauth_client_id` with the secret from `oauth_client_secret_env`, and sends the server the token it gets back as `Authorization: Bearer`.

`user_auth: on_behalf_of` sends the on-behalf-of form Microsoft Entra ID takes instead: `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`, the token as `assertion`, `requested_token_use=on_behalf_of` and `oauth_scopes`.

```yaml
version: 1
providers:
  - name: anthropic
    kind: anthropic
    url: https://api.anthropic.com
    key_env: ANTHROPIC_API_KEY
    models: [claude-sonnet-5-5]
mcp:
  - name: tickets
    url: https://tickets.example.com/mcp
    user_auth: token_exchange
    token_url: https://login.example.com/oauth2/token
    oauth_client_id: gantry
    oauth_client_secret_env: IDP_CLIENT_SECRET
    audience: api://tickets
    oauth_scopes: [tickets.read]
rules:
  - name: support
    principals: { team: support }
    models: [claude-sonnet-5-5]
    tools: [tickets.*]
```

The traded token is kept in memory until 30 seconds before it expires and is never written anywhere. The decision record says `upstream_auth: "token_exchange"` or `"on_behalf_of"` and holds neither token. A call without the header, or with a token the identity provider does not trade, is refused with `credential_needed`, and the message carries the identity provider's reason. The identity provider checks the token; the caller's Gantry key and rule still decide what it may call.

## Tool prices

A server's `call_price_usd` prices every call of its tools, and `tool_prices` prices single tools. A priced call that the server answered writes a usage record (`provider: "mcp"`, `model: "<server>.<tool>"`, `usage: "per_call"`, `cost_usd` and `charged_usd` the price) and counts against every budget the caller counts against: the rule's, the key's and the `limits:` list. Its `mcp_result` record carries `charged_usd` too. A call the server did not answer is not charged.

Once one of those budgets is spent, a priced call is refused with `budget_exceeded` before it reaches the server. `GET /admin/usage?group_by=model` shows the spend by tool, since a tool is its usage record's model.

```yaml
mcp:
  - name: search
    url: https://mcp.example.com/mcp
    call_price_usd: 0.002
    tool_prices: { deep_research: 0.25 }
```

## Sessions

`GET /admin/mcp/sessions` (permission `see_keys`) and the console's **MCP sessions** page list:

- `sessions`: each MCP client connected to this gateway, with the start of its session id, the person and team, what the client called itself at `initialize` (`client`, `client_version`), its `user_agent`, the OAuth client it signed in through, the bundle, when it started and when it was last used;
- `connections`: each person's own account at a server with `user_auth: headers` or `oauth`, as `<server>:<person>`.

`DELETE /admin/mcp/sessions/<id>` (permission `revoke_keys`), or **End session** and **Disconnect** on the page, ends one. A request in an ended session is refused with `session_revoked` until the client connects again; a disconnected person signs in to the server again on their next call. Each is an admin record, `end_mcp_session`. A role kept to an organization or teams sees and ends only the sessions of its own, and no connections.

<Aside type="note">
Client sessions are kept by the gateway that opened them. Behind several gateways, each lists and ends its own. Connections are shared through the store.
</Aside>

## Client allowlist

A rule's `mcp_clients` names the MCP client applications that may use the gateway under it. Without it every client may.

```yaml
rules:
  - name: payments-team
    principals: { team: payments }
    models: [claude-sonnet-5-5]
    tools: [github.*]
    mcp_clients: [claude-code, cursor*, "oauth:3f2a9c1e"]
```

| Entry | Matches |
|---|---|
| `claude-code` | A client that called itself that at `initialize` (`clientInfo.name`), or whose `user-agent` starts with that product name. Case does not matter |
| `cursor*` | The same, by prefix |
| `oauth:<client id>` | A client signed in through that OAuth client, as `mcp_oauth` records name it |

Every list, call, prompt and resource read from another client is refused with `mcp_client_not_allowed`, and the record's `mcp_client` names what the client called itself. A name and a user agent are what the client says of itself, so they keep honest clients to an approved set; `oauth:` entries hold against a client that lies, since Gantry issued that sign-in.

## Guardrails on tool calls

The rule's guardrails run on tool calls as on model requests, with the same `action` and, for webhooks, the same `on_failure`:

- Guardrails that run on requests (the default, `on: [request]`) read every string in the call's `arguments`. `block` refuses the call with `guardrail_blocked` before it is recorded as allowed and before it reaches the server; `mask` sends the masked arguments.
- Guardrails with `on: [answer]` read the text of the result (`content` text and every string of `structuredContent`). `block` replaces the result with an error and records `outcome: "guardrail_blocked"`; `mask` masks it.

What they found is on the decision record (`guardrails`) for the arguments and on the `mcp_result` record for the result, counts only.

## Approvals

A rule's `approve_tools` names tools whose calls wait for an admin. The call is held, open, until an admin approves or denies it on the console's **MCP approvals** page (which shows who asked, the rule and the arguments), or until `approval_timeout_seconds` pass. Approved, it runs and its decision record says `approved_by`; denied or timed out, it is refused with `approval_denied` or `approval_timeout`. Each approval and denial is an admin record in the audit log. With a store, any gateway's console can approve a call held on another.

```yaml
mcp:
  - name: github
    url: https://api.githubcopilot.com/mcp/
rules:
  - name: platform
    principals: { team: platform }
    models: [claude-sonnet-5-5]
    tools: [github.*]
    approve_tools: [github.delete_repo, github.merge_pull_request]
    approval_timeout_seconds: 120
```

## Tool pins and changed tools

A tool's description and schema are instructions to the model, so a server that changes them can change what an agent does. Gantry pins each tool the first time it lists a server: a hash of its title, description, input and output schema and annotations. On every later list:

- a new tool, or a tool whose hash changed, is recorded as an `mcp_tool_changed` record with the old and new hash;
- with `tool_changes: record` the new version is served and pinned;
- with `tool_changes: block` the tool is left out of `tools/list` and its calls are refused with `tool_changed` until an admin approves it on the console's **MCP tools** page.

The **MCP tools** page lists every tool seen, from which server, its pinned description, when it was first seen, who has called it (from the audit log), a held change with its new description, and the tool's kill switch.

## Upstream servers

Gantry is one MCP client to each server. It opens a session with `initialize` the first time a server is needed, shares that session among all callers, and opens a new one when the server ends it (HTTP 404). Each request to a server gets an id of Gantry's own, and the answer goes back with the caller's id.

A server with `user_auth` has one session per person instead.

### Transports

| `transport` | How Gantry reaches the server |
|---|---|
| `http` | Streamable HTTP: one POST per message. The default. |
| `sse` | The older HTTP+SSE transport (MCP 2024-11-05). Gantry opens the event stream at `url` with a GET, posts each message to the endpoint the stream's `endpoint` event names, and reads the answers from the stream. The endpoint must be on the server's own origin. `headers_env` and `user_auth` work as on `http`. |
| `stdio` | Gantry starts `command` with `args` and speaks to it on its standard input and output, one JSON-RPC message a line. One process serves every caller; it is started on the first call, started again if it exits, and stopped when its server leaves the policy or Gantry stops. |

Tools, guardrails, approvals, pins, prices and records are the same on every transport. Requests a server sends to the client (sampling, elicitation) and progress notifications are relayed from Streamable HTTP servers only; on `sse` and `stdio` the server gets JSON-RPC error `-32601` for them.

#### stdio servers

A stdio server is a program running with the gateway's own rights, so the policy alone cannot start one:

- The gateway starts only a command listed in `GANTRY_MCP_STDIO_ALLOW`, a comma separated list of absolute paths in the gateway's own environment. A policy that names another command does not load, at start or at a reload. Whoever can edit the policy, in the file, the console or the admin API, therefore cannot choose what the gateway runs.
- `command` is an absolute path, run directly, never through a shell. `args` are passed as written.
- The process gets an empty environment plus the variables `env` names, each read from the gateway's environment. Provider keys, the master key and the database URL do not reach it.
- A stdio server takes no `headers_env` and no `user_auth`: it has one credential, from `env`.

```yaml
mcp:
  - name: git
    transport: stdio
    command: /usr/local/bin/mcp-server-git
    args: [--repository, /srv/repos/handbook]
    env: { GIT_TOKEN: HANDBOOK_GIT_TOKEN }
```

```bash
export GANTRY_MCP_STDIO_ALLOW=/usr/local/bin/mcp-server-git
```

<Aside type="caution">
Gantry does not sandbox the process. It can read what the gateway's user can read and open any connection the gateway's network allows. Run the gateway as a user without a shell or a home directory, on a read-only root filesystem, with egress limited to what the server needs, and list a wrapper that drops rights (a container runtime, `bwrap`, `sandbox-exec`) in `GANTRY_MCP_STDIO_ALLOW` when the program is not yours. Where you can, run the server as its own service and reach it over `http` instead.
</Aside>

### Requests from servers and streaming

A server may answer with JSON or with an event stream (`text/event-stream`). When the client accepts event streams, a `tools/call` is answered as a stream too, passed through as the server sends it:

- progress and other notifications go to the client as they come;
- requests the server sends inside the stream (`sampling/createMessage`, `elicitation/create`, `roots/list`) go to the client under an id of Gantry's, if the client said at `initialize` that it supports them. The client's answer, posted to `/mcp`, goes back to the server under the server's own id. Only the client the request went to can answer it. A client that did not say it supports one gets nothing, and the server gets JSON-RPC error `-32601`;
- the answer comes last, checked by the answer guardrails and recorded, with the client's id.

Gantry tells every server it supports sampling, elicitation and roots, and answers a server's `ping` itself. A client that does not accept event streams gets the answer as JSON, and requests from the server meanwhile are refused.

A server must start answering within the provider first-byte timeout, 120 seconds, and in a stream each event must follow the last within it.

## What is recorded

Every `tools/call` writes a decision record before it is forwarded, in the shape of a [model request's](/reference/audit-records/#request-decision), with `path: "/mcp"` and three fields more:

| Field | Value |
|---|---|
| `mcp_method` | `tools/call`, `prompts/get` or `resources/read` |
| `server` | The server, for example `github` |
| `tool`, `prompt` or `resource` | Its own name (or URI) on that server, for example `create_issue` |
| `bundle` | The bundle, when the call came to `/mcp/<bundle>` |
| `via` | `oauth` when the caller signed in with an OAuth token |
| `upstream_auth` | `user_headers` or `user_oauth` when the person's own credential went to the server; `token_exchange` or `on_behalf_of` when a traded token did |
| `mcp_client` | What the client called itself, on a rule with `mcp_clients` |
| `approved_by` | The admin who approved the call, for a tool in `approve_tools` |
| `guardrails` | What the guardrails found in the arguments, counts only |

```json
{"n":42,"id":"01J...","time":"2026-11-13T09:14:02.120Z","person":"maya.cohen","team":"payments","client":"10.0.0.7","key":"3f9a1c2e","method":"POST","path":"/mcp","model":null,"verdict":"allow","code":null,"rule":"payments-team","rule_line":18,"provider":null,"policy_sha256":"...","keys_sha256":"...","mcp_method":"tools/call","server":"github","tool":"create_issue","prev":"...","hash":"..."}
```

If the record cannot be written, the call is refused with `audit_unavailable` and never reaches the server.

When the server has answered, an `mcp_result` record follows with the same `id`:

| Field | Value |
|---|---|
| `event` | `mcp_result` |
| `id`, `time`, `person`, `team`, `key`, `server`, `tool` | As on the decision |
| `duration_ms` | From forwarding the call to its answer |
| `outcome` | `ok`, `tool_error` (the tool ran and reported `isError`), `rpc_error` (the server answered with a JSON-RPC error, its code in `upstream_code`), `guardrail_blocked`, `unreachable`, `timeout`, `http_error`, `unauthorized` (the server refused the credential), `unreadable_answer`, `session_ended`, `initialize_refused` or `caller_left` (the client closed the stream before the answer) |
| `guardrails` | What the answer guardrails found in the result, counts only |
| `charged_usd` | The price of a priced call the server answered |

Refused calls, and refusals of any other `/mcp` message (an unknown key, a killed person asking for `tools/list`), get a decision record with `verdict: "refused"` and the code. `initialize`, `ping` and allowed lists are not recorded.

The gateway also records, each as its own `event`:

| Event | When |
|---|---|
| `mcp_tools_pinned` | The first list of a server pinned its tools (`server`, `tools`: how many) |
| `mcp_tool_changed` | A tool was added or changed after that (`server`, `tool`, `change`, `old_sha256`, `new_sha256`, `held`) |
| `mcp_oauth` | A person let an MCP client sign in as them (`person`, `team`, `via`, `client_id`, `client_name`) |
| `mcp_credential` | A person connected their own account to a server (`person`, `team`, `server`, `kind`); never the value |

Approving a call or a changed tool, and stopping or starting a tool, are admin records (`mcp_approve_call`, `mcp_deny_call`, `mcp_approve_tool`, `mcp_stop_tool`, `mcp_start_tool`, `end_mcp_session`).

The arguments of a call and its result are never recorded. While a call waits for approval its arguments are kept for the admin to read, and removed once it is decided. `gantry audit verify` counts `mcp_result` records with the usage records.
