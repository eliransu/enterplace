Connect the admin console to your identity provider (Okta, Microsoft Entra ID, Google, Keycloak or any OpenID Connect provider). For SAML 2.0, see [SAML sign-in](/governance/saml/); for each provider's own steps, see the Identity providers pages, from [Okta](/governance/identity-providers/okta/) to [Zitadel](/governance/identity-providers/zitadel/), [Auth0](/governance/identity-providers/auth0/) and [Ping Identity](/governance/identity-providers/ping-identity/). People sign in with their company account and get the role their groups say. The same setup lets developers get their own expiring Enterplace key with `enterplace login`, without an admin.

## Example

```yaml title="enterplace.policy.yaml"
version: 1
providers:
  - name: anthropic
    kind: anthropic
    url: https://api.anthropic.com
    key_env: ANTHROPIC_PROVIDER_KEY
    models: [claude-sonnet-5-5, claude-haiku-5-5]
rules:
  - name: developers
    principals: { team: developers }
    models: [claude-sonnet-5-5, claude-haiku-5-5]
    budget: { usd: 200, per: month }
console:
  sso:
    issuer: https://login.example.com
    client_id: enterplace-console
    client_secret_env: ENTERPLACE_SSO_SECRET
    redirect_url: https://enterplace.example.com/console/sso/callback
    allowed_domains: [example.com]
    role_claim: groups
    admin_values: [enterplace-admins]
    read_only_values: [enterplace-viewers]
    self_issue:
      allowed_domains: [example.com]
      team: developers
      expires_days: 30
```

## Set up console sign-in

<Steps>

1. Register Enterplace as an OpenID Connect web application at your provider, with the redirect URL `https://<your enterplace>/console/sso/callback`.

2. Make the provider put `email` and your role claim (for example `groups`) in the **ID token**. Enterplace does not call the userinfo endpoint.

3. Add `console.sso` to the policy file, as above.

4. Set the client secret in the environment Enterplace runs in, under the name `client_secret_env` gives: `ENTERPLACE_SSO_SECRET=...`.

5. Open `/console`. The sign-in page shows **Sign in with single sign-on**.

</Steps>

The policy file is read on every console page, so `console.sso` changes need no restart.

### Fields

| Field | Type | Default | Description |
|---|---|---|---|
| `issuer` | string | required | Exactly as the provider writes it. The ID token's `iss` must equal it. |
| `client_id` | string | required | The client ID registered at the provider. |
| `client_secret_env` | string | required | Name of the environment variable holding the client secret. The secret never goes in the file. |
| `redirect_url` | string | required | The console's `/console/sso/callback` at its public address. |
| `allowed_domains` | list | `[]` | Email domains let in. |
| `allowed_emails` | list | `[]` | Whole addresses let in, for guests outside your domains. |
| `role_claim` | string | required | The ID token claim, a string or a list, that carries the role. |
| `admin_values` | list | `[]` | Claim values that give the admin role. |
| `read_only_values` | list | `[]` | Claim values that give the read-only role. |
| `self_issue` | map | none | Turns on `enterplace login`. See [below](#developer-keys-with-enterplace-login). |
| `scopes` | string | `openid email profile` | The scopes asked for, space separated. Must include `openid`. Okta's org authorization server and OneLogin send a `groups` claim only with `openid email profile groups`. |

### Roles

| Role | Can |
|---|---|
| Admin | Everything in the console: issue and revoke keys, including admin keys. |
| Read only | See the audit log, people and keys, policy and spend. An attempt to issue or revoke is refused and recorded with code `read_only`. |

The policy may define more roles with fine-grained permissions under `roles:`; a role's `sso_values` lists the claim values that give it. An admin value wins, then the first role whose `sso_values` match, then a read-only value. See [Console roles](/governance/policy/#console-roles).

There is no default role. A person whose role claim holds no admin, role or read-only value is refused. A role change at the provider applies at the next sign-in. Removing `console.sso`, or a person's email or domain, ends their session at once.

People can still sign in with an admin Enterplace key alongside SSO.

## What Enterplace checks

Enterplace refuses a sign-in on any failed check, with a message that names the cause and the fix.

- **Flow.** Authorization code with PKCE (S256), a random `state` tied to the browser by a cookie and usable once within 10 minutes, and a `nonce`.
- **Discovery.** From `<issuer>/.well-known/openid-configuration`, whose `issuer` must equal the configured one. Endpoints must be https (plain http only to localhost). Discovery and the key set are cached for 10 minutes. A token signed with an unknown `kid` fetches them again once, so key rotation is followed.
- **ID token.** Signature RS256 or ES256 only, with the key its `kid` names. Then `iss`, `aud` (and `azp` with several audiences), `exp` (60 seconds of clock skew allowed) and `nonce`.
- **Email.** Must be in `allowed_emails` or have a domain in `allowed_domains`, and must not be marked `email_verified: false`.

Starting a sign-in keeps nothing on the server: the state lives in a sealed cookie, so a flood of `/console/sso/start` requests fills no memory and locks nobody out. Only finished sign-ins are remembered, to refuse a second use.

### Audit records

Every sign-in, refusal and sign-out is an `admin` record in the audit chain, with `action: console_sign_in` or `console_sign_out`, the email as `person` and `target.via: sso`. A sign-in record holds the role, a refusal the reason code:

| Code | Cause |
|---|---|
| `sso_state` | The `state` is expired, already used, or was not started by this browser. |
| `sso_provider` | Discovery or the key set could not be read, an endpoint is not https, or the provider does not offer PKCE with S256. |
| `sso_issuer` | Discovery's `issuer`, or the token's `iss`, is not the configured issuer. |
| `sso_token` | The code could not be traded for an ID token, or the ID token is missing or not a well formed JWT. |
| `sso_signature` | The ID token is not signed with RS256 or ES256, or its signature does not match. |
| `sso_unknown_key` | The token's `kid` is not in the provider's key set. |
| `sso_audience` | `aud` or `azp` is not this client. |
| `sso_expired` | The ID token has expired. |
| `sso_nonce` | The `nonce` does not match. |
| `sso_email` | The ID token has no email, the email is not verified, or it is not allowed. |
| `sso_role` | The role claim holds no admin or read-only value. |
| `sso_config` | `console.sso` is not set, or the policy file has problems. |
| `sso_secret` | The client secret variable named by `client_secret_env` is not usable. |
| `sso_self_issue` | `enterplace login` with no `self_issue` section, or an email not on its lists. |
| `sso_team` | `enterplace login`, and `teams:` places the person in no team. See [Teams](/governance/teams/#which-team-a-person-is-in). |

Refused sign-ins are recorded one by one, up to 100 a minute from each client address (an IPv6 client counts by its /64). Past that, the address's minute is summed in one `console_sso_refusals` record with the count per code. A minute with 100 or more starts writes one `console_sso_starts` record.

## Developer keys with enterplace login

With `self_issue` set, a developer gets a personal key without an admin:

```bash
enterplace login https://enterplace.example.com
```

<Steps>

1. The CLI opens the browser at the console, and the person signs in at the identity provider.

2. The browser comes back to a listener the CLI opened on `127.0.0.1`, carrying a one-use code (valid for two minutes), never the key.

3. The CLI trades the code for the key, together with a PKCE verifier only it holds.

4. The CLI saves the key and prints the line to add to a shell profile: `. ~/.config/enterplace/env`.

</Steps>

The key:

- is named by the person's email and put in their [team](/governance/teams/#which-team-a-person-is-in): the team that lists their email, else the first whose `sso_values` match their `role_claim` values, else the `self_issue` team,
- expires after `expires_days`,
- is recorded as an `admin` record with `action: self_issue_key`, the email as `person`, and the key's hash prefix and expiry in `target`.

The CLI writes `~/.config/enterplace/credentials` (`$XDG_CONFIG_HOME/enterplace/credentials` when set) and, beside it, `env` with `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_API_KEY` and `ENTERPLACE_KEY` for Claude Code, the OpenAI SDKs and Codex. Both files are readable by their owner only, in a folder only they can open. The CLI sends a key only to an https address (plain http only to this machine).

Logging in again gives up the previous key and rewrites `env`, so a profile that sources it keeps working. A profile that holds the key itself breaks at the next login. When a login key expires or is revoked, the refusal (`key_expired` or `unknown_key`) says to run `enterplace login` again.

`--no-browser` prints the sign-in address instead of opening it.

On a setup with SAML and no OpenID Connect, `enterplace login` signs in through SAML: see [enterplace login over SAML](/governance/saml/#enterplace-login-over-saml).

### self_issue fields

| Field | Type | Default | Description |
|---|---|---|---|
| `allowed_domains` | list | `[]` | Email domains that may self-issue. |
| `allowed_emails` | list | `[]` | Whole addresses that may self-issue. |
| `team` | string | `developers` | The team of a person `teams:` places nowhere. When `teams:` places people and this is not written, such a person is refused with `sso_team`. Write a rule for it. |
| `expires_days` | integer | `30` | Days a key works, 1 to 365. |

No `self_issue` section, no `enterplace login`. No console role is needed: the key is for the person's own requests, which the policy's rules decide. An email outside the lists, or not verified, is refused and recorded with `sso_self_issue` or `sso_email`, and the CLI prints why.

### enterplace logout

```bash
enterplace logout
```

Revokes the saved key through `DELETE /admin/keys/self`, which any key may call for itself (recorded as `revoke_own_key`), then deletes the credentials and `env` files. A key Enterplace no longer knows counts as already revoked.

Expired login keys stay in the keys file until you run [`enterplace key prune`](/governance/keys/#prune-expired-keys).

<Aside type="note">
Console sessions and sign-ins in progress live in memory. A restart signs everyone out, and behind a load balancer the provider's callback must reach the node that started the sign-in.
</Aside>

## The Enterplace app

The Enterplace app (hosted and hybrid gateways) has its own sign-in. Each organization connects its own OpenID Connect provider, so people sign in with their company account. Password sign-in can add a code from an authenticator app.

### Connect your identity provider

<Steps>

1. In your provider, create an OpenID Connect web application with the redirect URI `https://app.enterplace.dev/sso/callback`. Okta: Applications, Create App Integration, OIDC, Web Application. Entra ID: App registrations, New registration, Web. Google Workspace: Google Cloud console, Credentials, OAuth client ID, Web application.

2. In the Enterplace app, an owner opens **Settings**, **Single sign-on** and enters the issuer, client ID, client secret and your email domain. Enterplace reads the issuer's discovery document before it saves.

3. Test the sign-in link it shows, `https://app.enterplace.dev/sso/<org-id>`, from a private window.

4. To require it, set **Require SSO** to yes. Members other than owners must then sign in through your provider to open the organization. Owners keep password access, so a broken provider cannot lock everyone out.

</Steps>

People in your email domain who sign in for the first time join with the role you choose (viewer or admin). Removing someone in your provider stops their next sign-in; to revoke their keys at once, remove them in Enterplace or connect SCIM on the **Members** page.

A session made by your SSO opens your organization only. It does not open the person's other organizations, it never carries Enterplace staff rights, and it cannot change account settings. So your provider vouches for your people in your organization, and nothing else.

The flow is the same as the console's: authorization code with PKCE, a `state` tied to the browser and usable once within 10 minutes, a `nonce`, and an ID token signed with RS256 or ES256 whose `iss`, `aud`, `exp` and `nonce` are checked. The email must be in your domain and not marked unverified. The client secret is stored encrypted.

### Two-step sign-in

Anyone who signs in with a password can turn on two-step sign-in under **Account security** on the organizations page. Enterplace shows a key to add to an authenticator app (1Password, Google Authenticator, Microsoft Authenticator, Authy), asks for one code to confirm, and shows 10 recovery codes once. Each recovery code works once.

After that, a matching password asks for the current 6-digit code. A code works once, and five wrong codes end the attempt, so the password must be entered again. SSO sign-ins skip this step: your provider runs its own MFA.
