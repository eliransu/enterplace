A guardrail reads the text of a request after the policy allows it and before it is recorded and sent. With `on: [answer]` it also reads the model's answer before the caller sees it. It can block, mask, or only record what it finds.

## Example

```yaml title="gantry.policy.yaml"
version: 1
providers:
  - name: openai
    kind: openai
    url: https://api.openai.com/v1
    key_env: OPENAI_API_KEY
    models: [gpt-4o-mini]
guardrails:
  - name: no-secrets
    type: secrets
    action: block
  - name: mask-pii
    type: pii
    action: mask
  - name: moderation
    type: openai_moderation
    key_env: OPENAI_API_KEY
    on_failure: fail_open
  - name: injection
    type: lakera
    key_env: LAKERA_GUARD_API_KEY
    on_failure: fail_closed
rules:
  - name: everyone
    principals: { any: true }
    models: ["*"]
    guardrails: [no-secrets, mask-pii, moderation, injection]
```

Guardrails are defined once at the top level and named by rules. A change applies to the next request after the file is reloaded.

## Three kinds

| Kind | Types | Runs |
|---|---|---|
| Built in | `secrets`, `pii` | Inside Gantry, no network call. |
| Custom | `regex`, `keywords` | Your patterns and word lists, inside Gantry, no network call. |
| Vendor | `openai_moderation`, `presidio`, `lakera`, `bedrock_guardrail`, `azure_content_safety`, `azure_prompt_shield`, `llama_guard`, `model_armor`, `pangea`, `nemo_guardrails`, `hiddenlayer`, `lasso`, `guardrails_ai`, `aporia`, `prisma_airs`, `enkrypt`, `grayswan`, `cisco_ai_defense`, `mistral_moderation` | Gantry calls the vendor's own API. No adapter needed. |
| Webhook | `webhook` | Your service, speaking [Gantry's contract](/governance/guardrail-webhooks/). |
| Events | `events` | Your service, sent the whole conversation as [typed events](/governance/plugin-events/) with a session and a turn: tool calls, tool results, reasoning, MCP calls. |

## Actions

| `action` | Effect |
|---|---|
| `block` | Refuse the request with `guardrail_blocked` (403). For a vendor or webhook, obey the service: refuse when it refuses, mask when it masks. |
| `mask` | Replace each finding with `[MASKED <kind>]` and forward the changed request. Built-in, `regex` and `keywords` types, and the vendors that redact: `presidio`, `pangea`, `hiddenlayer`, `lasso`. |
| `warn` | Forward unchanged and record what was found. Use it to see what a guardrail would catch before you enforce it. |

`action` is required for `secrets`, `pii`, `regex` and `keywords`. Vendors and webhooks default to `block`.

Every action records what was found: one entry per guardrail and kind with `guardrail`, `detector`, `kind`, `action` (`block`, `mask`, `warn`, `shadow` or `skipped`) and `count`. The matched text is never in a record, a refusal or Gantry's log. An empty list means the guardrails ran and found nothing.

### Order

On a request, a rule's [transforms](/governance/transforms/) run first, then its [function tool check](/governance/tool-permissions/), then its guardrails. On an answer the same order holds. So every check reads what is really sent or returned.

The built-in guardrails a rule names run first, then its vendors and webhooks in the order written. A remote guardrail sees the text after built-in masking. Once one blocks, no further remote guardrail is called. A `block` wins over a `mask`: a refused request is never changed.

Guardrails run before the cache, the rate limit and the budget. See [Order of checks](/governance/policy/#order-of-checks).

## Built-in detectors

| Type | Kinds found |
|---|---|
| `secrets` | `private_key` (the whole PEM or PGP block), `aws_access_key`, `github_token`, `slack_token`, `gantry_key`, `jwt`, `gcp_service_account_key` (the `private_key_id` of a key file; its PEM block is a `private_key` too), `gcp_api_key` (`AIza...`), `azure_connection_string` (the `AccountKey=` or `SharedAccessKey=` part), `stripe_key` (`sk_` and `rk_`, live and test; never the public `pk_`), `twilio_api_key` (`SK...`), `sendgrid_key` (`SG.`), `openai_project_key` (`sk-proj-`, `sk-svcacct-`, `sk-admin-`), `anthropic_key` (`sk-ant-api03-`, `sk-ant-admin01-`), `api_key` (any other `sk-...`), `database_url` (a `postgres`, `mysql`, `mariadb`, `mongodb`, `redis`, `amqp` or `mssql` URL with a password that is not a placeholder such as `${DB_PASSWORD}` or `password`) |
| `pii` | `email_address`, `phone_number`, `credit_card` (Luhn checked), `iban` (mod 97 checked), `israeli_id` (check digit), `us_ssn`, `medical_record_number` and `date_of_birth` (only after a label such as `MRN:` or `DOB:`) |

These are pattern detectors. A password on its own, a key with no known prefix (a Twilio auth token is 32 bare hex digits), a name, an address, or a date of birth or record number with no label is not found. Text that is encoded, split across messages, spelled out or translated is not found either. Any 9-digit number with a valid Israeli ID check digit, and some long digit runs that pass Luhn, are reported. Use a vendor such as Presidio for names, addresses and anything else beyond these patterns.

`gantry-detectors-v2` is 1,943 labelled lines in the repository at `crates/gantry-core/tests/corpus/gantry-detectors-v2.jsonl` (Apache-2.0), made by `scripts/make_detector_corpus.py`. It is v1 (1,223 lines, kept unchanged beside it) with `sk-proj-` and `sk-ant-` keys labelled with their own kinds, plus 40 positives and 40 hard negatives for each kind v2 added. Every key in it is random. Each kind has realistic positives in prose, chat, code, logs and JSON, and hard negatives that look like it: public keys and certificates, IAM IDs, commit hashes, base64 JSON that is not a token, order numbers, timestamps, values with a broken checksum, and labels with no value. Every value is synthetic or a published example: AWS's example key, the card networks' test numbers, RFC 2606 mail domains, fictional phone ranges. A positive is a value a careful reader would report; precision counts a finding on any line, recall counts the values found.

`cargo test` measures the corpus and fails when this table differs from the measurement, or when a kind falls below its floor. A new corpus is a new version; v1 is not edited to move its numbers.

The kinds v2 added were written together with their corpus rows, so their 100% is what the patterns reach on shapes their author thought of: publishable `pk_` keys, account SIDs, placeholders, password-less and placeholder database URLs, wrong lengths. Real traffic will find shapes the corpus lacks. Backtest a guardrail on your own examples before you enforce it (see [Backtest](#backtest-before-enforcing)).

What the corpus shows the detectors miss or over-report:

- `phone_number`: national formats without a country code outside the US and Israel (`07700 900123`, `0491 570 146`) are missed. Order numbers shaped like a US number (`123-456-7890`) are reported.
- `email_address`: `git@github.com` and an image name such as `logo@2x.png` are reported. A login in a URL (`postgres://app:pw@db.example.com`) is not an address and is not reported.
- `us_ssn`: an SSN without dashes is missed. Any number shaped like an issued SSN is reported, such as a part number.
- `israeli_id`, `credit_card`: any 9-digit number with a valid check digit, and digit runs that pass Luhn (an IMEI, some millisecond timestamps), are reported. An ID written with its check digit apart (`12345678-2`) is missed.
- `iban`: an IBAN in lowercase is missed.
- `medical_record_number`, `date_of_birth`: a value after another label (`D.O.B.`, `birth date`, an HL7 `PID` segment) or a date written in words is missed. A labelled word (`MRN: UNKNOWN`) or `born on` before any date is reported.
- `api_key`, `slack_token`: a URL slug starting `sk-` and a placeholder such as `xoxb-your-token` are reported.

The corpus does not cover names, postal addresses, passwords on their own, secrets with no fixed prefix, or values that are encoded, split across messages, spelled out or translated. The detectors do not find those, so no number here speaks for them.

### The Gitleaks pack

`pack: gitleaks` on a `secrets` guardrail reads with [Gitleaks](https://github.com/gitleaks/gitleaks)' default rule set (221 rules, MIT license, Copyright (c) 2019 Zachary Rice) in place of Gantry's own secrets kinds. Each finding's kind is the Gitleaks rule ID, such as `aws-access-token` or `github-pat`, and its detector is `gitleaks`.

```yaml
guardrails:
  - name: gitleaks
    type: secrets
    pack: gitleaks
    action: mask
```

Each rule is read as Gitleaks reads it: its keywords first, then its regex, its secret group, its entropy floor and its allowlists (regexes and stopwords, the rule's own and the global ones). Path allowlists do not apply to a prompt. Where two rules find the same text, a named rule wins over `generic-api-key`, so one secret is one finding.

On the `gantry-detectors-v2` corpus, scored as one class of secrets, the pack measures 97.2% precision and 84.9% recall over the kinds Gitleaks has rules for (a CI test holds it to 97% and 84%). It does not find `gantry_key`, and its generic rule reports some hard negatives the built-in detector passes. The rules are at `crates/gantry-core/data/gitleaks-rules.json`, made by `scripts/gitleaks_import.py` from Gitleaks' `config/gitleaks.toml`; the only change is escaping literal braces for Rust's regex.

## Custom detectors: regex and keywords

Your own patterns and word lists, run inside Gantry like the built-in detectors, with `block`, `mask` or `warn`, on requests, answers or both.

```yaml
guardrails:
  - name: internal-ids
    type: regex
    action: mask
    on: [request, answer]
    patterns:
      ticket_id: 'TKT-[0-9]{6}'
      employee_id: '\bE[0-9]{7}\b'
  - name: codenames
    type: keywords
    action: block
    keywords:
      unreleased: [Project Falcon, bluebird]
      competitors: [Acme Corp]
```

Each entry's name is the finding's kind: it is what records show, what a refusal names, and what masking writes (`[MASKED ticket_id]`). A name uses letters, digits, dots, dashes and underscores, at most 64 characters. It never holds the matched text.

| Field | Type | Default | Description |
|---|---|---|---|
| `patterns` | map | required for `regex` | Entry name to pattern. |
| `keywords` | map | required for `keywords` | Entry name to a list of words and phrases. |
| `case_sensitive` | bool | `false` | `keywords` only. Matching ignores ASCII case unless this is `true`. |
| `whole_word` | bool | `true` | `keywords` only. A word matches only on its own, so `bluebird` does not match `bluebirds`. Set `false` to match inside words. |

Patterns use RE2 syntax, read by Rust's `regex` crate: no lookaround and no backreferences, so every pattern runs in time linear in the text, whatever it is. `gantry check` refuses a pattern that does not compile, one larger than 1 MiB compiled (such as `x{1000}{1000}`), one that matches empty text, and one with a capturing group: findings are told apart by group, so write `(?:...)` for a group. Classes, `\b` and case folding are ASCII; literal text in any script still matches.

In a keyword list, a phrase's spaces match any run of white space, so `Project Falcon` also matches `project   falcon` across a line break. Every keyword is literal text: `C++` means those three characters.

## Shadow mode

Add `shadow_until` to any guardrail, built-in, custom, vendor or webhook, to run it for a set period before it enforces anything:

```yaml
  - name: codenames
    type: keywords
    action: block
    shadow_until: 2026-12-01
    keywords:
      unreleased: [Project Falcon]
```

Until that UTC date (or time, `2026-12-01T09:00:00Z`) the guardrail checks every request its rules give it and records what it finds with `action: shadow`, the kind and the count, and never blocks or masks. From that moment it acts as `action` says, with no reload. Count the `shadow` entries in the audit log to see what it would have stopped.

## Backtest before enforcing

Run a guardrail over examples before any request meets it. The guardrail must be defined under `guardrails:`; no rule needs to name it yet.

```bash
gantry guardrail test internal-ids --corpus examples.jsonl --policy gantry.policy.yaml
```

```text
guardrail "internal-ids" (regex) on 120 requests: would hit 14 (11.7%).
  ticket_id: 12
  employee_id: 3
samples (masked):
  #3 /messages/0/content ticket_id TK******56
labelled 120 examples: precision 92.9% (13 of 14 hits expected), recall 100.0% (13 of 13 expected hit)
```

The corpus has one JSON object per line: `{"text": "..."}` (read as one user message) or `{"body": {...}}` (a whole request body), with an optional `id` and an optional `expect` (`true`, `false`, or a list of kinds, where an empty list is `false`). Blank lines and lines starting with `#` are skipped, so the detector corpus above reads as one. With `expect` on some lines, the report gives precision and recall over those lines. Up to 20 matched spans are shown with all but their first and last two characters masked.

The admin API does the same, for a guardrail a rule of the running policy uses, or for a definition not in the policy yet:

```bash
curl -s -X POST http://127.0.0.1:8080/admin/guardrails/test \
  -H "Authorization: Bearer $GANTRY_ADMIN_KEY" \
  -d '{"guardrail": {"name": "ids", "type": "regex", "action": "warn", "patterns": {"emp": "E[0-9]{7}"}},
       "corpus": [{"text": "badge E1234567", "expect": true}, {"text": "no id here", "expect": false}]}'
```

It needs the `edit_policy` permission. It answers with `requests`, `hits`, `kinds`, `samples` and `labelled` (`precision`, `recall` and the four counts), and the call is recorded like every admin call.

A backtest runs the `secrets`, `pii`, `regex` and `keywords` types. A vendor or webhook guardrail is refused, because a backtest would send every example to the service; use `shadow_until` for those. `--since 7d` (and `"since"` in the API) asks for recent traffic. The audit log holds no prompt text by design, so until request bodies are captured, Gantry says so and asks for a corpus.

## Vendors

### Fields every remote guardrail shares

| Field | Type | Default | Description |
|---|---|---|---|
| `name` | string | required | Unique. Named by rules and records. |
| `type` | string | required | A vendor type or `webhook`. |
| `on_failure` | string | required | `fail_closed` refuses the request when the service is down, slow, answers an error status or something unreadable. `fail_open` forwards it and records `kind: unavailable`, `action: skipped`. |
| `action` | string | `block` | `block` or `warn`. `mask` only for `presidio`. |
| `shadow_until` | string | none | A UTC date or time before which findings are recorded as `shadow` and not obeyed. See [Shadow mode](#shadow-mode). |
| `url` | string | per vendor | `https://`, or `http://` on `localhost`, `127.0.0.1` or `[::1]` only. |
| `timeout_ms` | integer | `1000` | 1 to 30000. Covers every call the guardrail makes for one request. |
| `key_env` | string | none | Environment variable holding the vendor's API key. |
| `headers_env` | map | none | Extra headers from environment variables, for a proxy in front of the vendor. |
| `on` | list | `[request]` | `[request]`, `[answer]` or `[request, answer]`. |

Credentials are read from the environment when a call is made. Gantry does not start, and a reload is refused, while a variable a guardrail names is unset. No credential, matched text or vendor message reaches a record, a log line or a refusal.

<TabItem label="OpenAI moderation">

Calls `POST {url}/moderations`. Default `url` `https://api.openai.com/v1`. `key_env` required, sent as `Authorization: Bearer`. Optional `model` (OpenAI defaults to `omni-moderation-latest`).

Each text is one input. A flagged result blocks. Each category set to true is a finding, such as `violence` or `harassment_threatening` (a `/` becomes `_`). Cannot mask.

```yaml
guardrails:
  - name: moderation
    type: openai_moderation
    key_env: OPENAI_API_KEY
    on_failure: fail_open
    timeout_ms: 800
```

</TabItem>
<TabItem label="Presidio">

Microsoft Presidio, self-hosted. `url` is the analyzer (`POST {url}/analyze`), required. No key: run it beside Gantry, or behind a proxy that adds one through `headers_env`.

The messages are sent as one text, in English. Each entity is a finding of its type, lowercased (`email_address`, `person`, `phone_number`). `block` refuses when anything is found. `mask` needs `anonymizer_url`: Gantry sends the analyzer's results to `POST {anonymizer_url}/anonymize` and forwards the text with `[MASKED email_address]` and the like.

A message holding the character U+001E cannot be checked (Gantry joins messages with it) and counts as a service failure.

```yaml
guardrails:
  - name: presidio-mask
    type: presidio
    url: http://127.0.0.1:5002
    anonymizer_url: http://127.0.0.1:5001
    action: mask
    on_failure: fail_closed
```

</TabItem>
<TabItem label="Lakera Guard">

Calls `POST {url}/v2/guard`. Default `url` `https://api.lakera.ai`. `key_env` required, sent as `Authorization: Bearer`. Optional `project_id` picks the Lakera project and its policy.

The messages go as chat messages with `breakdown: true`. `flagged: true` blocks. Each detector that fired is a finding of its `detector_type`. A project in Detect mode never flags, so it never blocks. Cannot mask.

```yaml
guardrails:
  - name: injection
    type: lakera
    key_env: LAKERA_GUARD_API_KEY
    project_id: project-1234567890
    on_failure: fail_closed
```

</TabItem>
<TabItem label="Bedrock">

An Amazon Bedrock guardrail through ApplyGuardrail, `POST {url}/guardrail/{guardrail_id}/version/{guardrail_version}/apply` with `source: INPUT`, signed with AWS Signature Version 4. `region`, `guardrail_id` and `guardrail_version` (a number or `DRAFT`) are required. Default `url` `https://bedrock-runtime.{region}.amazonaws.com`. Credentials come from `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN`; no `key_env`.

`NONE` allows. `GUARDRAIL_INTERVENED` blocks, with a finding per policy entry that acted: a denied topic's name, a content filter type (`hate`, `prompt_attack`), a sensitive information type, a word list type or `custom_word`. When every entry anonymized and Bedrock returned one text per text sent, the request is masked with Bedrock's texts; otherwise it is refused rather than sent unmasked. `action: mask` is not taken: the guardrail's AWS configuration decides.

```yaml
guardrails:
  - name: bedrock
    type: bedrock_guardrail
    region: us-east-1
    guardrail_id: abc123def456
    guardrail_version: "1"
    on_failure: fail_closed
    timeout_ms: 1500
```

</TabItem>
<TabItem label="Azure Content Safety">

Calls `POST {url}/contentsafety/text:analyze?api-version=2024-09-01`. `url` is the resource endpoint, required. `key_env` required, sent as `Ocp-Apim-Subscription-Key`.

The messages are joined and sent in pieces of 10,000 characters, one call each, all within `timeout_ms`. A category with severity at or above `threshold` (0 to 7, default 4) is a finding: `hate`, `selfharm`, `sexual`, `violence`. Cannot mask.

```yaml
guardrails:
  - name: content-safety
    type: azure_content_safety
    url: https://contoso-safety.cognitiveservices.azure.com
    key_env: AZURE_CONTENT_SAFETY_KEY
    threshold: 4
    on_failure: fail_closed
```

</TabItem>
<TabItem label="Azure Prompt Shields">

Calls `POST {url}/contentsafety/text:shieldPrompt?api-version=2024-09-01`, with the same `url` and `key_env` as Content Safety.

The last user message is the prompt. Every other user message and every tool result is a document, where an indirect attack would hide. System and assistant text are not sent. A detected attack is `prompt_injection` or `indirect_prompt_injection`. Cannot mask.

```yaml
guardrails:
  - name: shields
    type: azure_prompt_shield
    url: https://contoso-safety.cognitiveservices.azure.com
    key_env: AZURE_CONTENT_SAFETY_KEY
    on_failure: fail_closed
```

</TabItem>
<TabItem label="Llama Guard">

Any model behind an OpenAI-compatible chat completions API, used as a classifier: `POST {url}/chat/completions` with `temperature: 0`. `url` and `model` required. `key_env` optional for a local server.

Without `prompt`, the conversation is sent as user and assistant turns, as a Llama Guard model expects. With `prompt`, any chat model can classify: the prompt is sent as one user message with `{conversation}` replaced by the messages.

The first line of the answer must be `safe` or `unsafe`. An optional second line of comma-separated categories gives the findings (`s1`, `s10`). Any other answer counts as a service failure. Cannot mask.

```yaml
guardrails:
  - name: llama-guard
    type: llama_guard
    url: http://127.0.0.1:8000/v1
    model: meta-llama/Llama-Guard-3-8B
    on_failure: fail_closed
    timeout_ms: 3000
  - name: classifier
    type: llama_guard
    url: https://api.openai.com/v1
    key_env: OPENAI_API_KEY
    model: gpt-4o-mini
    prompt: |
      You check messages sent to an AI assistant at a bank. Answer "safe" on the first line if the last
      message is fine. Otherwise answer "unsafe" on the first line and the reasons on the second, comma
      separated, from: fraud, injection, offtopic.

      {conversation}
    on_failure: fail_open
```

</TabItem>
<TabItem label="Google Model Armor">

Calls `POST {url}/v1/projects/{project_id}/locations/{region}/templates/{template_id}:sanitizeUserPrompt` with `{"userPromptData": {"text": ...}}` for a request, and `:sanitizeModelResponse` with `{"modelResponseData": {"text": ...}}` for an answer (`on: [answer]`). Default `url` `https://modelarmor.{region}.rep.googleapis.com`. `project_id`, `region` (the Model Armor location, such as `us-central1`) and `template_id` required. The template holds the filter settings, made in the Google Cloud console.

`key_env` required: a variable holding a Google OAuth access token, sent as `Authorization: Bearer`. It can be the same variable a Vertex AI provider uses. An access token lasts about an hour, so renew the variable (and reload) from your token source.

The texts are joined, with a blank line between them, into one text. `filterMatchState: MATCH_FOUND` blocks. Each filter that matched is a finding: `pi_and_jailbreak`, `malicious_uris`, `sdp`, `csam`, and for responsible AI, each category that matched, such as `dangerous` or `harassment`. `NO_MATCH_FOUND` allows only when `invocationResult` is `SUCCESS`: a filter that did not run is a service failure, and `on_failure` decides. Cannot mask.

```yaml
guardrails:
  - name: model-armor
    type: model_armor
    project_id: acme-prod
    region: us-central1
    template_id: strict
    key_env: GOOGLE_ACCESS_TOKEN
    on_failure: fail_closed
    on: [request, answer]
```

## Requests and answers

### What a request check reads

| Route | Read |
|---|---|
| `/v1/chat/completions`, `/v1/messages` | The system prompt, every text message or text block, text in tool results, text documents, search results. |
| `/v1/responses` | `instructions`, every `input` text, the `output` of `function_call_output` items, string values of `prompt.variables`. |
| `/v1/embeddings` | `input` strings. Token ID arrays are not text. |
| Gemini `generateContent` bodies | `systemInstruction` and every `contents` part's `text`. |

Tool definitions, tool arguments, images and files (a PDF or any base64 document) are not read. On a rule with guardrails, a body that names the same key twice in any object is refused with `unreadable_request`, because a guardrail would read one copy and the provider might act on the other.

When nothing is masked, the body is forwarded byte for byte. A masked body is re-serialized from its parsed JSON, keeping key order and numbers.

### Checking the answer

```yaml
guardrails:
  - name: no-secrets-out
    type: secrets
    action: block
    on: [answer]
  - name: no-pii-out
    type: pii
    action: mask
    on: [answer]
```

On an answer, a guardrail reads the model's text and the arguments of its tool calls: a chat completion's `choices[].message.content` and `tool_calls[].function.arguments`, a message's `text` blocks and `tool_use` input, a Responses answer's output text and `function_call` arguments, and a Gemini answer's `parts[].text` and `functionCall.args`. Arguments given as a JSON object are read as their JSON text; masked arguments must still be JSON, or the answer is withheld. Every type works there.

- `block` replaces the answer with a 403 `guardrail_blocked` refusal, for example `Refused: guardrail "no-secrets-out" withheld the model's answer, which contained aws_access_key (1). ...`. The answer was produced, so its usage still counts.
- `mask` rewrites the text in the answer. `warn` records only.
- Each checked answer gets an `answer_guardrails` record with the request's `id` and a `verdict` (`block`, `mask` or `pass`). The answer is passed on only once that record is written.
- Provider errors are not checked. A cached answer is checked like a fresh one.

### Streamed answers and buffer_stream

By default a stream is passed on as it arrives and is not checked. Its `answer_guardrails` record says `verdict: not_run`. Claude Code and most coding agents stream, so a rule that must check every answer sets `buffer_stream: true`:

```yaml
guardrails:
  - name: no-secrets-out
    type: secrets
    action: block
    on: [answer]
rules:
  - name: platform-team
    principals: { team: platform }
    models: ["*"]
    guardrails: [no-secrets-out]
    buffer_stream: true
```

Gantry then holds the whole stream (up to 64 MiB), joins the text its events carry so a secret split across events is found, and runs the answer guardrails.

| Verdict | The caller gets |
|---|---|
| Allowed | The events exactly as the provider sent them. |
| Masked | A stream with the masked text in the first event of each text and later events of that text empty. |
| Blocked | The 403 `guardrail_blocked` refusal in its own error shape, and none of the stream. |

The cost is latency: the caller sees no token until the model has written its last. `gantry check` refuses `buffer_stream: true` on a rule with no `on: [answer]` guardrail.

### Checking a stream as it comes: check_stream_every

`check_stream_every: <characters>` is the middle way. Gantry passes the stream on a window at a time: it holds each window until the answer guardrails, webhooks included, have read the whole text so far, then sends it. When a guardrail blocks, the stream stops there. The caller has the text checked before it, then an error event in its API's shape (`code: guardrail_blocked`), and the provider's stream is dropped. Blocked text never reaches the caller.

```yaml title="gantry.policy.yaml"
version: 1
providers:
  - name: openai
    kind: openai
    url: https://api.openai.com
    key_env: OPENAI_PROVIDER_KEY
    models: [gpt-4o-mini]
guardrails:
  - name: vendor
    type: webhook
    url: https://guard.example.com/check
    on_failure: fail_closed
    on: [answer]
rules:
  - name: everyone
    principals: { any: true }
    models: ["*"]
    guardrails: [vendor]
    check_stream_every: 300
```

- The caller sees text in bursts of about `check_stream_every` characters, each one guardrail round trip later than the model wrote it. 50 to 100000.
- Each check sends the whole answer so far, so a webhook sees context, and a phrase split across windows is still found.
- The record is one `answer_guardrails` record: `pass` at the end, or `block` with `stopped_after_chars`, the characters sent before the stop.
- Masking cannot rewrite text already sent: `gantry check` refuses a masking answer guardrail on such a rule, and a webhook that answers `mask` stops the stream like a block. Use `buffer_stream` to mask streamed answers.
- `gantry check` refuses it with `buffer_stream` on the same rule, and on a rule with no `on: [answer]` guardrail.

<Aside type="caution">
A Responses request that names `previous_response_id`, `conversation` or a stored `prompt` makes the provider add text Gantry never sees, so guardrails do not check it. Send `store: false` and the whole conversation in `input`.
</Aside>

## Realtime sessions

On a realtime session (OpenAI Realtime, Gemini Live) the rule's guardrails read each text the session carries, and the session's record lists what they found, without the text.

| Text | Read as | When a guardrail blocks |
|---|---|---|
| The caller's text events: `conversation.item.create` text, `session.update` and `response.create` instructions; Gemini's `clientContent` turns and `realtimeInput.text` | request | The event is dropped. OpenAI gets an `error` event with `guardrail_blocked`; Gemini, which has no error event, has its session ended. A `mask` sends the event on masked. |
| The transcript of the caller's speech: `conversation.item.input_audio_transcription.completed`, Gemini's `inputTranscription` | request | The session ends with close code 1008. |
| What the model said: `response.output_audio_transcript.done`, `response.output_text.done`, Gemini's `outputTranscription` and model text | answer (`on: [answer]`) | The session ends with close code 1008. |

A transcript is of speech already heard, so a `mask` there is recorded and not applied. Audio itself is not read. Gemini sends model text in pieces, and each piece is read alone, so a finding split across two pieces is missed. The session's `realtime_session` record has `ended_by: guardrail` and a `guardrails` list.

## Refusal codes

| Code | Status | Cause |
|---|---|---|
| `guardrail_blocked` | 403 | A guardrail blocked the request or the answer, or a `fail_closed` service could not check it. |
| `tool_not_allowed` | 403 | The request declares, or the answer calls, a function tool the rule's `tools:` does not allow. See [Tool permissions](/governance/tool-permissions/). |
| `transform_failed` | 502 | A `fail_closed` transform could not rewrite the request or answer. See [Transforms](/governance/transforms/). |
| `unreadable_request` | 400 | A body naming the same key twice on a rule with guardrails. |
