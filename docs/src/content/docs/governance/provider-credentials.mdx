A provider key is what Enterplace sends to OpenAI, Anthropic or another vendor. Callers never see it: they send their [Enterplace key](/governance/keys/), and Enterplace sends the provider key. A provider takes its key from one of three places:

| Field | Where the key is | Rotation |
|---|---|---|
| `key_env` | An environment variable of the gateway | A restart |
| `key_file` | A file the gateway reads once a second | Within 2 seconds, on that gateway |
| `credential` | The [store](/operations/store/), sealed with AES-256-GCM under your master key | Within 2 seconds, on every gateway on the store |

This page covers `credential`, and a rule's opt-in to a caller's own provider key.

## Stored credentials

A stored credential is added once, in the console or through the admin API, and named by the providers that use it:

```yaml title="enterplace.policy.yaml"
store: { postgres_url_env: DATABASE_URL }
providers:
  - name: openai
    kind: openai
    url: https://api.openai.com
    credential: openai-prod
    models: [gpt-4o, gpt-4o-mini]
```

A provider takes one of `key_env`, `key_file` or `credential`. `credential` needs `store:` in the policy, and is not allowed on `bedrock`, which signs with AWS keys.

### The master key

Every value is sealed with AES-256-GCM under a master key that you hold. Enterplace reads it from `ENTERPLACE_MASTER_KEY`, or from the file `ENTERPLACE_MASTER_KEY_FILE` names: 64 hex characters, made once.

```bash
openssl rand -hex 32   # keep it in your secret manager
export ENTERPLACE_MASTER_KEY=<the 64 hex characters>
```

- Every gateway on one store needs the same master key. The first gateway seals a check value with it; a gateway started with another master key is refused at start, with the fix.
- The database holds sealed bytes only. Someone who reads the database without the master key reads no provider key.
- Each value is sealed with its credential's name as associated data, so a sealed value copied to another row does not open.
- Without a master key, credentials are off: the gateway starts on `key_env` and `key_file` as before, and the console page and the admin API say how to turn them on. A policy that names a credential is then refused at start.
- A lost master key cannot be recovered. Delete the credentials (`DELETE FROM enterplace_credentials; DELETE FROM enterplace_master;`) and add them again under a new one.

### Add, rotate and remove

In the console, open **Provider credentials**. Or call the [admin API](/reference/admin-api/) with an admin key:

```bash
# Add
curl -X POST https://enterplace.example.com/admin/credentials \
  -H "Authorization: Bearer $ENTERPLACE_ADMIN_KEY" \
  -d '{"name": "openai-prod", "provider": "openai", "value": "sk-..."}'

# Rotate: every gateway sends the new value within 2 seconds
curl -X PUT https://enterplace.example.com/admin/credentials/openai-prod \
  -H "Authorization: Bearer $ENTERPLACE_ADMIN_KEY" \
  -d '{"value": "sk-..."}'

# List: names, never values
curl https://enterplace.example.com/admin/credentials \
  -H "Authorization: Bearer $ENTERPLACE_ADMIN_KEY"

# Remove
curl -X DELETE https://enterplace.example.com/admin/credentials/openai-prod \
  -H "Authorization: Bearer $ENTERPLACE_ADMIN_KEY"
```

A credential is shown as its name, the vendor it is for, `...` and the last 4 characters of its value, who added it and when, and who rotated it last and when. The value is never shown again: not in a page, an API answer or an audit record.

- **Rotation.** Each gateway reads the store every half second and puts the new value in place at its next one-second check: within 2 seconds, with no restart and no new policy version. A request already sent finishes with the value it was sent with.
- **Removal.** A credential a provider of the policy in use names is not removed (`credential_in_use`): point the provider elsewhere first. A gateway whose credential is removed by another keeps the value it has and reports it; it would not start again without it.
- **Audit.** Each add, rotate and remove is an `admin` record with `action` `add_credential`, `rotate_credential` or `remove_credential`, the admin who did it, and a target of the name, the vendor and the fingerprint. Never the value.

`enterplace check` connects to the store when its variable is set and names each credential the store does not hold, with its line. Without the variable it warns that the names were not checked.

## A caller's own provider key

A rule may let callers pay for their own requests with their own provider key:

```yaml title="enterplace.policy.yaml"
rules:
  - name: research
    principals: { team: research }
    models: [gpt-4o]
    caller_provider_key: allowed
```

The caller still sends their Enterplace key as always, and adds their provider key in one header:

```bash
curl https://enterplace.example.com/v1/chat/completions \
  -H "Authorization: Bearer $ENTERPLACE_KEY" \
  -H "x-enterplace-provider-key: $MY_OPENAI_KEY" \
  -d '{"model": "gpt-4o", "messages": [{"role": "user", "content": "hello"}]}'
```

Enterplace sends that key to the provider in place of its own, in the header the provider expects. Everything else is as on any request: the Enterplace key identifies the caller, the rule's models, rate and token limits, guardrails and kill switches apply, and the request is recorded before it is sent.

| `caller_provider_key` | A request with `x-enterplace-provider-key` |
|---|---|
| `refused` (default) | Refused with `caller_provider_key_not_allowed` (403). Never forwarded, and never sent with Enterplace's key instead. |
| `allowed` | Sent with the caller's key. Its spend is recorded as caller-paid and not counted against budgets. |
| `allowed_budgeted` | As `allowed`, and its spend counts against budgets as any other. |

- **Budgets.** A budget limits what the organization pays, and with `allowed` the caller pays the provider, so caller-paid spend is not reserved or counted. Rate and token limits still hold. Use `allowed_budgeted` when a budget should cap use whatever key pays for it.
- **Never a Enterplace key.** A request without a Enterplace key is refused with `no_key`, whatever provider key it carries.
- **Never elsewhere.** The header is taken off the request as soon as it is read. It is never logged, never echoed, and never sent to a guardrail webhook, a trace or a fallback provider: with a caller's key, retries stay on the provider the model is served by.
- **The record.** The decision record says `caller_provider_key: true` and `caller_provider_key_sha256`, the first 8 hex characters of the key's SHA-256. The usage record says `caller_paid: true` and `budget: counted` or `not_counted`.
- **Not for Bedrock.** A model served on Bedrock is refused with `caller_provider_key_unsupported`: Enterplace signs Bedrock requests with AWS keys.
- Sent twice, the header is refused with `ambiguous_key`.

<Aside type="caution">
A caller's key is theirs to manage. Enterplace does not check that it is valid before sending it: a wrong key comes back as the provider's own 401.
</Aside>
