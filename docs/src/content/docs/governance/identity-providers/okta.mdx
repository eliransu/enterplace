Okta can sign people in to the admin console with OpenID Connect (`console.sso`) or SAML 2.0 (`console.saml`). In both, Okta sends the person's groups, and Enterplace maps the group names to a console role and, at `enterplace login`, to a team.

The examples use `https://enterplace.example.com` for your Enterplace address and the groups `enterplace-admins` and `enterplace-viewers`.

## OpenID Connect

<Steps>

1. In the Okta Admin Console, go to **Applications and Resources** > **Applications**, click **Create App Integration**, select **Classic experience** if Okta asks, then choose **OIDC - OpenID Connect** as the sign-in method and **Web Application** as the application type.

2. Under **Sign-in redirect URIs**, enter `https://enterplace.example.com/console/sso/callback`. Keep the **Authorization Code** grant type. `enterplace login` comes back on the same URI, so you add nothing for the CLI.

3. Under **Assignments** > **Controlled access**, choose **Limit access to selected groups** and add the groups that should reach the console (for example `enterplace-admins` and `enterplace-viewers`), then save.

4. On the app's settings page, copy the **Client ID**. Under **Client Credentials**, choose **Client secret** as the client authentication and copy the secret. Enterplace sends a PKCE challenge either way, so you can also require PKCE.

5. Put the groups in the ID token. With the org authorization server, set `scopes` as shown after these steps and configure the app's **Groups claim filter** on its **Sign On** tab (`groups`, **Matches regex**, `^enterplace-.*`). With a custom authorization server, add a claim instead. For a custom authorization server, go to **Security** > **API**, open the authorization server (for example `default`), and on the **Claims** tab click **Add Claim**:
   - **Name**: `groups`
   - **Include in token type**: **ID Token**, **Always**
   - **Value type**: **Groups**
   - **Filter**: **Matches regex** with `^enterplace-.*`, so only the console groups go in the token
   - **Include in**: any scope

6. Your issuer is the authorization server's issuer: `https://<your-org>.okta.com` for the org server, `https://<your-org>.okta.com/oauth2/default` for the `default` custom server.

</Steps>

<Aside>
Okta's org authorization server (issuer `https://<your-org>.okta.com`) puts the app's groups claim in the ID token only when the request asks for the `groups` scope. Add `scopes: openid email profile groups` to `console.sso`, as in the second example. A custom authorization server with the claim above needs no extra scope.
</Aside>

```yaml title="enterplace.policy.yaml"
console:
  sso:
    issuer: https://example.okta.com/oauth2/default
    client_id: 0oa1b2c3d4e5f6g7h8i9
    client_secret_env: ENTERPLACE_SSO_SECRET
    redirect_url: https://enterplace.example.com/console/sso/callback
    allowed_domains: [example.com]
    role_claim: groups
    admin_values: [enterplace-admins]
    read_only_values: [enterplace-viewers]
```

With the org authorization server instead:

```yaml title="enterplace.policy.yaml"
console:
  sso:
    issuer: https://example.okta.com
    client_id: 0oa1b2c3d4e5f6g7h8i9
    client_secret_env: ENTERPLACE_SSO_SECRET
    redirect_url: https://enterplace.example.com/console/sso/callback
    scopes: openid email profile groups
    allowed_domains: [example.com]
    role_claim: groups
    admin_values: [enterplace-admins]
    read_only_values: [enterplace-viewers]
```

Set the secret where Enterplace runs: `ENTERPLACE_SSO_SECRET=...`. The `issuer` must match the `iss` in Okta's ID tokens exactly, with no trailing slash.

## SAML 2.0

<Steps>

1. In the Okta Admin Console, go to **Applications and Resources** > **Applications**, click **Create App Integration**, select **Classic experience** if Okta asks, and choose **SAML 2.0**. Give the app a name.

2. In **General Settings**, select **Do not display application icon to users**. The Okta dashboard tile starts an IdP-initiated sign-in, which Enterplace refuses. People start at `/console` instead.

3. In the SAML settings:
   - **Single sign-on URL**: `https://enterplace.example.com/console/saml/acs`, with **Use this for Recipient URL and Destination URL** selected
   - **Audience URI (SP Entity ID)**: `https://enterplace.example.com/console/saml/metadata`
   - **Name ID format**: EmailAddress {/* option label not confirmed in Okta's public reference, 2026-11 */}
   - **Application username format**: Email

4. Open **Show Advanced Settings** and check the signing settings: the assertion signed, the signature and digest algorithms SHA-256, and **Assertion Encryption** off. Enterplace refuses SHA-1 and does not read encrypted assertions.

5. Add an attribute statement named `email` with the value `user.email`.

6. Add a group attribute statement named `groups` with the filter **Matches regex** and `^enterplace-.*`. Okta sends one value per matching group. (Okta now treats group attribute statements as the legacy configuration: on an existing app, open the **Sign On** tab, find **Attribute statements** and expand **Show legacy configuration**.)

7. Finish the wizard as an internal app. On the app's **Sign On** tab, copy the identity provider single sign-on URL and issuer, and download the certificate from **SAML Signing Certificates**. The metadata linked there carries the same three values.

8. On the **Assignments** tab, assign the `enterplace-admins` and `enterplace-viewers` groups.

</Steps>

{/* not checked: the certificate is a placeholder */}
```yaml title="enterplace.policy.yaml"
console:
  saml:
    idp_entity_id: http://www.okta.com/exk1a2b3c4d5e6f7g8h9
    idp_sso_url: https://example.okta.com/app/example_enterplace_1/exk1a2b3c4d5e6f7g8h9/sso/saml
    idp_certificate: |
      -----BEGIN CERTIFICATE-----
      MIIDqDCCApCgAwIBAgIGAY...
      -----END CERTIFICATE-----
    sp_entity_id: https://enterplace.example.com/console/saml/metadata
    acs_url: https://enterplace.example.com/console/saml/acs
    email_attribute: email
    role_attribute: groups
    admin_values: [enterplace-admins]
    read_only_values: [enterplace-viewers]
    allowed_domains: [example.com]
```

When Okta rotates its signing certificate, paste the new PEM block under the old one in `idp_certificate`, then remove the old one after the switch.

## Teams and custom roles

The group values work beyond the two built-in roles. A custom role under `roles:` takes them in `sso_values`, and so does a team under `teams:`. At `enterplace login`, a person listed in a team's `members` gets that team, otherwise the first team whose `sso_values` match one of their groups, otherwise `self_issue.team`.

## Check it

<Steps>

1. Open `https://enterplace.example.com/console` in a private window and click the sign-in button.

2. Sign in at Okta as a member of `enterplace-admins`. The console opens with the admin role.

3. Sign in as a member of `enterplace-viewers` only. The console opens read only.

</Steps>

A refusal with `sso_role` means the person's groups held no value from `admin_values`, `read_only_values` or a role's `sso_values`. Check the group filter in Okta and the exact group names in the policy.
