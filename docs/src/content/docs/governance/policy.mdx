The policy file names the providers Gantry forwards to and the rules that decide who may use which model. `gantry check` and `gantry serve` read it the same way, so a file that passes one is accepted by the other.

Any key Gantry does not know is an error. Nothing in the file is ignored.

## Example

```yaml title="gantry.policy.yaml"
version: 1
providers:
  - name: openai
    kind: openai
    url: https://api.openai.com
    key_env: OPENAI_PROVIDER_KEY
    models: [gpt-4o-mini, gpt-4o]
  - name: anthropic
    kind: anthropic
    url: https://api.anthropic.com
    key_env: ANTHROPIC_PROVIDER_KEY
    models: [claude-sonnet-5-5, claude-haiku-5-5]
  - name: local
    kind: openai
    url: http://127.0.0.1:11434
    allow_private: true
    models: [gpt-oss:20b]
guardrails:
  - name: no-secrets
    type: secrets
    action: block
  - name: mask-pii
    type: pii
    action: mask
rules:
  - name: maya-only
    principals: { name: maya.cohen }
    models: ["*"]
  - name: payments-team
    principals: { team: payments }
    models: [gpt-4o-mini, claude-sonnet-5-5, claude-haiku-5-5]
    guardrails: [no-secrets, mask-pii]
    budget: { usd: 2000, per: month }
    rate: { rpm: 600, tpm: 200000 }
    cache: { ttl_seconds: 300 }
  - name: everyone-else
    principals: { any: true }
    models: []
prices:
  gpt-oss:20b: { input: 0, output: 0 }
audit: { path: /var/lib/gantry/gantry-audit.jsonl }
```

```bash
gantry check gantry.policy.yaml
```

```text
gantry.policy.yaml is valid: 3 rules, 0 keys, 3 providers: openai (openai) at https://api.openai.com, anthropic (anthropic) at https://api.anthropic.com, local (openai) at http://127.0.0.1:11434.
```

## Rules and first match

Rules are read top to bottom. **The first rule that names the caller decides.** Later rules are never consulted, even if they would allow the model.

- A caller no rule names is refused with `no_rule`.
- A caller whose first matching rule does not list the model is refused with `model_not_allowed`. The message lists what that rule allows.
- A model a rule allows must still be served by a provider, or the request is refused with `unknown_model`.

In the example, `maya.cohen` of team `payments` may use every model, because `maya-only` comes first. The rest of `payments` gets the three models listed. Everyone else gets nothing, with a message that says so.

### Principals

Each rule names exactly one principal. The name and team come from the caller's [Gantry key](/governance/keys/).

| Principal | Matches |
|---|---|
| `{ name: maya.cohen }` | The one key, or keys, issued to that name. Keys from `gantry login` are named by email. |
| `{ team: payments }` | Every key issued to that team. |
| `{ tag: ci }` | Every key whose entry carries that tag. A tag sent in a header never picks a rule. |
| `{ any: true }` | Every identified caller. Put it last as the catch-all. |

A rule with `org: <org>` names only callers of that [organization](#organizations); a rule without one names callers of every organization.

### Models

| Value | Meaning |
|---|---|
| `[gpt-4o-mini, claude-sonnet-5-5]` | Exact model names, or alias names. |
| `["*"]` | Every model any provider serves. `"*"` must stand alone. |
| `[]` | No model. The rule matches the caller and refuses every request. |

A key can carry its own `models:` list that narrows its rule further, never widens it. See [Keys](/governance/keys/#limits-per-key).

### Providers

| Field | Type | Default | Description |
|---|---|---|---|
| `name` | string | required | Letters, digits, `.`, `-`, `_` and `@`, up to 100 characters. Unique. Audit records name the provider by it. |
| `kind` | string | required | `openai`, `anthropic`, `azure`, `bedrock`, `gemini`, `vertex` or `vertex_anthropic`. |
| `url` | string | required | Base URL, `http://` or `https://`, no query, fragment or login. May carry the vendor's path, such as `https://api.groq.com/openai/v1`. Not used by `bedrock`. |
| `key_env` | string | required | Name of the environment variable holding the provider key. Optional for an `openai` provider with `allow_private: true`. Not used by `bedrock`, which signs with the AWS credentials it finds. Optional for `vertex` and `vertex_anthropic`, which otherwise sign in to Google Cloud themselves. |
| `key_file` | string | none | Instead of `key_env`: the path of a file holding the provider key. Read at start and again within 2 seconds of a change, without a restart. A relative path is read from where Gantry runs. Not used by `bedrock`. |
| `credential` | string | none | Instead of `key_env` or `key_file`: the name of a [provider credential](/governance/provider-credentials/) kept in the store, sealed under `GANTRY_MASTER_KEY`. | `models` | list | required | Exact model names this provider serves. Not empty, no `"*"`. A model may be listed by one provider only. |
| `retries` | integer | `0` | 0 to 5. Retries after a connection failure, timeout, 429 or 5xx, before any byte reaches the caller. |
| `fallback` | string | none | Another provider of the same API to try after the retries fail. |
| `accept_chat` | boolean | `false` | `anthropic`, `bedrock` and `vertex_anthropic`: also take chat completions requests, translated to messages. |
| `accept_messages` | boolean | `false` | `openai`, `azure`, `gemini` and `vertex`: also take messages requests (Claude Code), translated both ways. |
| `allow_private` | boolean | `false` | Let `url` point at this machine or a private network. |
| `deployments` | map | `azure` only | Model name to Azure deployment name. |
| `api_version` | string | `azure` only | The Azure OpenAI `api-version`. |
| `region` | string | `bedrock` only | The AWS region. |
| `role_arn` | string | `bedrock` only | An IAM role to assume with the AWS credentials Gantry finds. |
| `model_ids` | map | `bedrock` only | Model name to Bedrock model ID. |
| `batch` | map | `bedrock`, `vertex`, `vertex_anthropic` only | `{ bucket: s3://<bucket>/<prefix>/ or gs://<bucket>/<prefix>/, role_arn: <IAM role>, url: <batch API>, storage_url: <S3 or Cloud Storage endpoint> }`. Runs `/v1/batches` as Bedrock batch inference or Vertex AI batch prediction on files Gantry keeps in the bucket. `role_arn` (the service role Bedrock assumes) is required for `bedrock` and refused otherwise; `url` and `storage_url` are for private endpoints. See [Files, batches and realtime](/providers/batches-and-realtime/#bedrock-and-vertex-ai-batches). |

Per-kind routes, headers and examples are in [Providers](/providers/overview/).

### Rules

| Field | Type | Default | Description |
|---|---|---|---|
| `name` | string | required | Letters, digits, `.`, `-`, `_` and `@`. Shown in refusals and audit records. |
| `principals` | map | required | Exactly one of `{ team: ... }`, `{ name: ... }`, `{ tag: ... }`, `{ any: true }`. |
| `models` | list | required | Exact names, `["*"]`, or `[]`. Optional for a rule that includes profiles: theirs are added to the rule's. |
| `org` | string | none | Name only callers of this organization, one `orgs:` lists. |
| `profiles` | list | `[]` | [Access profiles](#access-profiles) the rule includes, in order. |
| `customers` | list | `[]` | End customers a caller may name in `x-gantry-customer`, or `["*"]` for any. See [End customers and tags](/governance/budgets-and-rate-limits/#end-customers-and-tags). |
| `tags` | list | `[]` | Tags a caller may send in `x-gantry-tags`, or `["*"]` for any. |
| `parallel` | integer | none | Most requests in flight at once, 1 to 100000, counted where the budget is. |
| `guardrails` | list | `[]` | Names from the top-level `guardrails:`, run in this order. An undefined name is an error. |
| `budget` | map or list | none | `{ usd: <above 0>, per: <period>, tz: <zone>, models: [...] }`, or a list of them. See [Budgets and rate limits](/governance/budgets-and-rate-limits/#budgets). |
| `rate` | map | none | `{ rpm: 1 to 1000000, tpm: 1 to 1000000000 }`, either or both. A file upload and a batch creation count as one request against `rpm`. |

The most lines one batch may hold (`batch_too_many_lines`), and the most batches a person under the rule may have not yet ended (`batch_too_many_open`). See [Files, batches and realtime](/providers/batches-and-realtime/#batch-limits). |
| `file_retention_days` | integer | none | 1 to 30. Days a file uploaded under the rule is kept. See [Retention](/providers/batches-and-realtime/#retention). |
| `cache` | map | none | `{ ttl_seconds: 1 to 86400, scope: person or team, semantic: { model, threshold } }`. See [Caching](/routing/caching/). |
| `prompt_cache` | string | `off` | `auto` marks cache breakpoints on Anthropic messages requests. See [Caching](/routing/caching/#prompt-caching). |
| `buffer_stream` | boolean | `false` | Hold a streamed answer whole so `on: [answer]` guardrails check it first. Needs a guardrail with `on: [answer]`. |
| `check_stream_every` | integer | none | Check a streamed answer every this many characters, sending only what was checked. See [guardrails](/governance/guardrails/#checking-a-stream-as-it-comes-check_stream_every). |
| `passthrough` | list | `[]` | Native provider paths the rule may reach as sent. See [Passthrough](#passthrough). |
| `from` | list | `[]` | Address ranges the rule's callers may send from. See [Source address ranges](/governance/access-control/#source-address-ranges). |
| `regions` | list | none | Residency: the regions an alias deployment must be labelled with. Anything else is refused, never sent elsewhere. See [Residency](/routing/strategies/#residency-regions). |
| `tags` | list | `[]` | Tags callers may send in `x-gantry-tags`. Any other is refused with `tag_not_allowed`. |
| `shadow_until` | string | none | A UTC date or time, such as `2026-12-31` or `2026-12-31T18:00:00Z`. Until then what the rule would refuse (its models, `rate`, `parallel`, `regions` and budgets) is forwarded and recorded as `would_refuse`. See [Observe mode](#observe-mode). |
| `caller_provider_key` | string | `refused` | Whether a caller may send their own provider key in `x-gantry-provider-key`: `refused`, `allowed` (sent in place of Gantry's, spend recorded as caller-paid and not counted against budgets) or `allowed_budgeted` (counted). See [A caller's own provider key](/governance/provider-credentials/#a-callers-own-provider-key). |

Every model a budgeted rule reaches must have a price, built in or under `prices:`. For `models: ["*"]` that is every model every provider serves. `gantry check` refuses a file that breaks this.

## Observe mode

`mode: observe` turns the policy into a dry run. Every request a valid key sends for a model Gantry serves is forwarded, and each decision that would have refused it goes on its record as [`would_refuse`](/reference/audit-records/#would_refuse), in the same audit chain. Use it for a first rollout, or before you enforce a new rule, budget or guardrail.

```yaml
version: 1
mode: observe
providers:
  - name: openai
    kind: openai
    url: https://api.openai.com/v1
    key_env: OPENAI_API_KEY
    models: [gpt-4o-mini, gpt-4o]
rules:
  - name: payments-team
    principals: { team: payments }
    models: [gpt-4o-mini]
    budget: { usd: 200, per: month }
```

What observe mode lets through, and records:

- a model the rule does not allow, a caller no rule names, and a key's own `models:` list
- budgets, `rate` (`rpm`, `tpm`) and `parallel`, from rules, keys and the `limits:` list
- guardrails: they record what they find, as in their [shadow period](/governance/guardrails/#shadow-mode), and neither block nor mask
- `regions`, a rule's or key's `from:` address ranges (`ip_not_allowed`), and a tag or customer the rule does not list
- a budgeted request whose cost cannot be estimated: `no_price`, `max_tokens_needed` and `stored_context` are recorded with that code, nothing is reserved, and the answer's cost still counts

What it still refuses, because forwarding would open the gateway:

- a missing, unknown, expired or revoked key
- a model no provider serves (`unknown_model`)
- a [kill switch](/governance/kill-switches/): a stop button always works

Spend and limits still count. A request a budget would refuse is charged to that budget's counter, and a request over `rpm`, `tpm` or `parallel` holds its tokens and its place as an enforced one does, so the numbers are real when you switch to enforce. `gantry check` warns while observe mode is on, and the console's audit log shows "Observe mode: nothing is blocked". Remove the line, or write `mode: enforce`, and the next request after the [reload](#reloading) is enforced.

To try one feature while the rest is enforced, give it a `shadow_until` date instead: a rule, each budget, and each `limits:` entry take one, as guardrails do. Until that date it records what it would refuse; after it, it enforces. See [Budgets and rate limits](/governance/budgets-and-rate-limits/#trying-a-limit-first).

Observe mode covers every governed route: the model routes (chat, messages, responses, embeddings and the rest), files, batches, fine-tuning jobs, realtime sessions, passthrough calls and MCP tools, prompts and resources. In observe mode `tools/list` lists every tool of the MCP servers. A passthrough path with a `..`, `.` or `%` segment is refused in both modes, and an MCP tool that waits for approval still waits.

## Organizations

One install may hold several organizations, each with its own rules, budgets, keys and console view:

```yaml title="gantry.policy.yaml"
version: 1
providers:
  - name: openai
    kind: openai
    url: https://api.openai.com
    key_env: OPENAI_API_KEY
    models: [gpt-4o-mini]
orgs: [acme, globex]
rules:
  - name: acme-everyone
    org: acme
    principals: { any: true }
    models: [gpt-4o-mini]
  - name: globex-data
    org: globex
    principals: { team: data }
    models: [gpt-4o-mini]
limits:
  - { org: acme, budget: { usd: 20000, per: month } }
  - { org: globex, budget: { usd: 5000, per: month }, parallel: 50 }
```

- A key belongs to the organization its entry names (`org: acme`, or `gantry key new --org acme`). A key without one belongs to none, and counts as before organizations.
- A rule with `org:` names only that organization's callers. Teams, people, customers, tags and models are counted per organization, so `team:acme/payments` and `team:globex/payments` are two counters.
- A key, rule, limit or role naming an organization `orgs:` does not list is refused by `gantry check`, so a misspelling never becomes a tenant of its own.
- A console role kept to an organization (a key with `org:` and a role, or a role with `org:`) sees only that organization's keys, records and spend, issues keys only in it, and cannot set kill switches or change provider credentials, which act on the whole install.
- Records carry `org`. Every organization's records are in the install's one audit chain.

## Access profiles

A profile is a named set of models, guardrails, tools and limits that rules include:

```yaml title="gantry.policy.yaml"
version: 1
providers:
  - name: openai
    kind: openai
    url: https://api.openai.com
    key_env: OPENAI_API_KEY
    models: [gpt-4o-mini, o3]
guardrails:
  - name: no-secrets
    type: secrets
    action: block
profiles:
  - name: standard
    models: [gpt-4o-mini]
    guardrails: [no-secrets]
    budget: [{ usd: 10, per: day }, { usd: 100, per: month }]
    rate: { rpm: 60, tpm: 100000 }
    parallel: 4
rules:
  - name: payments
    principals: { team: payments }
    profiles: [standard]
    models: [o3]
    budget: { usd: 20, per: day }
  - name: everyone-else
    principals: { any: true }
    profiles: [standard]
```

- **Models and tools** of the profiles are added to the rule's. **Guardrails** of the profiles run first, then the rule's, each once.
- **Limits**: the rule's own value wins, then the first profile listed that sets it. A budget is overridden only by one over the same period and models. Above, `payments` gets $20 a day (its own), $100 a month, 60 rpm, 100000 tpm and 4 in flight (from `standard`).
- What the rule overrode is listed in the [explanation](/governance/budgets-and-rate-limits/#why-was-this-allowed-or-refused) under `rule.overrides`, and each limit names the profile it came from.

| Field | Type | Description |
|---|---|---|
| `name` | string | Unique. |
| `models`, `guardrails`, `tools` | list | As on a rule. |
| `budget`, `rate`, `parallel` | | As on a rule. |

## Console roles

Every install has two roles: `admin` (every permission) and `read_only` (`see_keys`, `see_spend`, `see_records`). The policy may define more:

```yaml title="gantry.policy.yaml"
version: 1
providers:
  - name: openai
    kind: openai
    url: https://api.openai.com
    key_env: OPENAI_API_KEY
    models: [gpt-4o-mini]
orgs: [acme]
rules:
  - name: everyone
    principals: { any: true }
    models: [gpt-4o-mini]
roles:
  - name: finance
    permissions: [see_spend, see_records]
    sso_values: [finance]
  - name: acme-keys
    permissions: [see_keys, issue_keys, revoke_keys]
    org: acme
```

| Permission | Lets a person |
|---|---|
| `see_keys` | See keys and who holds them (console People, `GET /admin/keys`). |
| `issue_keys` | Issue keys (`POST /admin/keys`). A role may give a new key only a role whose permissions it holds itself. |
| `revoke_keys` | Revoke keys. |
| `kill` | Set and clear kill switches. |
| `credentials` | Add, rotate and remove provider credentials. |
| `edit_policy` | Change the policy, where the console offers it, and backtest a guardrail (`POST /admin/guardrails/test`). |
| `see_spend` | See spend and budgets, and the explanation of a caller's limits (`GET /admin/explain`). |
| `see_records` | See the audit log. |
| `see_bodies` | See captured request and answer bodies, where capture is on. |

A key gets a role with `role:` in its entry (`gantry key new --role finance`); `admin: true` is the role `admin`. A person signing in through [single sign-on](/governance/single-sign-on/) gets `admin` for an `admin_values` claim value, else the first role whose `sso_values` the claim holds, else `read_only` for a `read_only_values` value. The console and the admin API check the permission each page and action needs on every request, and a refusal names the role and the missing permission (`not_permitted`). Roles live in the policy file, so a change to them is reviewed in git like any rule.

## Passthrough

Gantry serves the common routes itself: chat completions, messages, responses, embeddings, images, audio, moderations, rerank, legacy completions, files, batches, fine-tuning jobs and realtime sessions. For any other endpoint of a provider's own API (Bedrock or Vertex batch jobs, Gemini's native methods), send the request to `/passthrough/<provider>/<path>`. Gantry swaps your Gantry key for the provider key and sends the request to that path unchanged.

A rule reaches nothing this way unless it lists the provider and the path prefixes:

```yaml title="gantry.policy.yaml"
rules:
  - name: data-team
    principals: { team: data }
    models: [gpt-4o-mini]
    passthrough:
      - { provider: openai, paths: [/v1/batches, /v1/files] }
```

```bash
curl https://gantry.example.com/passthrough/openai/v1/batches/batch_123 \
  -H "Authorization: Bearer $GANTRY_KEY"
```

- A prefix matches whole path segments: `/v1/batches` reaches `/v1/batches/batch_123/cancel`, not `/v1/batchesX`. A path with a `.`, `..` or escaped segment is refused, so a listed prefix cannot be climbed out of.
- A body with a `model` field is checked against the rule's models, as on every other route. A body without one is allowed by the path alone.
- Each call is recorded, counts against the rule's budget and rate, and is charged from the `usage` the provider returns, priced by the body's model. A call with no model is recorded with no cost.
- Guardrails read every string in the body, whatever its shape. A call with no body (a `GET`) is recorded with `guardrails: not_run: the request has no body`.
- Only providers of kind `openai`, `anthropic`, `azure` and `gemini`. Bedrock and Vertex requests must be signed or translated, so `gantry check` refuses them here.
- The provider key can reach any path you list. List the endpoints people need, never an account's admin API.

## Order of checks

Each request passes these steps in order and stops at the first that refuses it.

<Steps>

1. **Identify and decide.** Look up the key, check for an active [kill switch](/governance/kill-switches/), find the first rule that names the caller, check the model, choose the provider.

2. **Guardrails.** The rule's built-in detectors, then its vendors and webhooks, in the order written.

3. **Cache.** A hit is answered here.

4. **Rate limit.** Requests and tokens per minute, then requests in flight, for the rule, the key and every `limits:` scope.

5. **Budget.** The request reserves the most it could cost against every budget that applies.

6. **Record.** The decision record is written. Nothing is sent before it is on file.

7. **Forward.** Sent, retried and passed to the fallback as the provider allows. An `attempts` record follows when more than one try was made, and a usage record when the answer ends.

</Steps>

Guardrails run before the cache on purpose. A cached answer is served only to a request that passes the guardrails in force now, so a guardrail added by a reload also covers answers cached before it. A request a guardrail blocks never reads the cache and never counts against a rate limit or a budget.

The cache key, the budget's estimate and the recorded usage are all of the body actually sent: masked if a guardrail masked it, translated if it was translated.

For the full path, from body limits to provider errors, see [How it works](/getting-started/how-it-works/).

## Reloading

Save the policy file or the keys file and Gantry uses the new version within 2 seconds, without a restart. `kill -HUP <pid>` makes it check at once. Gantry compares the SHA-256 of both files once a second, so editors that save by renaming and symlinks switched to another file are both noticed.

- **A change that passes** the same checks as `gantry check` is written to the audit log as a `config_loaded` record, then decides every request after it. The policy and keys switch together.
- **A change that fails** is not used. Gantry keeps the version it has, prints every problem to stderr, writes one `config_rejected` record per distinct pair of files, and uses the next save that passes.
- **A request decided before the switch** finishes under the decision it got, its stream included.

```text
/etc/gantry/gantry.policy.yaml:12: "modles" is not a key Gantry knows. Did you mean "models"?
gantry: the change to /etc/gantry/gantry.policy.yaml or /etc/gantry/gantry.keys.yaml is not used: 1 problem above. Gantry keeps deciding with the version it has (policy 5d41402a, keys 7c211433) and uses the next save that passes `gantry check`.
```

Rules, guardrails, budgets, rate limits, caches, prices, keys and providers all change without a restart. A provider may be added, removed, or given a new `url`, `kind`, `key_env`, `key_file`, `credential`, `region` or `api_version`: the reload builds a new route for it, reading its key at that moment, and requests already sent finish on the old one. A provider whose key cannot be read then (an unset `key_env`, a missing `key_file`) makes the reload fail, and the version in use is kept. Spend already counted and the cache are kept across a reload.

These need a restart, and a change to one of them is rejected with that reason:

- the audit log path,
- the `mcp` servers,
- the store's `postgres_url_env` or `policy_from`,
- a new provider key value in a `key_env` variable of a provider that did not change. A new key in a `key_file` is used without a restart: see [Provider keys](/providers/overview/#provider-keys).

`GET /healthz` names the hashes in use and those of a rejected version still on disk:

```json
{"status":"ok","policy_sha256":"5d41...","keys_sha256":"7c21...","rejected":null}
```

## Policy versions in the store

With a store, the policy can live in Postgres instead of the file, as versions an admin edits in the [console](/operations/console-editing/) or the admin API. Each save is a new version, checked exactly as `gantry check` checks a file, recorded in the audit chain, and used by every gateway on the database within 2 seconds, without a restart.

```yaml title="gantry.policy.yaml"
store: { postgres_url_env: DATABASE_URL, policy_from: store, approval: true }
```

| Field | Type | Default | Description |
|---|---|---|---|
| `policy_from` | `file` or `store` | `file` | Which one is the source of the policy. Never both. |
| `approval` | boolean | `false` | A new version waits for a second admin to approve it before it goes live. Read from the live version, so turning it off is itself a change that needs an approval. |

### Which one wins

One source decides, and Gantry says so out loud when the other disagrees.

- **`policy_from: file`** (the default): the file decides, as it always has. The console and the admin API show the policy and export it, and refuse every change with `policy_in_file`. A GitOps team keeps this setting: the file in git is the only way to change the policy, and the console cannot drift from it.
- **`policy_from: store`**: the store's live version decides. The first gateway on an empty store imports the file as version 1. From then on the file is read only for its `store:` section, which says where the store is. When the file differs from the live version, Gantry says so at every start and the console's Policy page shows a banner. To bring them together, export the live version (`GET /admin/policy`) into the file, or import the file as a new version (`PUT /admin/policy`).

Switching from `store` back to `file` is a restart with the file as the source; switching to `store` again makes the store's live version decide, so import the file first if it changed meanwhile.

### Admin API

Every call takes an admin key and is recorded before anything is done.

| Call | What it does |
|---|---|
| `GET /admin/policy` | The live policy as YAML. `ETag` is its version number, `X-Gantry-Policy-Source` is `store` or `file`. This is the export. |
| `PUT /admin/policy` | A new version from the YAML body (the import). `If-Match` names the version it started from (`none` for the first); a version saved meanwhile makes it `409 version_conflict`. `X-Gantry-Note` says why. |
| `GET /admin/policy/versions` | The history, newest first, with state, who saved it and who approved it. |
| `GET /admin/policy/versions/<n>` | One version, its text and its diff from the version it was drafted on. |
| `POST /admin/policy/versions/<n>/approve` | Puts a pending version live. Refused with `own_version` for the admin who saved it, and with `version_conflict` when another version went live after it was drafted. |
| `POST /admin/policy/versions/<n>/reject` | Rejects a pending version. |
| `POST /admin/policy/versions/<n>/rollback` | Saves the text of version `n` as a new version. It goes live, or waits for approval, as any change does. |
| `POST /admin/policy/dry-run?hours=24` | Replays the last 1 to 720 hours of this gateway's request records against the YAML body and lists the requests it would now refuse, now allow, or allow by another rule. Nothing is saved. |

```bash
curl -s -D - -H "Authorization: Bearer $GANTRY_ADMIN_KEY" http://127.0.0.1:8080/admin/policy -o gantry.policy.yaml
curl -s -X PUT -H "Authorization: Bearer $GANTRY_ADMIN_KEY" -H 'If-Match: "3"' \
  -H "X-Gantry-Note: give interns gpt-4o-mini" --data-binary @gantry.policy.yaml http://127.0.0.1:8080/admin/policy
```

A draft that `gantry check` refuses comes back as `400 invalid_policy` with every problem on its line. A draft that would need a restart (a new audit path, new MCP servers, another store) is refused the same way, so no version goes live that a gateway would then reject.

### In the audit chain

Each call is an `admin` record (`propose_policy`, `approve_policy`, `reject_policy`, `rollback_policy`, `dry_run_policy`) that carries a saved draft's whole text, so a pending or refused draft is on file too. Each gateway then writes a `config_loaded` record with `trigger: store` and `policy_version` when it starts using a new version. The policy holds no secrets: provider keys stay in the environment, in key files or in [sealed credentials](/governance/provider-credentials/).

## gantry check

```bash
gantry check <policy> [--keys <file>]
```

`gantry check` prints every problem, one per line, with file and line, then `<file> cannot be used: N problems above.` It exits 0 when the files can be used and 1 when they cannot. The keys file is `gantry.keys.yaml` beside the policy unless `--keys` names another. A missing keys file is fine.

An unknown key stops the check of that file at that point, because the rest cannot be read reliably. Fix the names it lists and run it again.

| Problem | Message |
|---|---|
| Misspelled key | `gantry.policy.yaml:18: "modles" is not a key Gantry knows. Did you mean "models"?` |
| Unknown key | `"colour" is not a key Gantry knows. Remove it, or check the spelling.` |
| MCP tool on no server | `tool "gitlab.create_issue" is on MCP server "gitlab", which is not defined under mcp. The MCP servers are: github, docs.` |
| Key in the wrong place | `"retries" does not belong here. The keys here are name, principals, models, ... Move it to where it belongs, or remove it.` |
| Missing key | `"url" is missing here. Add it.` |
| Wrong type | `budget is integer 5. Write it as budget: { usd: 20, per: month }.` |
| Wrong version | `version is 2. This version of Gantry reads version 1.` |
| No provider | `the file lists no provider, so no request could be forwarded. Add one under providers.` |
| Model on two providers | `model "claude-sonnet-5-5" is listed by provider "anthropic" and by provider "local" at line 8. A model is served by one provider. Remove it from one of them.` |
| Private URL | `the provider url points at this machine or a private network. If that is intended, for example a local model server, add allow_private: true to the provider.` |
| Bad `key_env` | `key_env is the name of an environment variable, for example OPENAI_API_KEY. The key itself never goes in this file.` |
| Bad principals | `principals must be exactly one of { team: <team> }, { name: <person or workload> } or { any: true }.` |
| `"*"` with other models | `"*" already allows every model. List it alone, or list the models by name.` |
| `retries` too high | `retries is at most 5. Each retry can wait as long as the provider's whole timeout, so more would leave a caller waiting for many minutes.` |
| Unknown `fallback` | `fallback names provider "bedrok", and there is none. The providers are: groq, azure, anthropic, bedrock.` |
| Budget period | `per is "fortnight". A budget starts again each minute, hour, day, week, month or year, or every so many of them: write per: day, per: month, or a count such as per: 6h, 15min, 7d, 2w or 3mo.` |
| Time zone | `tz is "Mars/Olympus", which is not a time zone Gantry knows. Write an IANA name such as America/New_York, Europe/Berlin or Asia/Jerusalem, or leave tz out for UTC.` |
| Organization not listed | `organization "acme-corp" is not listed under orgs. Add it to orgs: at the top of the policy, or check the spelling.` |
| Profile not defined | `rule "payments" includes profile "standrd", which is not defined under profiles. Define it there, or check the spelling.` |
| Limits entry | `a limits entry names one scope: global: true, org: <org> (or "*" for each), or one of team, person, key, customer, tag or model ...` |
| Unknown permission | `"see_everything" is not a permission. The permissions are: see_keys, issue_keys, ...` |
| Budget on an unpriced model | `rule "everyone-else" has a budget in dollars, and model "my-model" has no price, so its spend could not be counted. Add its price ...` |
| Rate | `rpm is the number of requests one person may send per minute, 1 to 1000000, for example rate: { rpm: 600 }. To set no limit, remove the line.` |
| Cache | `ttl_seconds is how long an answer is served again, 1 to 86400 seconds, for example cache: { ttl_seconds: 300 }. To cache nothing, remove the line.` |
| Guardrail not defined | `rule "payments-team" names guardrail "no-secret", which is not defined under guardrails. Define it there, or check the spelling.` |
| Guardrail without an action | `guardrail "mask-pii" has no action. Add action: block, mask or warn.` |
| Webhook without `on_failure` | `guardrail "vendor" does not say what to do when the service fails. Add on_failure: fail_closed ... or fail_open ...` |
| Bad key hash | `gantry.keys.yaml:4: sha256 must be 64 hex characters. Run gantry key new to add a key instead of writing one by hand.` |
| Impossible expiry | `gantry.keys.yaml:4: expires 2026-11-31 is not a date: November 2026 has 30 days. Write a day that exists.` |

Each message starts with `<file>:<line>: `, shortened in the table.

**Warnings** do not stop the file from loading: a model a rule names that no provider serves, a provider model name with spaces at its ends or holding `*`, two provider model names that differ only in case or spaces, and a key whose expiry has passed. `gantry serve` and a reload accept expired keys, because keys expire while Gantry runs.

A rule's `tools:` list and the `mcp:` servers it names are described in [MCP gateway](/governance/mcp-gateway/).
</Aside>
