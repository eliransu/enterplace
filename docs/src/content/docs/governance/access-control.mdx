Two controls on who reaches the model routes and from where: address ranges on keys and rules, and JWTs from your own identity provider accepted in place of a Gantry key. Both are refusals with a code and a record, decided before the request body is read.

## Source address ranges

```yaml title="gantry.policy.yaml"
version: 1
providers:
  - name: openai
    kind: openai
    url: https://api.openai.com
    key_env: OPENAI_API_KEY
    models: [gpt-4o-mini]
trusted_proxies: [10.0.0.0/8]
rules:
  - name: ci
    principals: { team: ci }
    models: [gpt-4o-mini]
    from: [10.20.0.0/16]
  - name: everyone
    principals: { any: true }
    models: [gpt-4o-mini]
```

A key takes its own list with `from:` in its entry, `gantry key update <prefix> --from 203.0.113.0/24`, or `PATCH /admin/keys/<prefix>` with `{"from": ["203.0.113.0/24"]}`.

| Where | Field | Effect |
|---|---|---|
| Rule | `from: [<cidr>, ...]` | Every caller the rule decides for must send from one of the ranges |
| Key | `from: [<cidr>, ...]` | Requests with this key must come from one of the ranges |
| Top level | `trusted_proxies: [<cidr>, ...]` | Load balancers whose `X-Forwarded-For` names the client |

A range is written as `10.0.0.0/8`, `2001:db8::/32`, or a single address. A key and its rule both apply: a request must pass each list that is set. An IPv4 address mapped into IPv6 counts as IPv4.

### Behind a load balancer

The client's address is the connection's. When the connection comes from an address in `trusted_proxies`, Gantry reads `X-Forwarded-For` from the right and takes the first address that is not a trusted proxy. From any other address the header is ignored, so a caller cannot claim another address by writing it. The decision record's `client` is the address the check used.

<Aside type="caution">
List only your own load balancers in `trusted_proxies`. An address listed there can name any client it likes.
</Aside>

A request whose address cannot be known (Gantry embedded without a listener) is refused under a `from` list: it fails closed.

## Browser pages (CORS)

A page that calls Gantry from the browser, such as the Claude add-in for Office or an Open WebUI direct connection, needs Gantry to answer cross-origin requests. `cors:` lists the origins allowed to. It is off by default: without it Gantry sends no CORS headers and a browser refuses every cross-origin call.

```yaml
cors:
  allowed_origins: [https://pivot.claude.ai, https://chat.example.com]
```

- An origin is the scheme and host (and port) the page is served from, as the browser sends it in `Origin`: `https://pivot.claude.ai`, `http://localhost:3000`. No path, no trailing slash. `"*"` allows any origin.
- Gantry answers the `OPTIONS` preflight of a listed origin itself, with the methods it serves and the headers the page asked for, and records nothing for it: a preflight carries no key.
- The call itself is decided, governed and recorded as any other, with the caller's own Gantry key in `Authorization` or `x-api-key`. Its answer names the origin and lets the page read `x-gantry-decision`.
- Credentials are never allowed (`Access-Control-Allow-Credentials` is never sent, with `"*"` or without): callers authenticate with a key in a header, never a cookie.
- The console and the admin API answer no other origin, whatever `cors:` lists.
- A change applies on the next reload, with no restart.

## JWTs from your identity provider

A workload or a person can call the model routes with an access token from your identity provider, sent as `Authorization: Bearer <jwt>`, in place of a Gantry key. Gantry checks it and decides and records the request as the person the token names.

```yaml title="gantry.policy.yaml"
version: 1
providers:
  - name: openai
    kind: openai
    url: https://api.openai.com
    key_env: OPENAI_API_KEY
    models: [gpt-4o-mini]
jwt:
  - issuer: https://login.example.com
    audience: gantry
    jwks_url: https://login.example.com/.well-known/jwks.json
    person_claim: email
    team_claim: team
rules:
  - name: everyone
    principals: { any: true }
    models: [gpt-4o-mini]
```

| Field | Type | Default | Description |
|---|---|---|---|
| `issuer` | string | required | The token's `iss` must equal it |
| `audience` | string | required | The token's `aud` must be it or contain it |
| `jwks_url` | string | required | Where the issuer publishes its signing keys, over `https` (`http` only on this machine) |
| `person_claim` | string | `sub` | The claim that names the person, such as `email` |
| `team_claim` | string | one of the two | The claim that names the team. A list of one value is read as that value |
| `team` | string | one of the two | One team for every caller of this issuer |
| `role_claim` | string | none | The claim (a string or a list, such as `groups`) whose values sign in to the admin API. Without it, this issuer's tokens are refused on the admin API |

What is checked, each failing closed:

- The issuer is listed, and the token is signed with RS256 or ES256 by a key in its key set. A token whose key is not in the cached set fetches the set again, at most every 30 seconds per issuer.
- `aud` holds the audience, `exp` is set and not passed (60 seconds of clock difference allowed), and `nbf` has come.
- The person and team claims are each one name: letters, digits, dots, dashes, underscores and `@`.

The decision record names the person and team from the token, with `"auth": "jwt"`, `jwt_issuer` and `jwt_subject`. The token itself is never recorded. Its `key` is the first 8 hex characters of the SHA-256 of issuer and subject, so a [kill switch](/governance/kill-switches/) by key prefix, `gantry kill --person`, budgets, rate limits and rules all work for JWT callers as for keys.

Keys keep working beside JWTs.

### The admin API

The same tokens sign in to the admin API (`/admin/keys`, `/admin/kills`, `/admin/credentials`, `/admin/policy` and the rest) when the issuer has `role_claim`. The token gets the first role under [`roles:`](/governance/policy/#console-roles) whose `sso_values` holds one of the claim's values, and may do what that role permits, as a key with that role may:

```yaml title="gantry.policy.yaml"
jwt:
  - issuer: https://login.example.com
    audience: gantry
    jwks_url: https://login.example.com/.well-known/jwks.json
    person_claim: email
    team: platform
    role_claim: groups
roles:
  - name: key-admins
    permissions: [see_keys, issue_keys, revoke_keys]
    sso_values: [gantry-key-admins]
  - name: policy-editors
    permissions: [edit_policy]
    sso_values: [gantry-policy]
```

```bash
curl -H "Authorization: Bearer $TOKEN" https://gantry.example.com/admin/keys
```

A token whose claim holds no role's value is refused with `not_admin` (403), naming the claim. A token that fails a check above is refused with its `jwt_*` code, as on the model routes. Each call's `admin` record names the person, with `"auth": "jwt"`, `jwt_issuer` and `jwt_subject`; the token is never recorded. `DELETE /admin/keys/self` gives up the Gantry key it is sent with, so it is refused for a token.

## Errors

| Code | Status | Cause |
|---|---|---|
| `ip_not_allowed` | 403 | The request's address is outside the key's or the rule's `from`. The record says which (`ip_not_allowed: key` or `rule`). |
| `jwt_untrusted` | 401 | The token's issuer is not under `jwt:`. |
| `jwt_invalid` | 401 | Malformed, wrong algorithm, unknown key, bad signature, wrong audience, or not valid yet. |
| `jwt_expired` | 401 | The token's `exp` has passed. |
| `jwt_claims` | 401 | The person or team claim is missing, holds several values, or is not a name. |
| `jwt_keys_unavailable` | 503 | The issuer's key set could not be read and none was cached. May clear by itself. |
