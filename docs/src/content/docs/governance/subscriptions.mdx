A provider with `auth: passthrough` sends each caller's own login on to Anthropic or ChatGPT and holds no key of Enterplace's. Claude Code on a Claude subscription (Pro, Max, Team or Enterprise) goes through Enterplace this way, so a company governs it without buying API access for anyone. Codex on a ChatGPT login (Plus, Pro, Business, Enterprise or Edu) goes through a provider of kind `openai` at `https://chatgpt.com/backend-api/codex` the same way. Setup is on the [Claude Code](/integrations/claude-code/) and [Codex](/integrations/codex/#chatgpt-subscription) pages.

## The provider

```yaml title="enterplace.policy.yaml"
version: 1
providers:
  - name: claude-subscriptions
    kind: anthropic
    url: https://api.anthropic.com
    auth: passthrough
    identity: required
    models: ["claude-*"]
rules:
  - name: everyone
    principals: { any: true }
    models: ["*"]
    rate: { tpd: 5000000, rpd: 2000 }
```

| Field | Values | Default | Description |
|---|---|---|---|
| `auth` | `key`, `passthrough` | `key` | `passthrough`: the caller's own `Authorization` (or `x-api-key`) goes to the provider unchanged. The provider takes no `key_env`, `key_file`, `credential` or `keys`. Kind `anthropic` (Claude) or `openai` (ChatGPT) only |
| `identity` | `required`, `optional` | `required` | `required`: a request without `x-enterplace-user` is refused with `person_needed`. `optional`: it is recorded as the person `unknown`, by session. Only with `auth: passthrough` |

A passthrough provider and a keyed provider may list the same model. A request that carries a login goes to the passthrough one; a request with an Enterplace key goes to the keyed one. Neither ever falls back to the other.

## Who sent it

The person comes from `x-enterplace-user`, which Claude Code sends from `ANTHROPIC_CUSTOM_HEADERS` and Codex from its model provider's `http_headers`. Its value is an Enterplace person token (`enterplace_u_...`, from the console, `enterplace key new --identity-only`, or the device agent) or any Enterplace key of the person (from `enterplace login`). The token names the person and team for rules, records, guardrails, kill switches and limits. On its own it reaches no model: sent as the only credential it is refused with `person_token_only`.

Every request is named by default. `enterplace start` writes `identity: required` and makes a person token for whoever runs it, printed once with the Claude Code lines, so the first request already carries a name.

A company can allow unnamed requests while it rolls out tokens: on the console's **Coding agents** page, or with `identity: optional` on the provider. The console switch (`PUT /console/api/policy/identity`) sets every passthrough provider at once, as a policy edit that is checked, audited with the admin's name and used within 2 seconds. Without `x-enterplace-user`, on `identity: optional`, the person is `unknown` and the team `unknown`, and each Claude Code session is told apart by a hash of its session ID. The console warns while unnamed requests are allowed.

## What applies

| | On subscription traffic |
|---|---|
| Rules and model lists | Yes |
| Guardrails on requests and answers, streamed too | Yes |
| Kill switches (person, team, key, model, all) | Yes. `unknown` can be stopped by name |
| MCP gateway, tool permissions | Yes |
| Audit records, request log, analytics, coverage, plugin events | Yes. Decision records carry `"auth": "passthrough"` and `"identity"` |
| Rate limits: `rpm`, `rph`, `rpd`, `tpm`, `tpd`, `parallel` | Yes |
| Dollar budgets | Only with `budget_basis: api_equivalent` on the rule |
| Answer cache | Yes, per person |

## Cost is an estimate

A subscription is paid by the seat, not by the request. Enterplace still records the tokens Anthropic reports and prices them at the API list price. The usage record says so with `"cost_basis": "api_equivalent_estimate"`, and the console shows the figure as `~$0.0123 (est.)`. Read it as relative usage across people and teams, not as an invoice.

Dollar budgets limit what the organization is billed, so by default they do not count subscription traffic (the usage record says `"budget": "not_counted"`). To limit it in dollars anyway, at the estimate:

```yaml
rules:
  - name: everyone
    principals: { any: true }
    models: ["*"]
    budget: { usd: 50, per: day }
    budget_basis: api_equivalent
```

The console's budget meters (Spend) and budget forecasts (Usage) count exactly what the gateway counts. Subscription traffic a budget leaves out is never in its meter: the meter's note says how much of it there was, as an estimate not counted against the budget.

## Limit tokens and requests

Tokens are what a subscription is metered in, so limit them directly:

| Limit | Where | Counts |
|---|---|---|
| `tpd` | `rate:` of a rule, or a `limits:` entry | Tokens (prompt and answer) per calendar day, UTC, per person for a person or `any` rule, per team for a team rule |
| `rpd`, `rph` | `rate:` | Requests per day and per hour, per person |
| `tpm` | `rate:` | Tokens per minute |

A request is admitted while the day's tokens are under `tpd` and counted with what its answer used, so one request may end above the limit; the next is refused with `rate_limited` and `Retry-After` until midnight UTC. Per team:

```yaml
limits:
  - { team: payments, rate: { tpd: 20000000 } }
```

## What is never kept

The login is taken off the request before anything reads it. It goes to the passthrough provider and nowhere else: not to a guardrail webhook, events plugin, trace, log line, audit record, request index or cache key, and no hash of it is recorded. A request without `x-enterplace-user` is told apart by its session ID, or, when it names none, by a short fingerprint that cannot be turned back into the login.

## Limits

<Aside type="caution">
Each company should check that routing its plan's traffic through its own gateway fits Anthropic's terms for that plan: the consumer terms for Pro and Max, and the commercial agreement for Team and Enterprise. Enterplace does not change what Claude Code sends; it reads it on the way.
</Aside>

- Anthropic only for now. OpenAI's Codex with a ChatGPT login is planned on the same `auth: passthrough` field.
- Binding a subscription to a person without a token (by its login, the first time it is seen after a console sign-in) is not offered: Claude Code renews its login token on its own, so a binding to one token would not last. Use person tokens, `enterplace login` or the device agent.
- The `/passthrough/<provider>/...` route takes Enterplace keys only.
