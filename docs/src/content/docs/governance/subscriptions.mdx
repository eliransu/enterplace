A provider with `auth: passthrough` sends each caller's own login on to Anthropic and holds no key of Gantry's. Claude Code on a Claude subscription (Pro, Max, Team or Enterprise) goes through Gantry this way, so a company governs it without buying API access for anyone. Setup is on the [Claude Code](/integrations/claude-code/) page.

## The provider

```yaml title="gantry.policy.yaml"
version: 1
providers:
  - name: claude-subscriptions
    kind: anthropic
    url: https://api.anthropic.com
    auth: passthrough
    identity: optional
    models: ["claude-*"]
rules:
  - name: everyone
    principals: { any: true }
    models: ["*"]
    rate: { tpd: 5000000, rpd: 2000 }
```

| Field | Values | Default | Description |
|---|---|---|---|
| `auth` | `key`, `passthrough` | `key` | `passthrough`: the caller's own `Authorization` (or `x-api-key`) goes to the provider unchanged. The provider takes no `key_env`, `key_file`, `credential` or `keys`. Kind `anthropic` only |
| `identity` | `required`, `optional` | `required` | `optional`: a request without `x-gantry-user` is recorded as the person `unknown`, by session. Only with `auth: passthrough` |

A passthrough provider and a keyed provider may list the same model. A request that carries a login goes to the passthrough one; a request with a Gantry key goes to the keyed one. Neither ever falls back to the other.

## Who sent it

The person comes from `x-gantry-user`, which Claude Code sends from `ANTHROPIC_CUSTOM_HEADERS`. Its value is a Gantry person token (`gantry_u_...`, from the console, `gantry key new --identity-only`, or the device agent) or any Gantry key of the person (from `gantry login`). The token names the person and team for rules, records, guardrails, kill switches and limits. On its own it reaches no model: sent as the only credential it is refused with `person_token_only`.

Without `x-gantry-user`, on `identity: optional`, the person is `unknown` and the team `unknown`, and each Claude Code session is told apart by a hash of its session ID. A company can start with no setup per person and add tokens later.

## What applies

| | On subscription traffic |
|---|---|
| Rules and model lists | Yes |
| Guardrails on requests and answers, streamed too | Yes |
| Kill switches (person, team, key, model, all) | Yes. `unknown` can be stopped by name |
| MCP gateway, tool permissions | Yes |
| Audit records, request log, analytics, coverage, plugin events | Yes. Decision records carry `"auth": "passthrough"` and `"identity"` |
| Rate limits: `rpm`, `rph`, `rpd`, `tpm`, `tpd`, `parallel` | Yes |
| Dollar budgets | Only with `budget_basis: api_equivalent` on the rule |
| Answer cache | Yes, per person |

## Cost is an estimate

A subscription is paid by the seat, not by the request. Gantry still records the tokens Anthropic reports and prices them at the API list price. The usage record says so with `"cost_basis": "api_equivalent_estimate"`, and the console shows the figure as `~$0.0123 (est.)`. Read it as relative usage across people and teams, not as an invoice.

Dollar budgets limit what the organization is billed, so by default they do not count subscription traffic (the usage record says `"budget": "not_counted"`). To limit it in dollars anyway, at the estimate:

```yaml
rules:
  - name: everyone
    principals: { any: true }
    models: ["*"]
    budget: { usd: 50, per: day }
    budget_basis: api_equivalent
```

## Limit tokens and requests

Tokens are what a subscription is metered in, so limit them directly:

| Limit | Where | Counts |
|---|---|---|
| `tpd` | `rate:` of a rule, or a `limits:` entry | Tokens (prompt and answer) per calendar day, UTC, per person for a person or `any` rule, per team for a team rule |
| `rpd`, `rph` | `rate:` | Requests per day and per hour, per person |
| `tpm` | `rate:` | Tokens per minute |

A request is admitted while the day's tokens are under `tpd` and counted with what its answer used, so one request may end above the limit; the next is refused with `rate_limited` and `Retry-After` until midnight UTC. Per team:

```yaml
limits:
  - { team: payments, rate: { tpd: 20000000 } }
```

## What is never kept

The login is taken off the request before anything reads it. It goes to the passthrough provider and nowhere else: not to a guardrail webhook, events plugin, trace, log line, audit record, request index or cache key, and no hash of it is recorded. A request without `x-gantry-user` is told apart by its session ID, or, when it names none, by a short fingerprint that cannot be turned back into the login.

## Limits

<Aside type="caution">
Each company should check that routing its plan's traffic through its own gateway fits Anthropic's terms for that plan: the consumer terms for Pro and Max, and the commercial agreement for Team and Enterprise. Gantry does not change what Claude Code sends; it reads it on the way.
</Aside>

- Anthropic only for now. OpenAI's Codex with a ChatGPT login is planned on the same `auth: passthrough` field.
- Binding a subscription to a person without a token (by its login, the first time it is seen after a console sign-in) is not offered: Claude Code renews its login token on its own, so a binding to one token would not last. Use person tokens, `gantry login` or the device agent.
- The `/passthrough/<provider>/...` route takes Gantry keys only.
